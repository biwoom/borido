# 보리도 기술 명세

- 통합 개정 1.0 · 2026-10-29 · 현재 개발 기준
- 담당: 프로그램 구조·실행·API 경계·파일 변경/복구·변환·검증·빌드·인증/배포.
- 데이터 규칙은 [콘텐츠 명세](content-spec.md), 상호작용은 [화면 명세](ui-spec.md)가 기준이다. W01–W05 기반/프로젝트/로컬 API/최초 실행 UI와 읽기 전용 콘텐츠 검증은 있으며 저장·편집 기능은 아직 없다.

<a id="architecture"></a>
## 1. 실행 영역과 디렉터리

프로그램·운영 원본의 기준 저장소는 [biwoom/borido](https://github.com/biwoom/borido), Git 주소는 `https://github.com/biwoom/borido.git`다. 2026-10-29 확인한 기본 브랜치는 `main`, 공개성은 public이다. D23–D24에 따라 한 체크아웃과 `main`을 관리 기준으로 삼고, 공개 결과는 같은 저장소의 GitHub Actions Pages artifact로 배포한다.

```text
biwoom/borido 체크아웃 · main
├── app/admin/ → app/server/ → core/
├── scripts/ CLI → core/build + core/render + site/
└── project/                         # 예약된 기본 운영 루트
    ├── content/ · media/ · config/  # main에 원본 저장
    └── dist/                        # 로컬 결과, main에서 미추적
             ↓ 결과·원본 변경 확인과 명시 승인
       main fast-forward 푸시 → 정확한 커밋의 Actions workflow
                                      ↓
                           검증된 Pages artifact만 공개
```

공개 사이트는 정적 파일만으로 기본 읽기/탐색이 가능해야 한다. Node.js 서버와 DB가 공개 호스팅에 필요하지 않다. 설치 후 콘텐츠 작성·저장·미리보기·빌드는 오프라인 가능, 배포·최초 도구/브라우저 설치는 필요한 네트워크 작업으로 구분한다.

프로그램 예정 구조는 `app/server/{routes,services,security}`, `app/admin/{scripts,styles,assets}`, `core/`, `site/{templates,styles,scripts}`, `scripts/`, `tests/{unit,integration,e2e,fixtures}`, `docs/`와 패키지/잠금/지침 파일이다. 실제 운영 `content/`, `media/`, `config/`, `dist/`는 루트에 흩어놓지 않고 예약 `project/` 아래에 둔다. 프로그램 코드는 `project/` 원본을 직접 덮어쓰지 않고 Core의 프로젝트 경계를 통한다. 샘플은 테스트/예시 자료임을 명확히 표시한다.

|모듈|책임과 경계|
|---|---|
|`project`|루트/설정/초기화. 앱 업데이트와 사용자 프로젝트 생성을 구분|
|`content` / `schema`|원본 CRUD/매핑, 코드 스키마·필드 검증|
|`taxonomy` / `tree`|출처가 확인된 분류/참조, 폴더 기반 관계·독립 트리·정렬|
|`markdown` / `url` / `media`|본문/앵커/각주, ID→주소/이력, 자산 참조/사용/선별|
|`build` / `render`|검증/선별/작업 조정, 정리된 페이지 데이터의 템플릿 렌더링|
|`server` / `git`|제한된 API/파일 요청, Git·gh 상태/전송 경계|
|`admin` / `site`|관리 UI, 공개 템플릿/스타일/스크립트. 원본을 직접 탐색하지 않음|

Core는 UI/프런트엔드 라이브러리를 모르고 편집기·CLI·생성기는 같은 검증/주소/변환을 사용한다. UI 규칙 중복·타 모듈 내부 경로 조작·범용 이벤트/DI 프레임워크·무리한 컴포넌트 공유를 피한다. 함수는 명시적 입력/결과/진단을 반환한다.

시작 시 한 프로젝트 루트만 연다. 인자가 없으면 체크아웃의 정확한 `project/`, 인자가 있으면 명시한 외부 프로젝트를 사용한다. 다른 프로그램 내부 경로·요청으로 바꾸는 루트·전역 최근 프로젝트 DB·원격 CMS를 도입하지 않는다. 앱 업데이트와 프로젝트 초기화를 구분하고 `project/` 원본/설정을 무조건 덮어쓰지 않는다.

## 2. 채택한 도구와 실행 환경

|영역|채택|
|---|---|
|실행|Node.js 24 LTS, npm, JavaScript ES Modules|
|로컬 서버/UI|Node 기본 `http`, HTML/CSS/바닐라 JS의 명시적 상태 관리|
|Markdown/각주|`markdown-it`, `markdown-it-footnote`와 보리도 변환 계층|

정확한 Node/npm·패키지 패치 버전, 라이선스·전이 의존성·취약점·ESM/기능 호환은 W01 및 해당 도입 단계에서 확인하고 잠금 파일로 관리한다(R01). ‘채택’은 설치/전체 조합 테스트 통과를 뜻하지 않는다. 라이브러리 추가는 실제 필요·내장 대안·라이선스·유지보수·보안·호환을 평가하며 편의만으로 중복 도구를 추가하지 않는다.

### 2.1 W01 검증 기준

2026-10-29 W01에서 Node.js 24.22.2 LTS와 npm 11.14.1을 기준으로 `package-lock.json`을 생성했다. `package.json`은 Node 24 LTS와 npm 11만 허용하며 `.npmrc`가 엔진 불일치 설치를 차단한다. 당시 개발 컴퓨터의 기본 Node 25.2.1은 검증에 사용하지 않고 임시 Node 24 환경에서 잠금 설치와 명령을 실행했다.

잠금 재설치 69개 패키지와 `npm audit --audit-level=low`에서 알려진 취약점 0건을 확인했다. Markdown/각주→정화, Ajv, Nunjucks, Basecoat CSS 해석을 한 Node 24 ESM 프로세스에서 검사했다. 이 결과는 구체적인 스키마·정화 허용 목록·템플릿이나 브라우저 제품 기능의 통과 증거가 아니다.

검증 환경은 macOS Darwin 24.4.0 x86_64, Git 2.39.5, GitHub CLI 2.94.0이다. Windows/Linux와 실제 Chromium/Firefox/WebKit 브라우저 바이너리는 아직 검증하지 않았다. 패키지를 실제로 사용하는 W05·W11 및 브라우저 작업에서 호환성·취약점·지원 범위를 다시 확인한다.

로컬 편집기 최초 검증 환경은 macOS다. Windows/Linux 지원은 실제 검증 후 표시한다. 공개 사이트는 Chromium/Firefox/WebKit 자동 검증과 실제 Safari/모바일 확인을 목표로 한다. 지원 OS/브라우저 버전 범위는 검증 기록으로 확정하며 에뮬레이션을 실제 기기 통과로 보고하지 않는다.

Basecoat의 소스 CSS/Tailwind 빌드와 이미 컴파일된 배포 파일을 구분한다. 기본 배포 CSS를 제공하는 것으로 시작하고 vendor를 수정하지 않는다. 보리도 공통/컴포넌트 CSS를 따로 유지한다. 필요 전에는 Tailwind 전체 빌드·모든 컴포넌트 JS·React/Vue/TypeScript를 추가하지 않는다.

## 3. 로컬 서버와 API 계약

서버는 `127.0.0.1`에 바인딩하고 사용 가능한 루프백 포트 또는 실행 인자로 지정한 포트를 사용한다. 실제 Origin/프로젝트를 안내한다. 브라우저 요청이 임의로 허용 루트를 바꾸게 하지 않는다.

### 3.1 요청 보호

- 허용 Host/Origin을 검사하고 임의 CORS 허용을 하지 않는다. 변경 요청에는 로컬 실행 세션 토큰을 검사한다. 계정 시스템을 추가하는 것이 아니며 토큰을 일반 설정에 저장하지 않는다.
- GET은 원본 변경/빌드/배포 같은 부작용을 실행하지 않는다. 민감 원본·복구·작업 기록을 정적 파일 루트로 노출하지 않는다.
- JSON/업로드의 크기·형식·필드를 검증한다. 상한은 샘플/지원 범위에 맞춰 정하고 무제한으로 열지 않는다(R02).
- 콘텐츠 작업은 ID 중심으로 받고 서버가 인덱스에서 경로를 해석한다. 초기화·미디어 등록 등의 경로 입력도 정규화/허용 범위를 별도 검증한다.
- 루트와 정규화/실제 경로를 비교하며 상대/절대/인코딩 우회·심볼릭 링크·파일명 충돌·검증 후 변경 위험을 점검한다. 읽기·쓰기·목록·삭제·미리보기·빌드 모두 같은 경계를 사용한다.
- 실행 파일과 인자/작업 디렉터리를 분리한다. 브라우저에서 셸 문자열이나 임의 명령을 받는 API는 제공하지 않는다.
- 오류/로그/응답의 비밀·인증 출력·민감 절대 경로를 정제한다. 사용자 진단에는 프로젝트 상대 경로·ID·필드·가능한 조치를 제공한다.

### 3.2 계약 범위

|그룹|필요 계약|
|---|---|
|프로젝트|설정 읽기/저장, 초기화 전 확인, 기존 열기/권한/오류|
|콘텐츠/트리|목록/읽기/생성/저장, 이동/정렬/삭제 영향·확인·실행·복구|
|미디어|등록/목록/참조 삽입/사용 확인·이동/삭제/복구|
|미리보기|미저장 모델 변환, 마지막 빌드 미리보기, 진단/정리|
|검증/빌드|실행, 작업 상태·진단·결과 식별 조회|
|Git/gh/배포|설치/인증/원격/권한 상태, 변경 목록, 검증 결과/대상 확인·명시 실행|

실제 함수/엔드포인트·HTTP 메서드·요청/응답·오류 코드·리비전/확인 토큰 형식은 구현 전에 R02 계약으로 작성한다. 기존 함수 이름 예시를 이미 존재하는 API로 취급하지 않는다. 저장 충돌과 원격 오류를 정상 성공 응답으로 감추지 않는다. UI는 같은 스키마를 재구현하는 대신 서버 진단과 Core 계약을 사용한다.

<a id="w02-project-contract"></a>
### 3.3 W02 프로젝트/설정 계약

`core/project`는 `initializeProject`, `openProject`, `writeProjectSettings`와 설정 생성/검증 함수를 제공한다. `npm run project -- init|open`은 같은 Core를 사용하는 임시 CLI다. W03 서버도 이 계약을 호출하며 별도 설정 규칙을 만들지 않는다.

- 신규 초기화는 명시한 절대/상대 경로를 실제 경로로 정규화하고 프로그램 체크아웃 밖인지 확인한다. 상위 폴더가 존재하고 읽기/쓰기가 가능해야 하며 대상은 존재하지 않아야 한다.
- 준비 자료는 같은 상위 폴더의 무작위 임시 경로에 만들고 대상 폴더를 배타적으로 예약한 뒤 `content`, `media`, `config`, `dist`를 옮긴다. 기존 파일/폴더는 덮어쓰지 않는다. 중간 반영 실패는 `.borido-initializing` 표식과 `PROJECT_INITIALIZATION_INCOMPLETE`로 열기/재초기화를 막는다.
- 기존 열기는 필수 원본 폴더와 `config/site.json`을 확인한다. 생성물 `dist`는 없어도 열 수 있다. 한 호출 결과는 한 실제 루트만 가진다.
- 성공은 `{ ok: true, project: { root, settings, settings_revision, editable, diagnostics } }`, 실패는 `{ ok: false, error: { code, message, details } }` 형태다. CLI도 같은 오류 객체를 JSON으로 출력한다.
- 설정 리비전은 읽은 `site.json` 바이트의 SHA-256이다. 저장에는 `expectedRevision`이 필요하며 불일치하면 `PROJECT_REVISION_CONFLICT`로 원본을 바꾸지 않는다.
- 공개 URL을 생략한 초기화는 `base_url: null`, `base_path: "/"`, 원본/배포 저장소 `null`로 시작한다. 네트워크·Git/gh·원격 저장소 생성/확인은 실행하지 않는다.

W02는 단일 설정 파일의 안전한 교체까지만 담당한다. 일반 원본의 다중 파일 작업 기록·백업·복구는 W06, HTTP 요청/허용 루트 고정과 오류 정제는 W03에서 확장한다.

D23은 W02 완료 후 기본 배치를 변경했고 W06에서 다음 전환을 구현·검증했다.

- 인자 없는 실행은 정확한 `<checkout>/project`만 기본 후보로 사용한다.
- 다른 프로그램 하위 경로는 계속 거절하고 외부 프로젝트는 명시 인자로만 연다.
- 기존 외부 `/Users/damjin/Projects/my-borido-site`는 W06 시작 시 존재하지 않아 이동·삭제하지 않았다.
- 프로그램 변경과 `project/` 원본 변경의 허용 경로를 분리하고 테스트/개발 명령이 운영 원본을 fixture로 사용하지 않게 한다.
- 인자 없는 `npm run dev`는 통합 프로젝트, `--project`는 명시 외부 프로젝트를 연다.

<a id="w03-server-contract"></a>
### 3.4 W03 서버·요청·경로 계약

`npm run dev -- --project <path> [--port <number>]`는 Node 기본 HTTP 서버를 `127.0.0.1`에만 연다. 포트 기본값 `0`은 OS가 사용 가능한 포트를 선택하게 한다. 시작 성공 시 실제 Origin·프로젝트 루트·무작위 256비트 세션 토큰을 터미널 JSON으로 한 번 전달한다. 토큰은 프로세스 메모리에만 두며 프로젝트 설정/로그에 저장하지 않는다.

|메서드/경로|보호|결과|
|---|---|---|
|`GET /health`|정확한 Host|민감 정보 없는 `{ "ok": true }`|
|`GET /api/v1/bootstrap`|정확한 Host·세션|고정 루트의 `new`/`existing`/`blocked` 상태와 프로젝트 또는 정제 오류|
|`POST /api/v1/project`|정확한 Host·세션·Origin, `application/json`|`new` 상태의 고정 경로만 W02로 초기화|
|`GET /api/v1/project`|정확한 Host·`X-Borido-Session`; Origin이 있으면 정확히 일치|W02 프로젝트/설정·리비전·진단|
|`PUT /api/v1/project/settings`|정확한 Host·세션·Origin, `application/json`|`settings` 또는 단순 UI `input`, `expected_revision`으로 W02 설정 저장|

- 성공은 W02와 같은 `{ ok: true, project }`, 실패는 `{ ok: false, error: { code, message, details } }` JSON이다. 리비전 충돌은 409, 세션 실패 401, Host/Origin/권한 실패 403, 크기 초과 413, 미디어 타입 오류 415로 구분한다.
- JSON 본문은 UTF-8 `application/json`만 받고 최대 65,536바이트다. 요청 대상은 최대 4,096바이트이며 쿼리, 잘못된 percent 인코딩, 인코딩 구분자/NUL, `.`/`..`, 역슬래시와 authority 형태를 거절한다.
- API 응답은 `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`를 사용한다. `Access-Control-Allow-Origin`을 보내지 않으며 OPTIONS 사전 요청도 포괄 허용하지 않는다.
- 서버가 시작할 때 W02로 실제 루트를 한 번 고정한다. 요청에는 루트나 파일 경로를 받는 API가 없다. GET은 원본을 쓰지 않고 PUT 설정만 리비전 확인 후 변경한다.
- `resolveProjectPath`는 후속 내부 서비스가 사용할 공통 경계다. 프로젝트 상대 경로만 받고 실제 루트 포함 여부를 비교하며 존재하는 대상/새 대상 부모의 심볼릭 링크 이탈을 차단한다. 현재 API는 원본 파일을 직접 제공하지 않는다.
- 헤더/요청 제한과 15초 요청·5초 헤더 제한을 적용한다. 임의 셸·프로그램 실행, 정적 프로젝트 루트 노출, 런타임 루트 교체, 자동 Git/GitHub 작업은 제공하지 않는다.

고정 관리자 자산 `/`, `/assets/basecoat.css`, `/assets/admin.css`, `/assets/admin.js`만 세션 없이 제공한다. 프로젝트 폴더는 정적 루트가 아니다. 관리자 자산은 no-store, CSP, `nosniff`, `frame-ancestors 'none'`을 적용한다. 시작 URL은 세션을 fragment로 전달하며 화면이 `sessionStorage`로 옮기고 주소에서 제거한다.

<a id="w04-admin-contract"></a>
### 3.5 W04 최초 실행·설정 UI 계약

- 실행 인자의 고정 경로가 없으면 `new`, 유효한 보리도 프로젝트면 `existing`, 존재하지만 열 수 없으면 `blocked`다. UI 요청으로 루트를 선택하거나 변경하지 않는다.
- `new`는 사이트명·설명·기본 언어·시간대·작성자·라이선스·전체 공개 URL을 서버 입력으로 보내며 서버가 W02 설정을 생성한다. 브라우저 언어/시간대는 확인 가능한 기본값일 뿐 자동 확정값이 아니다.
- `existing`은 같은 필드를 명시 저장하고 읽을 때 받은 설정 리비전을 요구한다. 원본/배포 저장소 필드는 이 단순 화면이 보존하며 자동 연결·Git/GitHub 작업을 하지 않는다.
- 저장 버튼과 Cmd/Ctrl+S를 제공하고 자동 저장하지 않는다. 미저장 이동/새로고침은 경고하며 실패·충돌 상태를 화면에 남긴다.
- 생성 성공 후 경론 목록의 빈 상태로 이동한다. 경론 CRUD는 W05 이후이며 미리보기·빌드·배포 버튼은 해당 작업 전까지 비활성이다.
- Basecoat Vega 배포 CSS, 별도 `tokens.css`, 보리도 컴포넌트 CSS와 바닐라 JS는 모두 로컬에서 제공한다. 토큰은 검정·흰색·중립 회색 기반에 황금색 `#f0b100` 주 강조, 연두색 `#00c951` 보조 강조를 사용한다. Chromium 자동 흐름과 1440px/390px 가로 오버플로·콘솔 오류를 확인했으며 Firefox/WebKit·실제 모바일 기기 통과로 확대 해석하지 않는다.

W05 이후 ID 중심 콘텐츠 엔드포인트도 같은 Host/Origin/세션/본문/경로 경계를 사용하며 파일 경로를 외부 CRUD 식별자로 받지 않는다.

<a id="w05-content-contract"></a>
### 3.6 W05 콘텐츠 스키마·검증·인덱스 계약

`core/content`는 `text`, `text_area`, `tree_node`, `text_document`, `story`, `blog`, `page` 7개 레코드와 사이트 설정, 미디어 목록, 분류, URL 이력의 Ajv strict 스키마를 제공한다. 공통 레코드는 스키마 버전 1, UUID v4, 명시 유형·제목·slug·상태, 실제 UTC ISO 시각을 요구한다. 유형별 본문 파일명과 필드 외의 추가 필드는 오류이며 자동 삭제하지 않는다.

`indexProjectContent({ root })`는 W02로 실제 외부 루트를 연 뒤 `content/`, `media/`, `config/`를 읽기 전용으로 순회한다. 심볼릭 링크를 따라가지 않고 경론 세 영역·폴더 부모/유형·본문 매핑·ID 중복·형제 order 동률, 미디어 루트/중복/실제 파일, 분류 파일/항목 코드와 URL 이력 형식을 진단한다. 결과는 `{ ok, project, summary, diagnostics, index }`이며 진단은 `level`, `code`, 프로젝트 상대 `path`, `record_id`, `field`, `message`, `details`를 사용한다. 경고만 있으면 성공이지만 오류가 하나라도 있으면 실패다.

`media/assets.json`, 분류 파일과 `config/url-history.json`은 해당 기능 전까지 선택이며 없다고 생성하지 않는다. 미디어 MIME/크기 허용 목록은 R02/W13에서 정한다. 구체 필드가 아직 확정되지 않은 `content-types.json`이 존재하면 W26 전에는 적용하지 않고 `CONTENT_TYPES_POLICY_DEFERRED` 경고를 준다. W05가 범용 스키마 편집 정책을 발명하지 않는다.

`npm run validate -- <project>`는 같은 인덱스를 JSON으로 출력한다. 성공은 종료코드 0, 콘텐츠 검증 오류는 1, 사용법/프로젝트 열기 오류는 2다. 실행 전후 원본 해시가 같아야 하며 저장·마이그레이션·빌드·Git 작업을 섞지 않는다. 저장/복구는 W06, 공개/참조는 W07–W08, 분류 의미 검증은 W09-A, URL 충돌/순환은 W12에서 확장한다.

<a id="w08-content-crud-contract"></a>
### 3.7 W08 기본 콘텐츠 CRUD·참조 계약

`core/content`는 ID를 입력으로 `createContent`, `readContent`, `updateContent`, `inspectContentDeletion`, `deleteContent`, `restoreDeletedContent`를 제공한다. 생성 대상은 `text`, `story`, `blog`, `page` 네 상위 유형이며 초기 상태는 `draft`다. 경론 생성은 세 기본 영역을 함께 만들고, 이야기·블로그·페이지는 각 고정 본문 파일을 만든다. 경론 내부 구조/문서 변경과 slug/폴더 이동은 W09-B–W10 전에는 이 API 범위가 아니다.

수정은 ID·유형·slug·생성 시각·본문 매핑을 불변으로 두고 W06 SHA-256 리비전과 다중 파일 저장을 사용한다. 적용 직전 프로젝트와 참조를 다시 검사해 동시 삭제/외부 변경을 덮어쓰지 않는다. 생성·삭제·복원은 같은 프로젝트 쓰기 직렬화에 참여한다. 생성 ID는 현재 레코드/미디어뿐 아니라 삭제 보관 manifest의 대상/하위 ID와도 중복될 수 없다.

`validateContentReferences`는 경론의 `related_texts`, 내부 본문 문서의 `related_documents`, 이야기의 `featured_media_id`를 검사한다. 없는 대상이나 잘못된 유형은 오류이며, 공개 원본이 가리키는 비공개 선택 관계는 원본을 지우지 않고 공개 출력 제외 경고를 낸다. 분류 참조의 의미와 공개 차단은 W09-A에서 추가한다.

삭제는 메타데이터 리비전과 대상·경론 하위·외부 참조를 포함한 영향 리비전을 모두 요구한다. 외부 참조를 자동 제거하지 않으며 하나라도 남으면 차단한다. 성공 시 전체 콘텐츠 폴더를 `.borido/trash/{operation-id}/`와 manifest에 보관하고, 원래 경로가 비어 있을 때만 복원한다. 보관소 자동 정리·보존 기간은 아직 정하지 않는다.

<a id="storage"></a>
## 4. 저장·다중 파일 변경·복구·이행

W06에서 D23의 예약 `project/` 경계와 아래 저장 기능을 구현했다. `project/dist/`와 `project/.borido/` 복구/임시 자료는 `main` 커밋 대상에서 제외한다.

기본 저장은 명시 실행이다. 편집 시 받은 리비전과 현재 원본 내용 해시를 비교하고 다르면 덮어쓰기 없이 충돌을 반환한다. 타임스탬프만으로 외부 수정을 판단하지 않는다. 편집 버퍼는 실패/충돌 응답 후에도 유지하며 자동 병합하지 않는다.

단일 파일은 임시 쓰기 후 교체한다. 본문+JSON·이동·삭제·URL 이력처럼 여러 파일이 바뀌는 작업은 다음 절차를 따른다.

1. 대상/하위·참조·공개 URL·미디어 영향과 경로/ID/리비전 확인.
2. 변경 요약/위험을 표시하고 해당 작업에 필요한 사용자 확인.
3. 비공개 작업 위치에 변경 전 사본·계획/상태 기록. 앱의 변경 작업은 프로젝트별 직렬화.
4. 작은 단위로 변경하고 결과/불변 조건 검증.
5. 실패 시 이전 정상 상태 복원 또는 추가 작업을 막은 명확한 복구 대기 상태.

파일 시스템을 완전한 DB 트랜잭션으로 보장하지 않는다. 중간 종료/디스크 오류·복원 실패 후 재실행에서도 상태를 설명하고 복구할 수 있어야 한다. 삭제 자료는 복구 보관소에 두고 정리는 별도 명시 작업으로 한다. Git이 없어도 이 보호가 동작해야 한다. 자동 저장·주기적 미저장 입력 복구는 후속이며 브라우저 강제 종료 전 모든 입력을 복구한다고 보장하지 않는다.

W06 파일 Core는 `content/`, `media/`, `config/`의 일반 파일만 다룬다. 읽은 바이트의 SHA-256을 리비전으로 쓰며 새 파일은 기대 리비전 `null`을 요구한다. 다중 변경은 프로젝트별 직렬화하고 `.borido/recovery/{operation-id}/`에 변경 전 파일과 manifest를 준비한 뒤 각 대상의 리비전을 다시 확인한다. 실패하면 역순 복원하고, 중단/복원 실패 기록은 명시 복구 API로 조회·복구한다. 완료 작업을 되돌릴 때도 완료 후 리비전과 현재 파일이 같아야 하므로 후속 편집을 덮어쓰지 않는다.

복구는 본문·JSON·ID·참조·미디어 매핑·URL 이력·공개 상태를 함께 확인한다. 현재 사용자 변경이나 공개 주소와 충돌하면 무조건 덮어쓰지 않고 확인한다. 임시/복구 자료를 `dist/`나 공개 Git 결과에 포함하지 않는다.

마이그레이션은 별도 원본 변경 작업이다. 대상 버전/변경 목록 제시→백업→명시 실행→검증→실패 복구를 수행하며 실행/빌드/앱 업데이트 중 몰래 적용하지 않는다. 알 수 없는 스키마/필드는 [콘텐츠 명세](content-spec.md#settings)대로 원본 보존/쓰기·공개 빌드 차단/호환 안내를 한다. 기존 콘텐츠와 fixture의 호환성을 확인한다.

<a id="rendering"></a>
## 5. 본문 변환·템플릿·미리보기

Markdown은 파서 토큰을 이용해 제목/각주/내부 참조를 식별한다. Core가 ID→공개 URL/자산, 제목 앵커/목차·각주/왕복 링크를 생성하고 허용 요소/속성/프로토콜을 정화한다. 정규식만으로 Markdown 전체를 해석하지 않는다. 사용자 HTML·이벤트 속성·위험 링크가 검증 없이 통과하지 않도록 하며 정화 후 정상 앵커/서식도 유지되는지 검사한다.

Nunjucks 자동 이스케이프를 명시적으로 유지한다. 일반 문자열과 검증된 본문 HTML을 구분하고 검증된 결과만 안전 HTML로 전달한다. 템플릿은 콘텐츠 파일을 직접 탐색하지 않고 정리된 페이지 데이터를 받는다. 신뢰하는 프로젝트 템플릿만 실행하며 사용자 본문을 템플릿 정의로 실행하지 않는다. Nunjucks를 보안 샌드박스로 취급하지 않는다.

HTML 허용 목록·외부 URL/이미지·수동 앵커 문법/자동 정규화·내부 스킴 처리 순서 등은 R02에서 구체 사례와 정한다. 서버/빌드가 같은 정책을 쓰고 브라우저 미리보기만 정화하는 구조를 만들지 않는다. 각주 원본은 변경하지 않는다.

선택 미리보기는 미저장 버퍼를 메모리 모델로 변환하고 공개와 동일한 규칙/템플릿/CSS를 사용한다. draft/private는 로컬에서만 확인하고 저장/공개 전환을 하지 않는다. 임시 파일이 필요하면 비공개 작업 위치에 둔다. 마지막 성공 빌드의 사이트 미리보기와 구별하며 접두사/도메인 차이를 처리한다. 미리보기 후 공개 출력에 비공개 파일/캐시가 남지 않아야 한다.

## 6. 검증 오류와 경고

전체 원본의 기본 무결성과 실효 공개 대상의 변환 완전성을 구분한다. 아래 표가 심각도의 기준이며 UI/CLI는 같은 진단을 사용한다.

|분류|수준/효과|
|---|---|
|원본 JSON 문법·필수 필드/상태·유형/스키마 버전 오류, 미지원 필드, ID 중복/형식, 경로 탈출/파일 구조 오류|비공개여도 오류. 빌드/해당 쓰기 차단|
|잘못된 비어 있지 않은 분류 ID·없는 구조 부모/잘못된 소속, 본문 매핑 파일 누락|기본 무결성 오류|
|공개 경론의 미지정/미검증 분류·소속 근거, 공개 블로그 게시일 누락/미래|공개 검증 오류|
|최종 URL/파일 충돌·예약 경로 침범·이력 충돌/순환|오류|
|공개 본문의 없는/비공개 문서·앵커·미디어, 미정의/중복/중첩 각주|공개 변환 오류|
|초안/비공개 전용 정보·자산이 공개 출력에 유입|오류. 배포도 차단|
|조상 때문에 제외된 공개 자식, 미검증/미지정 초안 분류·서지, 비공개 본문의 작업 중 링크/각주 문제|경고, 이유/위치 표시|
|미사용 각주/미디어·미등록 파일·선택 서지 누락·동률 order·중복 H1|경고, 자동 수정/삭제하지 않음|
|선택 관련 관계의 공개 불가능한 대상, 비공개/삭제 대상의 과거 URL 이력|경고. 해당 링크/리디렉션 출력하지 않음|

오류는 임의 ID 변경·참조 삭제·콘텐츠 누락으로 숨기지 않는다. 사용자 진단은 성공/오류/경고, 프로젝트 상대 위치·ID·문제 항목·가능한 조치를 제공한다. 상세 보고서/원본 경로/manifest는 로컬 관리 자료이며 공개 산출물에 섞지 않는다.

W07의 공개 판정은 W05 인덱스 레코드와 필수 공개 blocker, 읽은 개요 텍스트를 입력으로 받는다. `published` 자기와 모든 콘텐츠 조상, blocker 부재를 `effective_published`로 계산하고, `text_area`/`tree_node`는 공백 아닌 개요나 최종 포함 자손이 있을 때만 `included`다. 경론 개요와 상위 유형/본문은 조건을 통과하면 직접 포함한다. 초안/비공개·조상 사유, 빈 구조, 없는 부모/순환과 blocker를 안정 이유 코드로 반환하며 파일/상태를 수정하지 않는다.

## 7. 정적 빌드와 결과 반영

편집기와 독립된 CLI로도 빌드한다. 절차는 설정/원본/미디어 인덱싱→전체 기본 검증→실효 공개 선별→분류/트리→Markdown/각주/참조/자산→페이지 데이터→템플릿/공통 자산→검색/사이트맵/리디렉션→전체 출력 재검증→성공 시 최종 반영이다.

앱 변경과 충돌하지 않도록 입력 스냅샷을 확보하고 원본·설정·템플릿·사용 자산을 해시로 식별한다. 입력과 출력 manifest를 로컬 비공개 위치에 기록해 어떤 결과를 확인/승인했는지 구분한다. 공개 결과에 불필요한 비공개 원본 인덱스나 상세 로그를 넣지 않는다.

임시 디렉터리에 완전한 결과를 만들고 검증 후에만 `dist/`로 반영한다. 반영 직전 원본/설정/템플릿 등 입력이 바뀌었으면 오래된 결과를 정상 최신 빌드로 승인하지 않는다. 교체 중 실패는 이전 정상 결과를 복원/보존해야 한다. 세부 스냅샷/교체 절차와 지원 파일 시스템 검증은 W15/R02에서 다룬다.

기존 `dist/`를 먼저 비우거나 실패 결과로 덮어쓰지 않는다. 성공 재빌드는 과거 공개 해제/삭제된 HTML·자산·인덱스·리디렉션을 남기지 않는다. 빌드·미리보기는 원본의 본문/JSON/수정 시각/URL 이력을 쓰지 않는다. 전후 원본 해시와 공개 결과 전체의 비공개 표식/경로·미디어를 확인한다.

## 8. GitHub 인증과 명시 배포

### 8.1 인증과 저장소 역할

Git 설치→gh 설치→인증 상태→필요 시 브라우저 인증 안내→상태 재확인→원격 접근→쓰기 권한→Pages/브랜치 설정을 분리한다. 앱은 GitHub 비밀번호/PAT를 직접 받지 않고 토큰을 UI/일반 설정/원본/로그에 기록하지 않는다. CLI의 비밀 포함 가능 출력은 그대로 노출하지 않는다.

gh/Git의 실제 자격 증명 관리 환경을 사용하며 모든 OS에서 반드시 키체인만 사용한다고 보장하지 않는다. SSH는 기존 Git 환경에서 가능하지만 기본 안내는 gh로 통일한다. 미설치면 설치 방법을 안내하고 동의 없이 외부 프로그램을 설치하지 않는다. 저장소 생성/Pages 설정 자동화를 필수로 넣지 않는다.

`biwoom/borido`의 `main`은 프로그램·문서와 `project/` 원본을 함께 저장한다. 일반 저장은 Git 작업을 하지 않지만 배포 버튼의 최종 확인은 허용된 `project/content`, `project/media`, `project/config` 변경만 커밋·fast-forward 푸시할 수 있다. 프로그램·문서·기타 사용자 변경은 자동 스테이징하지 않는다. 저장소가 public이므로 `draft`·`private` 원본도 Git에서 공개되며 이 상태는 사이트 미게시 필터일 뿐 비밀 보호가 아니다.

### 8.2 배포 방식과 승인 결과

배포는 GitHub Actions의 Pages artifact 방식을 채택한다. `main`만 관리하며 `gh-pages` 브랜치를 생성·체크아웃·푸시하지 않는다. `project/dist/`는 `main`에서 추적하지 않고 `docs/`는 개발 문서용으로 유지한다. workflow는 승인한 정확한 `main` 커밋을 체크아웃해 검증·빌드·비공개 유입 검사를 다시 실행하고, 통과한 정적 결과만 Pages artifact로 업로드/배포한다.

앱은 원본 체크아웃의 브랜치를 바꾸지 않는다. 배포 확인 화면은 원본 변경과 공개 결과를 나눠 보여주고, 승인 시 허용 경로만 스테이징한다. 원격 `main`이 앞서거나 충돌하면 중단하고 자동 merge/rebase·강제 푸시·확인 없는 이력 재작성을 금지한다. 커밋/푸시 성공 후 해당 커밋 SHA로 수동 workflow를 요청하며, 일반 코드/문서 변경이 섞였거나 로컬 빌드 코드와 원격 커밋이 다르면 별도 검토를 요구한다.

배포 전에는 다음을 모두 만족해야 한다.

1. 빌드 성공·공개 파일/경로·비공개 유입 검사 통과.
2. 입력 리비전/설정·출력 manifest/파일 해시로 검증된 결과 식별.
3. `main`에 커밋할 허용 원본 파일과 제외된 프로그램/문서 변경 확인.
4. 저장소·정확한 커밋 후보·Pages 공개 범위와 결과에 대한 사용자 승인.
5. 승인 후 입력/출력/원격 `main`이 바뀌지 않았음을 확인하고 fast-forward 푸시.
6. 푸시된 정확한 커밋으로 workflow를 실행하고 동일 조건의 재검증 통과.

인증 성공은 배포 승인이 아니다. 일반 저장·`main` 푸시만으로 Pages를 자동 배포하지 않고 사용자의 명시적 배포 확인으로 workflow를 실행한다. workflow 실패는 새 artifact를 공개하지 않고 이전 정상 Pages를 유지해야 하며, 원본 커밋 성공과 공개 실패를 별도 상태로 알린다. 실제 게시 상태·직접 URL/자산/404·`/borido/` 접두사·사용자 지정 도메인은 승인된 대상에서 별도로 확인한다.

실패 단계·대상·가능 원인·조치를 보여주며 원본 커밋/푸시, 인증/권한, workflow 요청, Actions 검증/빌드, Pages 배포 오류를 구분한다. 실패가 원본이나 이전 정상 빌드/Pages를 손상시키지 않아야 한다. 이미 공개된 `main` 이력의 삭제는 일반 배포/공개 해제에 포함하지 않는다.

참고: [GitHub Pages 게시 원본](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site). 실제 설정을 변경하거나 게시한 것은 아니다.

## 9. 명령·테스트·개발 완료

제품 스크립트 `dev`는 W03–W04 서버/UI, `validate`는 W05 읽기 전용 콘텐츠 검증에 연결했다. `build`는 W15 전까지 제공하지 않는다. `check`, `test`, `test:e2e`는 환경·단위/통합·W04 Chromium 흐름을 검사한다. 배포/복구/이행은 별도 작업이며 `build`에 섞지 않는다. 성공하는 빈 대체 명령을 만들지 않는다.

- 단위/통합: Core/주소/상태/각주·실제 임시 파일 왕복·빌드 실패 보존. GitHub/외부 API 없이 실행.
- 브라우저: 최초 실행·편집/저장·트리/독서·반응형·해시/브라우저 이력·JS 비활성·초점/키보드·인증 오류 안내.
- 보안: 경로/심볼릭 링크·요청 출처/Host/토큰·HTML/URL·자격 증명/명령 인자·비공개 출력.
- 수동: 실제 경론/출처·가독성·OS 설치/인증·실제 Safari/모바일·승인 Pages 게시/복구.

운영 원본과 fixture를 섞지 않는다. 실제 경론도 격리된 복제/자료로 검증한다. 기본 테스트에 실제 원격 게시를 넣지 않으며 로컬 bare 원격과 프로세스 대역을 사용한다. 최초 패키지/브라우저 설치와 이후 오프라인 테스트 가능성을 구별한다.

성능은 실제 경론과 장문/큰 트리의 규모·환경·반복 결과를 측정해 예산을 확정한다(R06). 기능이 살아 있는지만으로 성능 통과를 대신하지 않으며, 근거 없는 커버리지/시간 수치를 도입하지 않는다. 테스트 실패/미실행·남은 검증은 명시하고 주요 변경은 관련 검증을 통과한 상태로 검토/병합한다.

작업 순서·필수 사례·완료 증거는 [개발 계획](development-plan.md)에 둔다. 현재 문서의 존재는 앱 설치/보안/성능/배포 검증의 통과 증거가 아니다.
