# 보리도 콘텐츠·파일 명세

- 통합 개정 1.0 · 2026-10-29 · 현재 개발 기준
- 담당: 원본 형식·모델·공개·식별/주소·본문/미디어·검색 데이터.
- 결정 근거: D04–D05·D07–D12·D15·D19–D20. 실제 JSON Schema 파일과 fixture 작성/호환 검증은 W05 이후에 수행한다.

## 1. 원본과 사용자 프로젝트

원본은 UTF-8 Markdown·JSON·바이너리 미디어다. 줄바꿈·문단·내용은 보존하고 편집기/빌드는 원본 Markdown을 HTML로 치환하지 않는다. 프로그램 설치 경로와 사용자 프로젝트 루트는 분리한다. 경로 보안과 작업 파일은 [기술 명세](technical-spec.md#architecture)를 따른다.

```text
user-project/
├── content/
│   ├── texts/
│   ├── stories/
│   ├── blog/
│   └── pages/
├── media/
│   ├── assets.json
│   ├── images/
│   ├── documents/
│   └── icons/
├── config/
│   ├── site.json
│   ├── content-types.json
│   ├── canons/taisho.json
│   └── url-history.json
└── dist/                     # 공개 결과물, 원본 아님
```

위는 앞으로 생성할 구조이며 이번 문서 작업에서 운영 프로젝트를 생성한 것이 아니다. 복구/미리보기/임시 빌드 자료는 공개 `dist/`와 구분된 비공개 작업 위치에 둔다. 그 정확한 이름·보존 용량은 R02에서 정한다.

폴더/파일명은 기본적으로 소문자 영문·숫자·하이픈을 사용한다. 제목의 한글·한자·음역은 그대로 보존한다. `meta.json`, `_node.json`, `_index.md`, 문서의 `body.md`는 역할이 예약되어 일반 문서 이름으로 중복 사용하지 않는다. 구조 폴더는 `_node.json`으로 존재를 표현하므로 빈 디렉터리 자체에 의존하지 않는다.

## 2. 레코드와 트리 모델

상위 콘텐츠 유형은 `text`, `story`, `blog`, `page`의 네 가지다. 경론 내부 레코드 `text_area`, `tree_node`, `text_document`를 명시적으로 구분한다. 미디어와 분류는 별도 모델이다.

|레코드|저장|본문 매핑 `body_file`|자식과 관계|
|---|---|---|---|
|경론 `text`|경론 폴더의 `meta.json`|선택 `_index.md`|세 자료 영역 소유|
|영역 `text_area`|영역 폴더의 `_node.json`|선택 `_index.md`|`area`는 `translation`/`original`/`research`, 구조/본문 자식|
|구조 `tree_node`|구조 폴더의 `_node.json`|선택 `_index.md`|`node_kind`로 의미 표시, 구조/본문 자식|
|본문 `text_document`|문서 폴더의 `_node.json`|필수 `body.md`|자식 없음|
|이야기 `story`|콘텐츠 폴더의 `meta.json`|필수 `story.md`|트리 자식 없음|
|블로그 `blog`|콘텐츠 폴더의 `meta.json`|필수 `post.md`|연도 폴더는 보관 위치이며 상위 콘텐츠 아님|
|페이지 `page`|콘텐츠 폴더의 `meta.json`|필수 `page.md`|트리 자식 없음|

`body_file`은 위 파일명만 허용하는 레코드 내 본문 매핑이다. 개요가 없으면 필드를 생략한다. 필드가 있는데 파일이 없거나, 허용하지 않은 본문/경로를 가리키면 오류다. 개요 파일은 별도 콘텐츠 ID·상태·URL을 가지지 않고 소유 레코드의 표시/공개 조건을 따른다. 별도 상태가 필요한 내용은 본문 문서로 만든다.

부모·소속 경론·영역은 폴더 포함 관계에서 해석한다. 원본에 `parent_id`나 자식 목록을 중복 저장하지 않는다. Core의 읽기 결과에는 해석된 부모 ID·경론 ID·영역을 제공한다. 영역의 코드와 폴더명이 맞아야 하며, 본문 노드에 자식을 두거나 영역을 중첩하지 않는다. 폴더 밖/없는 부모·잘못된 소속을 오류로 보고한다.

`node_kind`는 `volume`, `chapter`, `section`, `topic`, `group`, `custom` 중 의미를 고르며 깊이를 결정하지 않는다. 번역·원문·연구를 강제로 같은 구조로 맞추지 않는다. 각 경론에는 서로 다른 ID를 가진 세 영역 레코드를 두고 아직 작성하지 않은 영역은 초안으로 보관할 수 있다.

```text
content/texts/sample-text/
├── meta.json
├── _index.md                 # 경론 개요, 선택
├── translation/
│   ├── _node.json             # type: text_area
│   └── volume-one/
│       ├── _node.json         # type: tree_node
│       ├── _index.md         # 구조 개요, 선택
│       └── first-document/
│           ├── _node.json     # type: text_document
│           └── body.md
├── original/
│   └── _node.json
└── research/
    └── _node.json
```

이 폴더명은 합성 예시이며 실제 경론/분류 자료가 아니다.

## 3. 공통 메타데이터와 ID

아래 공통 필드는 §2의 콘텐츠/내부 레코드에 적용한다. 미디어·분류·설정 파일은 별도 표를 따른다.

|필드|형식/필수|규칙|
|---|---|---|
|`schema_version`|정수, 필수|최초 형식 버전 1. 앱/문서 버전과 구분|
|`id`|UUID v4, 필수|생성 시 한 번 부여, 일반 수정/이동/이름 변경 시 불변|
|`type`|§2 유형 코드, 필수|파일 역할과 일치|
|`title`|비어 있지 않은 문자열, 필수|화면 제목. 파일명/slug/ID와 독립|
|`slug`|문자열, 필수|[URL 규칙](#urls)에 따른 공개 식별자. 영역은 고정 영역 코드|
|`status`|상태 코드, 필수|`draft`, `published`, `private`. 생성 기본 `draft`|
|`created_at` / `updated_at`|UTC ISO 8601 문자열, 필수|`Z`를 사용. 실제 내용/메타데이터 변경 시 수정 시각 갱신|
|`description`|문자열, 선택|요약/소개|
|`order`|정수|영역/트리 형제에서는 필수, 다른 유형에서는 필요 시 사용|
|`body_file`|허용 파일명|§2의 필수/선택 매핑|

ID는 프로젝트 내 UUID 레코드 전체에서 중복되면 오류다. 분류는 별도 안정 문자열 ID로 식별하고 소속 대장경과 함께 검증한다. 중복을 자동 수정하지 않으며 이동/가져오기/복구에도 같은 검증을 수행한다. 삭제한 ID를 무관한 새 자료에 재사용하지 않는다.

형제 트리는 `order` 오름차순, 동률은 ID의 안정적 순서로 정렬하고 경고한다. 파일명·생성 시각을 기본 트리 순서로 사용하지 않는다. 순서 변경은 명시적인 편집 작업이다. 구조/문서의 시각적인 구분은 [읽기 화면](ui-spec.md#reader)을 따른다.

JSON 예시는 합성 자료의 본문 레코드다. 원본 계층과 유효한 사이트 설정을 함께 가진 완성 fixture는 아직 아니다.

```json
{
  "schema_version": 1,
  "id": "10000000-0000-4000-8000-000000000004",
  "type": "text_document",
  "title": "검증용 첫 문서",
  "slug": "first-document",
  "status": "draft",
  "created_at": "2026-10-29T00:00:00Z",
  "updated_at": "2026-10-29T00:00:00Z",
  "order": 10,
  "body_file": "body.md",
  "related_documents": []
}
```

## 4. 유형별 필드

### 4.1 경론과 서지

`text`는 `canon` 객체를 가지며 대장경/대표 분류에 연결한다. 문헌 번호·소속은 추측하지 않는다. 작성 중 미검증/누락 정보는 보존할 수 있으나 공개 적합성은 [분류 검증](#taxonomy)을 만족해야 한다.

|필드|형식/의미|
|---|---|
|`canon.canon_id`|체계 ID. 초기 지원 `taisho`|
|`canon.section_id`|대표 분류 ID. 작성 중 미지정은 `null`, 공개 전 유효 참조 필요|
|`canon.catalog_number`|확인된 문헌 번호 문자열 또는 `null`|
|`canon.verification_status`|`unverified` 또는 `verified`|
|`canon.source_references`|근거 자료 목록(§5)|
|`authors` / `translators` / `source_languages`|선택 문자열 배열. 표시명/언어 정보|
|`edition`|선택 객체. `name`과 선택 `source_url`|
|`bibliography`|선택 배열. 항목은 `citation`과 선택 `url`|
|`related_texts`|선택 경론 UUID 배열|

`text_area`에는 `area`, `tree_node`에는 `node_kind`를 추가한다. `text_document`의 선택 `related_documents`는 대응 자료 문서 UUID 배열이다. 없는 관련 대상은 진단하며, 공개할 수 없는 선택 관계는 출력하지 않는다. UI는 같은 경론의 목표 영역에 유효한 대응이 있을 때 사용하고, 다른 계층의 같은 위치를 대응으로 추정하지 않는다.

### 4.2 이야기·블로그·일반 페이지

|유형|필드|형식/규칙|
|---|---|---|
|이야기|`sources`, `source_text`|선택 출처 목록(§5), 원전 서지 문구|
|이야기|`adapted`, `adaptation_note`|선택 boolean과 각색 설명|
|이야기|`featured_media_id`|선택 미디어 UUID. 미디어 참조 검증 대상|
|블로그|`author`, `tags`|선택 표시명, 문자열 배열|
|블로그|`published_at`|공개 전환 전 필수 UTC ISO 시각. 작성/수정 시각과 구분|
|페이지|`menu_visible`, `menu_order`|메뉴 노출 boolean·정수. 미지정이면 메뉴 미노출|
|페이지|`template`|선택 허용 템플릿 이름. 실제 파일 경로를 받지 않음|

블로그는 게시일 역순, 동률 ID 순으로 정렬한다. 공개 상태인데 게시일이 없거나 빌드 기준 시각보다 미래이면 오류다. 초안에는 계획 날짜를 둘 수 있으나 시간이 지나도 자동 공개하지 않는다. 날짜를 파일명/생성 시각으로 추정하지 않는다. 시각은 사이트 시간대로 표시한다.

선택 대표 이미지·서지·각색·관련 문서가 없어도 화면은 자연스럽게 유지한다. 메뉴 표시와 템플릿 선택은 [공개 조건](#visibility)을 바꾸지 않는다. 추가 필드/새 템플릿은 명시적 스키마·코드 변경과 호환 검증 대상이다.

## 5. 분류·출처 검증

`config/canons/taisho.json`은 `schema_version`, `canon_id`, 표시 `name`, `sections` 배열을 가진다. 분류 항목은 `id`, `canon_id`, `name`, `slug`, `order`, 선택 `description`, `verification_status`, `source_references`를 가진다. 분류 ID는 안정적으로 유지하고 화면 코드에 목록을 하드코딩하지 않는다.

출처 항목은 `title`(자료명), 선택 `url`, `locator`(권/쪽/목록 위치), `checked_at`(확인 시각)을 표현한다. 검증된 분류/경론 서지에는 실제 대조 근거를 남긴다. 검증 전 자료는 `unverified`로 표시하고 공식 공개 목록에 자동 포함하지 않는다.

원 목차와 [SAT](https://21dzk.l.u-tokyo.ac.jp/SAT/)·[CBETA](https://cbeta.org/) 자료를 대조하되 각 자료의 분류 관례와 한국어 표시명 차이를 기록한다. 사이트 주소를 아는 것만으로 전체 분류/소속/번호가 검증된 것은 아니다. 사용할 경론 한 편과 필요한 분류부터 확인하고, 실제 본문은 출처/사용 범위가 확인된 격리 자료를 사용한다(R03).

초기 공개 탐색은 대표 분류 하나를 사용한다. 추가 대장경·주제 분류/인물 그래프·자동 분류는 초기 범위에 넣지 않는다. 존재하지 않는 비어 있지 않은 분류 참조는 오류다. 미지정/미검증 초안은 공개하지 않으며, 공개 경론이 유효/검증된 대표 분류와 소속 근거를 충족하지 못하면 공개 빌드를 차단한다.

## 6. 공개 조건의 단일 기준

콘텐츠 레코드의 실효 공개 조건은 **자기 상태와 콘텐츠 조상 모두가 `published`이며 필수 공개 검증을 통과한 것**이다. 사용자 프로젝트/보관용 연도 폴더는 상태를 가진 조상이 아니다. `draft`·`private`는 공개하지 않으며 누락/유효하지 않은 상태는 비공개 취급과 동시에 스키마 오류다.

|자기 상태|모든 콘텐츠 조상|결과|
|---|---|---|
|`published`|모두 `published` 또는 조상 없음|공개 후보, 분류/참조 등 공개 검증 필요|
|`published`|하나라도 `draft`/`private`|공개 제외, 편집기와 검증 보고서에 이유 경고|
|`draft`/`private`|어떤 상태든|공개 제외, 조상/자식 상태를 자동 변경하지 않음|
|누락/유효하지 않음|어떤 상태든|공개 제외, 필수 스키마 오류로 빌드 차단|

개요는 소유 레코드의 상태를 따른다. 실효 공개인 구조 노드가 개요 또는 실효 공개 자손을 가지면 공개 트리에 표시한다. 둘 다 없으면 숨긴다. 자식을 위로 끌어올리거나 조상을 자동 공개하지 않는다. 자료 영역의 공개 자료가 없으면 공개 자료 전환 진입점을 만들지 않는다. 공개 경론 자체의 개요/서지 페이지는 유지할 수 있다.

공백만 있는 개요 파일은 표시할 개요가 없는 것으로 판정한다. 파일/메타데이터를 자동 삭제하지 않으며, 자손도 없는 구조에 빈 소개 프레임을 만들지 않는다.

같은 판정을 HTML·목록·트리·breadcrumbs·검색·사이트맵·관련 문서·리디렉션·미디어 선별에 적용한다. 비공개 제목·경로·본문·ID 관계/전용 자산을 생성된 JS/JSON을 포함한 공개 파일에 남기지 않는다. 공개 해제 후 재빌드에서는 과거 공개 출력도 제거한다. 기존 원격 Git 이력을 지우는 작업까지 포함하지는 않는다.

## 7. 공개 URL과 변경 이력

|페이지|사이트 내부 경로|
|---|---|
|홈|`/`|
|경론 분류 진입|`/texts/`|
|분류별 목록|`/texts/categories/{section-slug}/`|
|경론 개요|`/texts/{text-slug}/`|
|영역 개요/목록|`/texts/{text-slug}/{area}/`|
|본문 문서|`/texts/{text-slug}/{area}/{document-slug}/`|
|구조 노드 개요/자식 탐색|`/texts/{text-slug}/{area}/nodes/{node-slug}/`|
|이야기 목록/본문|`/stories/`, `/stories/{story-slug}/`|
|블로그 목록/본문|`/blog/`, `/blog/{post-slug}/`|
|일반 페이지|`/pages/{page-slug}/`|
|검색|`/search/`|
|없는 URL 대응|정적 호스팅용 `404.html`|

경로는 폴더명이 아니라 레코드의 slug/소속에서 생성한다. 제목 변경은 slug 변경이 아니다. 같은 경론·영역 안의 부모/폴더 이동은 문서·구조 URL을 바꾸지 않는다. 다른 경론/영역 이동, 경론 slug 변경, 명시적 URL 변경은 영향받는 공개 주소 전체와 이력을 계산하는 별도 편집 작업이다.

slug 기본 계약은 소문자 영문·숫자·하이픈, 빈 값/경로 구분자/`.`·`..`/인코딩된 우회 경로를 허용하지 않는 것이다. 한글 제목을 자동 음역하지 않는다. 자동 생성 slug도 충돌 검증과 사용자 편집을 거친다. 대소문자/정규화 차이를 충돌 우회로 쓰지 않는다.

- 경론 slug는 프로젝트의 경론 사이에서 고유하며 `categories`는 예약한다.
- 문서 slug는 한 경론·영역의 모든 본문 문서 사이에서 고유하며 `nodes`는 예약한다. 구조 node slug도 같은 영역의 구조 노드 사이에서 고유하다.
- 이야기/블로그/페이지 slug는 각 유형 안에서 고유하다. 분류 slug는 체계 내에서 고유하다.
- `/texts/`, `/stories/`, `/blog/`, `/pages/`, `/search/`, `/assets/`, `404.html`, `sitemap.xml` 등 시스템 출력 경로를 콘텐츠가 덮어쓰지 못한다.
- 전체 최종 경로/출력 파일 충돌은 마지막에 다시 검사한다. 중복을 자동 덮어쓰기나 공개 URL의 조용한 접미사 변경으로 해결하지 않는다.

구조 노드가 개요 없이 공개 자손만 가져도 그 경로에는 자식 탐색 페이지를 생성할 수 있다. 그 페이지를 독립된 본문 문서로 취급하지 않는다. 모든 공개 페이지는 실제 링크·새로고침·직접 입력·브라우저 이력으로 접근한다.

### 7.1 URL 이력

`config/url-history.json`의 항목은 과거 내부 경로 `from`, 대상 UUID `target_id`, UTC `changed_at`을 기록한다. 새 주소는 대상 ID로 현재 해석하여 중복 저장하지 않는다. 명시적인 URL 변경/이동 작업이 쓰며 빌드는 읽기만 한다.

```json
{
  "schema_version": 1,
  "entries": [
    {
      "from": "/texts/sample-text/translation/old-document/",
      "target_id": "10000000-0000-4000-8000-000000000004",
      "changed_at": "2026-10-29T00:00:00Z"
    }
  ]
}
```

`from`에는 배포 접두사를 넣지 않는다. 중복 과거 경로·현재 경로와의 충돌·순환은 오류이며, 과거 경로를 다른 콘텐츠가 재사용하는 것은 초기 거절한다. 여러 번 변경해도 현재 공개 대상에 한 번에 연결한다. 비공개/삭제되어 현재 공개 대상이 없으면 경고하고 리디렉션을 출력하지 않는다. 대상 삭제 이력은 보존할 수 있으며 없는 필수 본문 참조와 구분한다.

위 합성 예시의 대상은 §3에서 `draft`이므로 이 상태 그대로 빌드하면 리디렉션을 출력하지 않는다. 형식 설명과 공개 가능한 완성 fixture를 구분한다.

정적 리디렉션 HTML에는 새 주소로 가는 실제 링크를 제공한다. HTTP 301/302를 지원하는 것처럼 표기하지 않는다. 접두사/도메인 변경은 기록된 내부 경로를 새 설정에 맞춰 렌더링한다.

## 8. Markdown·링크·앵커·각주

### 8.1 제목과 기본 표현

메타데이터 `title`을 페이지 제목으로 사용하고 본문은 기본 H2부터 작성한다. 기존 본문의 H1을 자동 삭제/치환하지 않으며 중복 제목을 경고한다. 제목/문단·목록·인용·표·이미지·링크·각주·코드 서식을 지원하고 한글·한자·팔리어/산스크리트어 문자를 보존한다.

제목 앵커는 한글/한자를 보존하는 정규화와 문서 내 중복 접미사로 일관되게 생성한다. 필요한 안정적 수동 앵커는 `## 제목 {#anchor-id}`의 제한된 제목 확장으로 지원하며 중복 수동 ID는 오류다. 정확한 자동 정규화/문자 처리 사례는 파서 계약/fixture에서 확정한다(R02). 목차·내부 해시·다른 문서 앵커는 동일한 결과를 사용한다.

### 8.2 내부 참조

```markdown
[관련 문서](doc:10000000-0000-4000-8000-000000000004#anchor-id)
![그림 설명](asset:20000000-0000-4000-8000-000000000001)
```

`doc:`와 `asset:`은 일반 Markdown 링크/이미지 구문 안에서 Core가 해석하는 내부 참조다. 공개 HTML에는 실제 URL로 변환하고 내부 스킴을 남기지 않는다. 파일 상대 경로를 ID 대신 영구 문서/자산 참조로 자동 고정하지 않는다. 외부 Markdown 도구에서는 이 내부 링크가 바로 작동하지 않을 수 있음을 안내한다.

실효 공개 본문의 없는 문서·비공개 대상·없는 앵커 참조는 오류다. 링크를 지워도 표시 문구에 비공개 제목이 남을 수 있으므로 사용자가 공개할 표현으로 수정한다. 선택 관련 문서/경론 관계는 공개 불가능한 대상을 표시하지 않고 경고하되 원본 관계를 자동 삭제하지 않는다. 모든 공개 참조 해석은 [공개 조건](#visibility)을 통과한 인덱스를 사용한다.

HTML·외부 URL 허용/정화는 [변환 보안](technical-spec.md#rendering)을 따른다. 본문을 정규식만으로 재해석하거나 Markdown 파서를 새로 작성하지 않는다.

### 8.3 각주 데이터

원본은 `[^id]` 참조와 정의를 같은 Markdown에 유지한다. 각주를 별도 원본 파일로 분리하지 않는다. 최초 참조 순서로 번호/목록을 생성하고 같은 각주의 반복 참조에는 고유 참조 앵커/왕복 링크를 부여한다. 여러 문단·목록·표·이미지·내부/외부 링크를 지원하고 긴 내용을 잘라내지 않는다.

초기에는 중첩 각주와 인라인 각주 확장을 지원하지 않는다. 실효 공개 본문의 미정의/중복 정의·지원하지 않는 중첩은 오류, 미사용 정의는 경고다. 정적 HTML에는 하단 각주와 실제 앵커를 제공한다. JS의 패널 전환·같은 DOM 활용·직접 각주 해시 예외와 인쇄는 [화면 명세](ui-spec.md#notes)를 따른다.

<a id="media"></a>
## 9. 미디어 자산

`media/assets.json`은 `schema_version`과 `assets` 배열을 가진다. 자산 항목은 필수 UUID `id`, 프로젝트 상대 `file_path`, `media_type`, `status`와 선택 `alt`, `caption`, 가져오기 시각 정보를 가진다. 미디어는 §3의 콘텐츠 공통 필드 전체를 요구하는 모델이 아니다.

상태는 기본 `private`, 명시적으로 `published`로 바꾼 것만 공개 가능하다. 파일 크기/사용 목록처럼 파일/참조에서 계산 가능한 값은 원본에 중복 누적하지 않는다. 미디어 파일 경로는 허용한 `media/` 하위여야 하며 중복 ID·파일 매핑·허용 루트 탈출을 검사한다.

공개 본문·각주·대표 이미지·사이트 공통 설정에서 실제로 참조하는 공개 자산의 집합만 출력한다. 공개 문서가 비공개/없는 자산을 참조하면 오류다. 로고/공통 아이콘은 명시적인 공통 자산 참조로 포함한다. 앱이 제공하는 신뢰된 UI 아이콘과 사용자 미디어는 출처를 구분한다. `media/` 전체나 인덱스 원문을 자동 복사하지 않는다.

초기는 일반 래스터 이미지와 PDF 중심으로 지원하고 정확한 형식/MIME·크기 상한을 R02에서 정한다. 사용자 업로드 SVG는 검증 전 제외한다. 미등록/미사용 파일은 표시하되 자동 삭제하지 않는다. 이동/이름 변경은 자산 ID를 유지하고 인덱스 경로만 명시적으로 갱신한다. 삭제 전 비공개 문서까지 포함한 사용 관계를 검사하며 복구는 [저장/복구](technical-spec.md#storage)를 따른다.

## 10. 사이트 설정과 스키마

`config/site.json`은 스키마 버전, 사이트명/설명·기본 언어·작성자 표시명·라이선스·시간대·공개 URL 구성·선택 공통 자산·배포 설정을 관리한다. UI에서 전체 공개 URL을 입력받되 저장/생성은 origin과 접두사를 구분한다.

W02의 최초 코드 계약은 다음 필드를 사용한다. 모두 필수이며 아직 연결하지 않은 저장소/공개 URL은 `null`로 명시한다. UI 입력 이름 `public_url`은 저장 필드가 아니며 `base_url`과 `base_path`로 나눈다.

|필드|형식|
|---|---|
|`schema_version`|정수 `1`|
|`site_name`|비어 있지 않은 문자열|
|`description`|문자열|
|`default_language`|유효한 BCP 47 언어 태그|
|`author_name` / `license`|문자열, 값이 없으면 빈 문자열|
|`timezone`|유효한 IANA 시간대|
|`base_url`|HTTP(S) origin 또는 `null`|
|`base_path`|정규화한 `/` 시작/끝 접두사|
|`source_repository`|원본 저장소 객체 또는 `null`|
|`deployment`|배포 저장소 객체 또는 `null`|

`source_repository`는 `repository_url`, `branch`, `public_links` boolean을 가진다. `deployment`는 별개의 `repository_url`, `branch`를 가진다. W02는 이 값을 저장/구분할 뿐 원격 접근·브랜치/Pages 유효성을 보장하지 않으며 프로그램 저장소에서 기본값을 채우지 않는다. 그 검증은 W28–W31/R05에 속한다.

|항목|계약|
|---|---|
|`base_url`|공개 origin. 예: `https://example.github.io`. 저장소 주소나 접두사를 섞지 않음|
|`base_path`|`/` 또는 `/borido/`처럼 정규화한 사이트 접두사. 내부 경로에 한 번만 합성|
|`timezone`|시각 표시용 사이트 시간대. 저장 시각은 UTC|
|`deployment`|선택 저장소 URL·브랜치. 실제 게시 위치는 명시 설정하며 생성물 루트 배포|
|원본 연결 설정|원본 저장소/브랜치와 원본 링크 공개 허용을 별도 확인. 프로그램 저장소에서 추측 금지|

GitHub 비밀번호/PAT/세션 토큰을 일반 설정에 넣지 않는다. 사용자 지정 도메인 설정·실제 Pages URL·원격 브랜치는 별도 확인 대상이다(R05).

지원하지 않는 최상위 필드는 읽을 때 보존하고 진단하되 편집 저장을 막는다. 지원하지 않는 스키마 버전과 비밀로 보이는 필드는 오류다. 설정 저장은 읽은 원문의 SHA-256 리비전이 현재 파일과 일치할 때만 같은 폴더의 임시 파일을 거쳐 교체한다. 이 W02 단일 설정 보호는 W06의 전체 저장/복구 계약으로 확장한다.

JSON Schema의 기준은 앱 코드 한 곳이다. `content-types.json`은 지원된 필드의 표시·허용된 기본값 등 편집 정책만 다룬다. 필수 필드·공개 검증·유형 코드를 일반 설정으로 약화/확장하지 못한다. 미지원 필드/버전은 원본을 그대로 보존하고 편집 저장·공개 빌드를 차단해 지원 정보를 안내한다. 자동 필드 삭제·형식 추측·무제한 사용자 필드 편집기를 만들지 않는다.

스키마 변경은 [명시적 마이그레이션](technical-spec.md#storage)과 기존 콘텐츠/fixture 호환 검증을 거친다. 실행/빌드가 몰래 형식을 바꾸지 않는다.

<a id="search"></a>
## 11. 검색·사이트맵 데이터

검색 인덱스는 실효 공개 문서의 제목·유형·최종 URL·경론/영역 맥락·설명·본문 평문을 가진 정적 JSON으로 생성한다. 본문 문서는 결과 한 건, 경론/영역/구조 개요는 실제 개요가 있을 때만 별도 결과를 만든다. 순수 구조 폴더는 중복 본문 결과를 만들지 않는다.

초기 검색은 일관된 문자열 정규화 후 포함 검색, 제목 일치 우선·나머지 안정 정렬을 사용한다. 형태소/퍼지/외부 검색 서버는 제외한다. 정확한 공백·대소문자·Unicode·여러 검색어·동률 기대값과 JSON 키는 R02의 fixture/계약에서 확정한다. 인덱스 분할은 실측 전 미리 도입하지 않는다.

사이트맵은 고유한 현재 공개 페이지를 포함한다. 검색 결과 페이지·리디렉션·비공개 URL은 제외한다. 공통 공개 페이지/콘텐츠 페이지와 자산을 구분하며 미디어를 페이지로 올리지 않는다. 재빌드에서 공개 해제된 문서·자산·검색/사이트맵/이전 리디렉션이 남지 않아야 한다.

## 12. 변경과 검증의 연결

생성·편집·이동·삭제는 ID/경로/공개 주소/관련 참조/하위/미디어 영향을 확인하는 별도 작업이다. URL 변경 기록과 파일 변경은 같은 복구 가능한 작업 범위로 다룬다. 복구는 본문뿐 아니라 메타데이터·참조·URL 이력·공개 상태를 함께 검증한다.

오류/경고 수준의 단일 표는 [기술 명세](technical-spec.md#validation)에 있으며 데이터 규칙을 약화시키지 않는다. 구현/검증은 W05–W16·W23–W27·W33으로 연결한다. 전체 원본 JSON/식별자/경로 무결성, 공개 변환 완전성, 비공개 표식/원본 해시의 실제 테스트가 통과해야 한다.
