## 1. 프로젝트 목적

보리도(Borido)는 불교 경론, 이야기, 블로그, 일반 페이지 등의 콘텐츠를 작성하고 정리하여 정적 웹사이트로 배포하기 위한 로컬 중심 콘텐츠 시스템이다.

로컬 편집기는 사용자가 자신의 컴퓨터에서 콘텐츠를 작성·수정하고, 결과를 미리 확인한 뒤, 정적 사이트를 생성하여 GitHub Pages 등의 정적 호스팅 환경에 배포할 수 있도록 한다.

### 1.1 핵심 원칙

1. **로컬 우선**: 콘텐츠 원본과 편집 작업은 사용자 컴퓨터에서 이루어진다.
    
2. **파일 중심**: 데이터베이스 서버 없이 일반 파일과 디렉터리로 콘텐츠를 관리한다.
    
3. **정적 배포**: 공개 사이트는 HTML, CSS, JavaScript 및 필요한 미디어 파일로 생성한다.
    
4. **콘텐츠와 표현의 분리**: 콘텐츠 데이터와 사이트 디자인·템플릿을 분리한다.
    
5. **독립적인 콘텐츠**: 특정 CMS나 원격 서비스에 종속되지 않도록 원본 파일을 보존한다.
    
6. **사용자 주도 배포**: 빌드와 배포는 사용자가 명시적으로 실행한다.
    
7. **최소한의 복잡성**: 초기 버전에 불필요한 서버 기능, 메타데이터, 자동화 기능을 추가하지 않는다.
    
8. **자격 증명 보호**: GitHub 비밀번호와 인증 토큰을 편집기 UI나 일반 설정 파일에서 직접 취급하지 않는다.
    

## 2. 전체 시스템 구조

보리도는 로컬 편집기, 콘텐츠 원본, 사이트 생성기, 정적 사이트 출력물로 구성한다.

```
┌──────────────────────────────────┐
│          로컬 편집기              │
│                                  │
│  콘텐츠 관리 / Markdown 편집      │
│  설정 / 미리보기 / 빌드 / 배포    │
└────────────────┬─────────────────┘
                 │
          로컬 Node.js 서버
                 │
       ┌─────────┴─────────┐
       │                   │
       ▼                   ▼
┌──────────────┐   ┌────────────────┐
│ 콘텐츠 원본   │   │ 사이트 생성기   │
│              │   │                │
│ Markdown     │   │ 검증 / 변환     │
│ JSON         │   │ 링크 해석       │
│ 미디어 파일   │   │ HTML 생성      │
└──────────────┘   └────────┬───────┘
                            ▼
                   ┌────────────────┐
                   │ 정적 사이트 dist│
                   └────────┬───────┘
                            │
                      사용자 확인
                            │
                            ▼
                    로컬 Git 저장소
                            │
                       명시적 배포
                            ▼
                       GitHub Pages
```

### 2.1 구성 요소

|구성 요소|역할|
|---|---|
|로컬 편집기 UI|콘텐츠 편집과 관리, 설정, 미리보기, 빌드 및 배포 실행|
|로컬 Node.js 서버|파일 읽기·쓰기, 경로 검증, 빌드 작업 및 로컬 Git 명령 실행|
|콘텐츠 저장소|Markdown, JSON, 미디어 등 원본 파일 보관|
|사이트 생성기|콘텐츠 검증, Markdown 변환, 링크 처리 및 정적 페이지 생성|
|`dist/`|공개 배포용 정적 사이트 출력물|
|로컬 Git 저장소|변경 사항 관리 및 원격 저장소와의 동기화|
|GitHub 저장소|소스와 배포 결과물을 보관하는 원격 저장소|
|GitHub Pages|정적 사이트 공개|

편집기 UI는 브라우저에서 동작하되, 파일 시스템과 Git에 대한 접근은 로컬 서버가 담당한다. 브라우저 JavaScript가 임의의 로컬 파일이나 GitHub 인증 정보를 직접 다루는 구조로 만들지 않는다.

## 3. 기술 구성

|영역|기본 선택|
|---|---|
|실행 환경|Node.js|
|편집기 UI|HTML, CSS, JavaScript|
|디자인 기반|Basecoat UI|
|전용 디자인|보리도 고유 CSS 및 컴포넌트|
|콘텐츠 본문|Markdown|
|콘텐츠 메타데이터|JSON|
|저장 방식|일반 파일과 디렉터리|
|정적 사이트 생성|보리도 전용 생성기|
|버전 관리|로컬 Git|
|GitHub 인증|GitHub CLI(`gh`)를 기본 경로로 사용|
|배포|로컬 Git을 이용한 명시적 배포|
|공개 호스팅|GitHub Pages 우선 지원|

### 3.1 디자인 원칙

Basecoat UI를 기본 디자인 기반으로 사용한다. 다만 보리도만의 화면 구조와 콘텐츠 읽기 경험은 별도의 컴포넌트와 CSS로 구현한다.

- Basecoat 원본 파일을 직접 수정하지 않는다.
    
- 보리도 전용 CSS는 독립적인 계층으로 유지한다.
    
- 가능한 경우 필요한 CSS와 JavaScript를 프로젝트에 포함하여 CDN에 의존하지 않는다.
    
- GitHub 저장소의 파일 탐색 UI는 계층 구조와 탐색 방식의 참고 사례로만 사용한다.
    
- GitHub UI를 그대로 복제하지 않고, 보리도 콘텐츠 구조에 맞게 단순화한다.
    

## 4. 로컬 편집기 화면 구성

### 4.1 기본 레이아웃

편집기는 왼쪽의 관리 내비게이션과 중앙 작업 영역으로 구성한다.

```
┌───────────────────────────────────────────────────────┐
│ 보리도       저장 상태       미리보기   빌드   배포    │
├──────────────┬────────────────────────────────────────┤
│              │                                        │
│ 설정         │                                        │
│ 경론         │              작업 영역                  │
│ 이야기       │                                        │
│ 블로그       │       목록 / 편집기 / 설정 화면          │
│ 일반 페이지  │                                        │
│ 미디어       │                                        │
│              │                                        │
└──────────────┴────────────────────────────────────────┘
```

### 4.2 상단 영역

- 사이트 이름 또는 보리도 로고
    
- 저장 상태
    
- 미리보기
    
- 빌드
    
- 배포
    

빌드와 배포는 구별한다. 빌드는 공개 사이트를 생성하는 작업이며, 배포는 생성 결과를 원격 저장소에 반영하는 작업이다.

### 4.3 왼쪽 내비게이션

- 설정
    
- 경론
    
- 이야기
    
- 블로그
    
- 일반 페이지
    
- 미디어
    

각 항목은 해당 콘텐츠의 목록과 관리 기능으로 연결한다. 초기 버전에서는 복잡한 대시보드나 분석 화면을 추가하지 않는다.

### 4.4 작업 영역

선택한 메뉴에 따라 콘텐츠 목록, 편집기, 메타데이터 설정, 미디어 관리 등의 화면을 표시한다.

목록과 편집 화면의 세부 배치, 버튼 크기, 여백은 실제 화면을 구현하고 사용성을 검토한 뒤 조정한다.

## 5. 최초 실행 및 프로젝트 설정

최초 실행 시 편집기는 보리도 프로젝트를 생성하거나 기존 프로젝트를 열 수 있도록 한다.

### 5.1 최초 설정 항목

1. 로컬 프로젝트 저장 경로
    
2. 사이트 이름
    
3. 사이트 설명
    
4. 기본 언어
    
5. 작성자
    
6. 기본 라이선스
    
7. 공개 사이트 URL
    
8. GitHub 원격 저장소 URL
    
9. 배포 브랜치
    

공개 사이트 URL과 GitHub 저장소 URL은 서로 다른 설정이다.

- **공개 사이트 URL**: 사용자가 방문할 웹사이트 주소
    
- **저장소 URL**: 소스 또는 배포 파일을 전송할 Git 원격 주소
    
- **배포 브랜치**: 배포 결과물을 반영할 대상 브랜치
    

GitHub Pages의 프로젝트 사이트와 사용자 지정 도메인을 모두 고려한다. 프로젝트 사이트의 경로 접두사도 링크 및 자산 경로 생성에 반영한다.

### 5.2 프로젝트 생성

최초 설정을 마치면 다음을 생성한다.

- 기본 디렉터리 구조
    
- 기본 설정 파일
    
- 콘텐츠 유형별 초기 디렉터리
    
- 기본 템플릿 및 스타일
    
- 빌드에 필요한 프로젝트 파일
    
- Git 저장소 초기화 여부 확인
    

이미 프로젝트가 존재하는 경우 기존 파일을 무조건 덮어쓰지 않는다. 새 프로젝트 생성과 기존 프로젝트 열기는 구별한다.

## 6. GitHub 인증 및 저장소 연결

이 항목은 최초 사용 시 GitHub 계정 정보를 어떻게 처리할지에 관한 확정 설계다.

### 6.1 기본 원칙

**보리도 로컬 편집기는 GitHub 아이디와 비밀번호를 직접 입력받거나 저장하지 않는다.**

GitHub는 일반 계정 비밀번호를 HTTPS Git 인증에 사용하는 방식을 지원하지 않는다. 따라서 편집기에서 아이디와 비밀번호를 받아 Git 명령에 전달하는 구조는 사용하지 않는다.

인증은 별도 도구인 GitHub CLI를 기본 경로로 사용한다.

### 6.2 최초 인증 절차

1. 편집기가 로컬에 Git이 설치되어 있는지 확인한다.
    
2. GitHub CLI(`gh`)가 설치되어 있는지 확인한다.
    
3. GitHub CLI 인증 상태를 확인한다.
    
4. 인증되지 않았다면 사용자에게 인증 절차를 안내한다.
    
5. 사용자가 GitHub CLI의 브라우저 기반 인증을 진행한다.
    
6. 인증이 완료되면 편집기가 인증 상태를 다시 확인한다.
    
7. 사용자가 원격 저장소 URL과 배포 브랜치를 설정한다.
    
8. 저장소 접근 및 쓰기 권한을 별도로 확인한다.
    

GitHub CLI가 설치되어 있지 않다면 설치 안내를 제공한다. 초기 버전에서 편집기가 임의로 외부 프로그램을 다운로드하거나 사용자의 동의 없이 설치하지 않는다.

### 6.3 인증 정보의 보관

GitHub 인증 정보는 GitHub CLI와 운영체제의 자격 증명 관리 체계에 맡긴다.

- 편집기 설정 JSON에 비밀번호나 토큰을 저장하지 않는다.
    
- 브라우저 JavaScript에 인증 정보를 넣지 않는다.
    
- 로그나 오류 메시지에 인증 토큰을 출력하지 않는다.
    
- 인증 정보를 콘텐츠 파일이나 공개 저장소에 기록하지 않는다.
    
- 인증 정보가 포함될 수 있는 CLI 출력은 화면에 그대로 노출하지 않도록 주의한다.
    

GitHub CLI는 환경에 따라 운영체제의 자격 증명 저장소를 이용하거나 별도의 설정 파일에 인증 정보를 보관할 수 있다. 따라서 “모든 환경에서 반드시 운영체제 키체인에만 저장된다”고 가정하지 않는다.

### 6.4 인증과 저장소 권한의 구분

인증 성공만으로 배포가 가능하다고 판단하지 않는다.

|확인 항목|확인할 내용|
|---|---|
|Git 설치|로컬 Git 명령 실행 가능 여부|
|GitHub CLI 설치|`gh` 실행 가능 여부|
|계정 인증|GitHub 계정으로 인증되었는지|
|원격 저장소 접근|지정한 저장소를 읽을 수 있는지|
|쓰기 권한|해당 저장소에 변경 사항을 전송할 수 있는지|
|배포 설정|올바른 브랜치와 GitHub Pages 설정이 준비되었는지|

저장소가 없거나 쓰기 권한이 없다면 그 상태를 구체적으로 안내한다. 인증 성공과 저장소 연결 성공을 하나의 상태로 취급하지 않는다.

### 6.5 대체 인증 방식

SSH 키를 이용한 Git 인증도 가능하지만, 초기 버전의 기본 안내 경로는 GitHub CLI로 통일한다.

개인 액세스 토큰(PAT)을 편집기에 직접 입력받는 방식은 기본 경로로 제공하지 않는다. 불가피한 고급 사용 사례가 확인되기 전에는 별도의 토큰 관리 기능을 만들지 않는다.

### 6.6 사용자 동의와 배포

인증이 완료되었다고 해서 자동으로 저장소를 생성하거나 파일을 전송하지 않는다.

- 원격 저장소 연결은 사용자가 설정한다.
    
- 배포 대상 브랜치를 명시적으로 확인한다.
    
- 배포 전 변경 파일과 작업 결과를 확인할 수 있도록 한다.
    
- 빌드 오류가 있으면 배포를 중단한다.
    
- 인증, 저장소 연결, 빌드, 배포는 각각 구별된 상태로 표시한다.
    

초기 버전은 GitHub API를 필수로 사용하지 않는다. 저장소 생성이나 Pages 설정을 자동화하기보다, 필요한 경우 사용자가 GitHub 웹사이트에서 직접 설정하도록 안내한다.

## 7. 콘텐츠 유형 및 관리

초기 버전의 콘텐츠 유형은 네 가지다.

|유형|목적|기본 저장 위치|
|---|---|---|
|경론|경전, 논서 및 번역·연구 자료|`content/texts/`|
|이야기|붓다의 생애, 불교 설화 및 관련 콘텐츠|`content/stories/`|
|블로그|작성자의 글과 기록|`content/blog/`|
|일반 페이지|소개, 이용 안내 등|`content/pages/`|

미디어는 독립적인 관리 대상으로 두며 콘텐츠 유형과 구분한다.

콘텐츠 유형의 목록과 분류 규칙은 설정으로 관리할 수 있도록 한다. 초기 버전에서는 필요 이상의 분류 체계나 필수 메타데이터를 추가하지 않는다.

## 8. 콘텐츠 파일 및 메타데이터

### 8.1 기본 저장 형식

- 본문: Markdown
    
- 메타데이터: JSON
    
- 인코딩: UTF-8
    
- 내부 식별자: UUID v4
    
- 미디어: 일반 이미지 및 문서 파일
    

콘텐츠의 제목, 파일명, URL 슬러그, 내부 ID는 서로 다른 역할을 가진다. 제목이나 파일명을 바꾸더라도 내부 ID는 유지한다.

### 8.2 공통 메타데이터

기본 메타데이터는 다음과 같다.

```
{
  "id": "uuid-v4",
  "type": "story",
  "title": "콘텐츠 제목",
  "slug": "content-slug",
  "status": "draft",
  "created_at": "ISO-8601",
  "updated_at": "ISO-8601",
  "description": "",
  "order": 0
}
```

위 예시는 구조를 설명하기 위한 예시이며, 실제 구현에서는 스키마에 맞는 UUID와 날짜 값을 사용한다.

상태값은 다음과 같이 구분한다.

- `draft`: 초안. 공개 사이트에 포함하지 않는다.
    
- `published`: 공개 대상.
    
- `private`: 공개하지 않는 자료.
    

`private` 콘텐츠는 공개 사이트의 본문뿐 아니라 목록, 검색 인덱스, 내부 링크 결과 등에서도 노출되지 않도록 처리한다.

## 9. 경론 관리 구조

경론 관리에서는 원전, 번역, 연구 자료를 서로 구분하면서도 동일한 경론을 기준으로 연결한다.

### 9.1 경론 메타데이터

경론에는 다음과 같은 정보를 둘 수 있다.

- 경론 ID
    
- 제목
    
- 슬러그
    
- 원전 또는 문헌 분류 정보
    
- 저자 및 역자
    
- 언어
    
- 판본
    
- 서지 정보
    
- 관련 경론 ID
    

대장경 분류와 번호는 임의로 부여하지 않는다. 특히 신수대장경 분류는 권위 있는 목록과 대조하여 확정한다.

### 9.2 독립적인 자료 트리

각 경론 아래에 다음 자료 영역을 둔다.

```
경론
├── translation/
├── original/
└── research/
```

각 영역은 독립적인 트리 구조를 가진다.

- `translation/`: 번역문
    
- `original/`: 원문
    
- `research/`: 주석, 조사, 연구 자료
    

사용자는 현재 열어 본 자료 영역의 트리만 탐색한다. 번역·원문·연구 트리를 한 화면에 모두 펼쳐 놓지 않는다.

### 9.3 유연한 계층 구조

권, 장, 절, 주제 등의 계층 깊이를 미리 고정하지 않는다. 문헌마다 필요한 깊이를 사용할 수 있도록 한다.

구조 노드와 실제 본문 문서는 구분한다.

- `_node.json`: 구조 노드의 메타데이터
    
- `_index.md`: 필요한 경우 노드의 개요 또는 안내문
    
- 본문 Markdown: 실제 읽을 문서
    

모든 구조 노드에 본문을 강제하지 않으며, 모든 문서가 동일한 깊이에 위치해야 한다고 가정하지 않는다.

### 9.4 경론 읽기 화면과의 관계

로컬 편집기에서 경론을 관리하는 방식과 공개 사이트에서 경론을 읽는 방식은 동일한 콘텐츠 구조를 공유한다.

다만 편집기 UI와 공개 읽기 UI는 목적이 다르므로 별도로 구현한다. 공개 읽기 화면의 세부 동작은 「보리도 경론 읽기 화면 상세 명세서」를 기준으로 한다.

## 10. Markdown 편집 및 링크

### 10.1 본문 편집

본문은 Markdown으로 작성한다. 편집기는 본문과 메타데이터를 구분하여 저장하며, 본문 편집 과정에서 메타데이터가 의도치 않게 손상되지 않도록 한다.

Markdown 파서와 확장 문법은 구현 단계에서 선택하되, 표준 문법을 우선한다.

### 10.2 내부 링크

내부 콘텐츠 링크는 제목이나 경로를 직접 박아 넣기보다 안정적인 내부 ID를 기준으로 연결한다.

빌드 시 내부 ID를 실제 공개 URL로 해석한다.

- 대상 콘텐츠가 존재하는지 검증한다.
    
- 공개되지 않는 콘텐츠로 향하는 링크가 공개 결과에 노출되지 않도록 한다.
    
- 제목이나 슬러그가 변경되어도 내부 참조를 유지할 수 있도록 한다.
    
- 잘못된 링크는 빌드 보고서에 표시한다.
    

내부 링크를 본문에서 어떤 문법으로 표현할지는 별도 구현 항목으로 둔다.

### 10.3 각주

본문의 각주는 Markdown 원본에 유지한다.

공개 사이트에서는 각주 참조와 각주 내용을 읽기 화면의 우측 패널에서 탐색할 수 있도록 변환한다.

- 각주 참조를 누르면 해당 각주를 열고 강조한다.
    
- 각주 내용에서 참조 위치로 돌아갈 수 있다.
    
- 각주가 없는 문서에는 각주 버튼이나 빈 패널을 표시하지 않는다.
    
- 목차와 각주는 하나의 우측 패널에서 전환한다.
    

각주 원문과 렌더링 결과를 분리하여, 원본 Markdown을 보존하면서 읽기 경험을 개선한다.

## 11. 미디어 관리

이미지와 문서 파일은 콘텐츠 본문과 분리하여 관리한다.

기본 디렉터리는 다음과 같다.

```
media/
├── images/
├── documents/
└── icons/
```

초기 버전에서는 미디어 파일의 등록, 경로 확인, 본문 삽입 및 사용 여부 검증을 지원하는 방향으로 설계한다.

미디어별 복잡한 태그 체계나 자동 분류 기능은 필수로 두지 않는다. 실제 사용 패턴을 확인한 뒤 필요하면 확장한다.

## 12. 저장과 편집 상태

편집기에서 콘텐츠를 수정하면 로컬 파일에 저장한다.

저장 상태는 사용자가 현재 편집 내용이 저장되었는지 판단할 수 있도록 표시한다.

- 저장 전 변경 사항이 있는지 표시한다.
    
- 저장 중과 저장 완료 상태를 구분한다.
    
- 저장 실패 시 원인을 안내한다.
    
- 다른 콘텐츠로 이동할 때 저장하지 않은 변경 사항을 잃지 않도록 확인한다.
    
- 파일 쓰기는 로컬 서버를 통해 수행한다.
    

자동 저장 여부와 저장 지연 시간 등은 사용성 검증 단계에서 확정한다. 저장 실패 시 조용히 변경 사항을 버리는 동작은 허용하지 않는다.

## 13. 정적 사이트 생성 과정

사이트 생성기는 원본 콘텐츠를 읽어 공개 가능한 정적 사이트를 만든다.

### 13.1 빌드 순서

1. 설정 파일 읽기
    
2. 콘텐츠 메타데이터와 파일 구조 읽기
    
3. 필수 필드와 콘텐츠 상태 검증
    
4. 경론 분류 및 트리 구조 검증
    
5. Markdown 파싱
    
6. 내부 링크와 미디어 경로 해석
    
7. 각주와 목차 처리
    
8. 콘텐츠 유형별 페이지 생성
    
9. 공통 템플릿과 스타일 적용
    
10. 공개 검색 인덱스 생성
    
11. `dist/` 출력
    
12. 오류 및 경고 보고서 표시
    

### 13.2 빌드 검증

최소한 다음 항목을 확인한다.

- 필수 메타데이터 누락
    
- ID 중복
    
- 존재하지 않는 분류 참조
    
- 내부 링크 대상 누락
    
- 공개 URL 충돌
    
- 잘못된 콘텐츠 경로
    
- 존재하지 않는 미디어 파일
    
- Markdown 또는 각주 처리 오류
    
- 비공개 콘텐츠의 공개 결과 유입
    
- GitHub Pages 경로 접두사 오류
    

오류와 경고를 구분한다. 공개 결과의 무결성이나 개인정보·비공개 콘텐츠 보호에 영향을 주는 오류가 있으면 빌드를 실패 처리한다.

### 13.3 출력 디렉터리

정적 사이트 결과는 `dist/`에 생성한다.

`dist/`는 생성 결과물이며, 원본 콘텐츠와 구별한다. 생성 과정에서 원본 콘텐츠를 덮어쓰지 않는다.

## 14. 미리보기

편집기는 로컬에서 생성 결과를 확인할 수 있도록 한다.

미리보기는 공개 사이트와 가능한 한 동일한 템플릿, CSS, 콘텐츠 변환 규칙을 사용한다.

미리보기와 실제 공개 URL의 차이가 있다면 경로 접두사, 상대 경로, 사용자 지정 도메인 등의 설정 차이를 명확하게 처리한다.

미리보기 실행만으로 원격 저장소에 파일을 전송하지 않는다.

## 15. Git 및 배포 절차

### 15.1 기본 흐름

```
콘텐츠 편집
    ↓
로컬 저장
    ↓
미리보기
    ↓
빌드 및 검증
    ↓
오류 확인
    ↓
변경 파일 확인
    ↓
사용자 승인
    ↓
Git 커밋 및 원격 전송
    ↓
GitHub Pages 배포 결과 확인
```

### 15.2 배포 전 확인

배포 화면에서는 최소한 다음을 확인할 수 있어야 한다.

- 대상 원격 저장소
    
- 대상 브랜치
    
- 변경 파일
    
- 빌드 성공 여부
    
- 배포 작업 실행 여부
    

빌드에 오류가 있으면 배포를 진행하지 않는다. 사용자가 명시적으로 실행하기 전에는 원격 저장소에 변경 사항을 전송하지 않는다.

### 15.3 Git 명령 처리

Git 작업은 로컬 서버에서 실행한다. 사용자 컴퓨터의 Git 인증 환경을 활용하고, 브라우저에서 인증 정보를 직접 전달하지 않는다.

- 기존 원격 저장소와 브랜치를 확인한다.
    
- 변경 사항을 사용자에게 알린다.
    
- 충돌이나 전송 실패가 발생하면 오류를 표시한다.
    
- 강제 푸시를 기본 동작으로 사용하지 않는다.
    
- 인증 실패와 권한 부족을 구분하여 안내한다.
    

초기 버전에서는 GitHub API를 필수 의존성으로 추가하지 않는다. 저장소 생성, Pages 설정 등은 사용자가 직접 처리하고 편집기는 필요한 안내를 제공한다.

## 16. URL 및 공개 경로

공개 URL은 콘텐츠의 제목이나 파일명과 분리하여 관리한다.

기본 URL 구조는 다음과 같다.

```
/texts/
/texts/{section-slug}/
/texts/{text-slug}/
/texts/{text-slug}/{tab}/{node-path}/
/stories/
/blog/
/pages/{page-slug}/
```

위 구조는 기본 방향이며, 실제 URL 규칙은 콘텐츠 데이터 및 파일 구조 명세와 일치시킨다.

### 16.1 경로 처리 원칙

- GitHub Pages 프로젝트 사이트의 경로 접두사를 지원한다.
    
- 사용자 지정 도메인에서는 불필요한 접두사를 붙이지 않는다.
    
- 내부 링크는 빌드 시 실제 공개 경로로 변환한다.
    
- 콘텐츠 제목 변경과 URL 변경을 구분한다.
    
- 공개 URL 변경 시 이전 주소를 관리할 수 있는 구조를 마련한다.
    

URL 변경 이력과 리디렉션 방식은 별도 설정으로 관리하되, 초기 구현에서는 필요한 수준부터 적용한다.

## 17. 보안 및 데이터 보호

로컬 중심 시스템이라도 파일 시스템과 Git 명령을 다루므로 기본적인 보안 조치가 필요하다.

### 17.1 로컬 서버

- 기본적으로 로컬 컴퓨터에서만 접근할 수 있도록 바인딩한다.
    
- 외부 네트워크에 무단으로 서버를 공개하지 않는다.
    
- 파일 경로를 검증하고 프로젝트 디렉터리 밖으로 벗어나는 경로 접근을 차단한다.
    
- 임의의 셸 명령을 브라우저 입력값으로 직접 실행하지 않는다.
    
- 사용자 입력을 Git 명령의 안전하지 않은 인자로 조합하지 않는다.
    

### 17.2 인증 정보

- GitHub 비밀번호를 수집하지 않는다.
    
- PAT 등 토큰을 일반 설정 파일에 저장하지 않는다.
    
- 브라우저 JavaScript에 인증 정보를 전달하지 않는다.
    
- 로그와 오류 메시지에 비밀 정보를 출력하지 않는다.
    
- GitHub CLI 또는 Git이 제공하는 인증 메커니즘을 이용한다.
    

### 17.3 비공개 콘텐츠

`draft`와 `private` 콘텐츠는 공개 빌드 대상에서 제외한다.

본문 HTML뿐 아니라 검색 인덱스, 목록, 사이트맵, 링크 해석 결과 및 기타 생성 파일에도 비공개 콘텐츠의 정보가 유입되지 않도록 검증한다.

## 20. 완료 기준

다음 조건을 충족하면 초기 버전의 기본 기능이 구현된 것으로 판단한다.

1. 사용자가 로컬 프로젝트를 생성하거나 기존 프로젝트를 열 수 있다.
    
2. 네 가지 콘텐츠 유형을 관리할 수 있다.
    
3. 콘텐츠가 일반 파일로 저장되며 데이터베이스 서버가 필요하지 않다.
    
4. 경론의 원문·번역·연구 자료를 독립적인 트리로 관리할 수 있다.
    
5. 콘텐츠를 편집하고 미리보기에서 결과를 확인할 수 있다.
    
6. 빌드 오류를 확인하고 공개 사이트를 생성할 수 있다.
    
7. 초안과 비공개 콘텐츠가 공개 결과에 포함되지 않는다.
    
8. GitHub 계정 인증을 편집기에 비밀번호를 입력하지 않고 진행할 수 있다.
    
9. 계정 인증과 저장소 쓰기 권한을 구분하여 확인할 수 있다.
    
10. 사용자가 확인하고 승인한 경우에만 원격 저장소에 배포할 수 있다.
    
11. 인증 정보가 브라우저 코드나 일반 프로젝트 설정에 기록되지 않는다.
    
12. GitHub Pages 프로젝트 경로와 사용자 지정 도메인에서 링크가 정상 동작한다.
    

## 21. 확정 사항과 후속 검토 사항

### 확정 사항

- 로컬 우선, 파일 중심, 정적 사이트 생성 구조
    
- 로컬 Node.js 서버를 통한 파일 및 Git 작업
    
- Markdown 본문과 JSON 메타데이터
    
- 경론·이야기·블로그·일반 페이지의 네 가지 콘텐츠 유형
    
- 경론의 번역·원문·연구 트리 분리
    
- Basecoat UI 기반과 보리도 전용 CSS의 분리
    
- 로컬 미리보기와 정적 빌드의 분리
    
- 사용자 승인 기반 배포
    
- GitHub CLI를 기본 인증 경로로 사용

- 인증, 저장소 접근 권한, 빌드, 배포 상태의 분리
    
- 초기 버전에서 GitHub API와 복잡한 자동화 기능을 필수로 요구하지 않음

- 미디어 인덱스와 사용 여부 검증 방식
    
- URL 변경 이력 및 리디렉션 처리
    
- 빌드 오류와 경고의 세부 기준
    
- Basecoat 구성요소의 실제 선택과 화면 치수
    
- GitHub CLI 및 Git 버전 확인과 오류 안내의 구체적인 구현

## 설계 결론

보리도 로컬 편집기는 별도의 온라인 CMS를 만드는 것이 아니라, 사용자의 컴퓨터에 있는 콘텐츠 파일을 편집하고 정적 사이트로 변환하는 도구다.

콘텐츠 원본은 로컬 파일로 유지하고, 공개 사이트는 언제든 다시 생성할 수 있는 결과물로 취급한다. GitHub는 원본 및 배포 결과를 보관하고 공개하는 수단이며, 인증과 권한 관리는 기존 Git 및 GitHub 도구에 맡긴다.

초기 구현은 콘텐츠 작성과 읽기 경험, 안정적인 정적 빌드, 안전한 배포에 집중한다. 나머지 기능은 실제 사용 과정에서 필요성이 확인된 경우에만 추가한다.
