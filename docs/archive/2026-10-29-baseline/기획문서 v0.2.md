## 1. 프로젝트 개요

### 1.1 프로젝트 정의

보리도(Borido)는 로컬 파일을 기반으로 콘텐츠를 작성·관리하고, 독립적인 정적 사이트 생성기를 통해 웹사이트를 제작·배포하는 개인용 콘텐츠 관리 시스템(CMS)이다.

경론·이야기·블로그·일반 페이지를 하나의 콘텐츠 관리 환경에서 편집하되, 각 콘텐츠의 성격에 적합한 공개 화면을 제공한다.

### 1.2 핵심 목표

1. 콘텐츠를 로컬 파일로 안전하게 보관한다.
    
2. 웹 브라우저에서 편리하게 콘텐츠를 작성하고 관리한다.
    
3. 자체 정적 사이트 생성기를 통해 독립적인 웹사이트를 생성한다.
    
4. GitHub 저장소와 GitHub Pages를 이용해 콘텐츠를 배포한다.
    
5. 데이터 구조와 디자인을 사용자가 직접 수정·확장할 수 있게 한다.
    
6. 불필요한 서버·계정·데이터베이스 의존성을 최소화한다.
    

### 1.3 설계 원칙

- **단순성:** 처음부터 범용 CMS를 만들지 않는다.
    
- **독립성:** 특정 정적 사이트 프레임워크에 종속되지 않는다.
    
- **파일 중심:** 콘텐츠는 일반 파일로 보관하며, 별도의 데이터베이스 서버를 요구하지 않는다.
    
- **유지보수성:** 기능을 작은 모듈로 나누고 각 모듈의 책임을 명확히 한다.
    
- **확장성:** 초기에는 필요한 기능만 구현하되, 구조를 변경하지 않고 기능을 추가할 수 있도록 설계한다.
    
- **사용자 통제:** 콘텐츠·디자인·파일·배포에 대한 통제권을 사용자에게 둔다.
    
- **원본 보존:** 빌드와 배포 과정에서 원본 콘텐츠를 임의로 변경하거나 삭제하지 않는다.

## 2. 전체 시스템 구조

보리도는 로컬 편집기와 공개 정적 사이트를 별개의 실행 환경으로 구분한다.

### 2.1 로컬 편집기

- Node.js 로컬 서버에서 실행한다.
    
- 브라우저 기반 편집기에서 콘텐츠를 작성·수정한다.
    
- 로컬 파일 시스템의 콘텐츠를 읽고 저장한다.
    
- 콘텐츠 구조와 메타데이터를 관리한다.
    
- 사이트를 빌드하고 미리보기한다.
    
- 배포 전 변경 사항과 오류를 확인한다.
    
- Git 명령을 통해 저장소에 커밋하고 푸시한다.
    

### 2.2 공개 정적 사이트

- HTML·CSS·JavaScript·이미지 등 정적 파일로 생성한다.
    
- 별도의 데이터베이스나 서버 측 애플리케이션을 요구하지 않는다.
    
- GitHub Pages 또는 다른 정적 호스팅 환경에서 제공한다.
    
- 로컬 편집기와 콘텐츠 모델 및 디자인 규칙을 공유한다.
    
- 공개 사이트에는 공개 상태로 지정된 콘텐츠만 포함한다.
    

### 2.3 기본 실행 원칙

- 콘텐츠 작성과 빌드는 오프라인에서도 가능해야 한다.
    
- GitHub 배포에는 네트워크 연결이 필요하다.
    
- 로컬 편집기는 기본적으로 localhost에만 바인딩한다.
    
- 콘텐츠 저장, 사이트 빌드, GitHub 배포는 별개의 작업으로 처리한다.
    
- 빌드 결과물은 `dist/`에 생성하며 원본 콘텐츠와 구분한다.

## 3. 최초 실행 및 사이트 설정

로컬 편집기를 처음 실행하면 대시보드 대신 사이트 생성 마법사를 표시한다.

### 3.1 초기 설정 항목

1. **로컬 프로젝트 경로**
    
    - 콘텐츠와 설정 파일을 보관할 디렉터리
        
    - 지원되는 환경에서는 폴더 선택 기능 제공
        
    - 경로의 존재 여부와 쓰기 권한 확인
        
    - 기존 보리도 프로젝트가 있으면 인식
        
    - 기존 파일을 덮어쓸 가능성이 있으면 사전 경고
        
2. **공개 웹사이트 URL**
    
    - 예: `https://example.github.io/borido/`
        
    - URL 형식과 경로 접두부 검증
        
    - 프로젝트 사이트와 사용자 정의 도메인을 구분
        
3. **사이트 기본 정보**
    
    - 사이트명
        
    - 설명
        
    - 기본 언어
        
    - 작성자 또는 운영자 표시명
        
    - 기본 라이선스
        
4. **GitHub 설정**
    
    - 저장소 URL
        
    - 배포 브랜치
        
    - 배포 대상 경로
        
    - 인증 상태 확인
        

GitHub 저장소 URL과 공개 웹사이트 URL은 별도 항목으로 관리한다. 두 값은 서로 다른 목적을 가지므로 동일한 값으로 취급하지 않는다.

### 3.2 초기화 및 이후 실행

- 입력값을 검증한 후 초기 프로젝트 파일과 설정을 생성한다.
    
- 초기화가 완료되면 대시보드로 이동한다.
    
- 이후 실행에서는 마법사를 다시 표시하지 않는다.
    
- 설정 메뉴에서 프로젝트 경로와 사이트 정보를 관리할 수 있다.
    
- 프로젝트 경로를 변경할 때는 기존 파일과 참조의 이동·복사·검증 절차를 제공한다.
    

### 3.3 보안

- GitHub 인증정보를 브라우저 JavaScript나 일반 설정 파일에 평문으로 저장하지 않는다.
    
- 가능한 경우 로컬 Git의 인증 관리 기능을 이용한다.
    
- 파일 접근 경로를 검증하고 프로젝트 외부 파일에 대한 임의 접근을 제한한다.

## 5. 경론 분류 및 탐색 체계

### 5.1 기본 분류

경론 메뉴는 신수대장경(대정신수대장경)의 분류 체계를 기본 탐색 구조로 사용한다.

아함부·반야부·중관부 등 대분류를 경론 메뉴의 첫 페이지에 표시하고, 각 분류를 선택하면 해당 분류에 속하는 개별 경론 목록을 보여준다.

실제 분류명·소속·대장경 번호는 신수대장경의 목차와 서지자료를 확인하여 확정한다. 예시로 사용한 분류명이 전체 분류 목록을 의미하지는 않는다.

### 5.2 분류 데이터 원칙

- 분류에는 안정적인 내부 ID를 부여한다.
    
- 경론에는 대표 분류 및 필요한 서지정보를 기록한다.
    
- 분류 정보와 경론의 콘텐츠 본문을 분리한다.
    
- 메뉴와 분류별 목록은 데이터에서 자동 생성한다.
    
- 필요하면 한 경론에 대표 분류 외의 추가 분류 정보를 기록할 수 있다.
    
- 초기 버전에서는 신수대장경 분류를 기본 탐색 체계로 삼는다.
    
- 별도의 주제별 분류는 실제 필요가 확인된 후 추가한다.
    

### 5.3 경론 탐색 흐름

1. 사용자가 공개 사이트의 경론 메뉴에 들어간다.
    
2. 신수대장경 대분류 목록을 확인한다.
    
3. 대분류를 선택한다.
    
4. 해당 분류의 경론 목록을 확인한다.
    
5. 개별 경론을 선택한다.
    
6. 개별 경론의 전용 페이지에서 번역·원문·연구 자료를 탐색한다.

## 6. 개별 경론의 데이터 구조

### 6.1 경론과 문서의 구분

경론 자체는 하나의 상위 콘텐츠 단위이며, 번역·원문·연구는 그 아래에 놓이는 독립적인 콘텐츠 영역이다.

각 영역은 서로 독립적인 문서 트리를 가진다.

- 번역: 한국어 번역문과 관련 자료
    
- 원문: 한문·팔리어 등 원문 자료
    
- 연구: 용어·해석·주제별 연구 문서
    

### 6.2 독립 트리 원칙

- 세 탭의 계층 구조를 강제로 일치시키지 않는다.
    
- 각 탭은 서로 다른 권·장·절 구성을 가질 수 있다.
    
- 연구 탭은 권차 구조 대신 주제별 구조를 사용할 수 있다.
    
- 문서 ID와 공개 상태는 각 문서마다 독립적으로 관리한다.
    
- 다른 탭의 문서로 연결하는 기능은 선택적으로 제공한다.
    

### 6.3 구조 노드와 본문 문서

권·장·절은 콘텐츠를 정리하는 구조적 단위이며, 실제 본문 문서와 구분한다.

- 구조 노드는 하위 노드를 포함할 수 있다.
    
- 본문 문서는 Markdown 콘텐츠를 가진다.
    
- 구조 노드에는 선택적으로 개요나 소개 문서를 연결할 수 있다.
    
- 트리의 깊이는 고정하지 않는다.
    
- 문헌에 따라 권·품·편·장·절·게송·주제 등의 구조를 사용할 수 있다.
    
- 빈 구조 노드도 편집기에서 생성할 수 있다.
    
- 공개 트리에는 공개 규칙을 충족한 노드만 표시한다.
    

### 6.4 경론 편집 흐름

1. 경론을 생성하고 기본 서지정보를 입력한다.
    
2. 번역·원문·연구 영역을 구성한다.
    
3. 권·장·절 또는 주제별 노드를 추가한다.
    
4. 해당 노드에 본문 문서를 생성한다.
    
5. Markdown 편집과 미리보기를 수행한다.
    
6. 저장 및 공개 상태를 설정한다.
    
7. 빌드 결과에서 트리와 문서 연결을 확인한다.

## 7. 경론 공개 화면

### 7.1 경론 개요 페이지

개별 경론을 선택하면 해당 경론의 전용 페이지로 이동한다.

페이지에는 필요에 따라 다음 정보를 제공한다.

- 경론명
    
- 문헌 개요
    
- 저자·역자 및 출전 정보
    
- 신수대장경 분류 및 번호
    
- 번역·원문·연구 탭
    
- 각 탭의 문서 트리
    
- 관련 문서 및 원본 보기 링크
    

### 7.2 문서 읽기 화면

개별 문서를 열면 다음 요소를 제공한다.

- 문서 제목
    
- 경로 및 이동 경로(breadcrumbs)
    
- 본문
    
- 현재 탭의 문서 트리
    
- 문서 목차
    
- 문서 상단 도구모음
    

왼쪽에는 현재 선택된 탭의 트리를 표시한다. 트리는 접기·펼치기 및 표시·숨기기를 지원한다.

본문은 적절한 최대 너비와 줄 간격을 적용하여 장문 독서에 적합하게 구성한다.

### 7.3 문서 상단 도구모음

초기 도구모음에는 다음 기능을 포함한다.

- 문서 목차 패널 열기·닫기
    
- 각주 패널 열기·닫기
    
- 문서 트리 표시·숨기기
    
- Markdown 원본 다운로드
    
- 본문 텍스트 복사
    
- 인쇄
    
- 이전·다음 문서 이동
    
- 관련 번역·원문·연구 문서로 이동
    

실제 제공 여부는 문서 상태와 기능 지원 여부에 따라 결정한다.

### 7.4 각주 패널

원본 Markdown 문서에서는 각주를 일반적인 각주 문법으로 작성한다. 빌드된 공개 사이트에서는 각주를 오른쪽 사이드바 패널로 표시할 수 있도록 한다.

- 본문의 각주 참조를 클릭하면 대응하는 각주를 패널에서 찾고 강조한다.
    
- 패널의 각주 번호를 클릭하면 본문의 참조 위치로 이동한다.
    
- 각주가 없는 문서에서는 각주 버튼을 표시하지 않는다.
    
- 데스크톱에서는 오른쪽 패널을 사용한다.
    
- 모바일에서는 겹침형 패널 또는 이에 준하는 반응형 UI를 사용한다.
    
- 초기 버전에서는 목차와 각주 패널을 같은 위치에서 전환하는 방식을 기본으로 한다.
    
- 각주 내용은 일반 텍스트뿐 아니라 필요한 서식과 긴 역주를 수용할 수 있도록 한다.
    

각주 원문은 Markdown 안에 유지한다. 빌드 과정에서 각주를 인식하여 본문 참조와 패널 표시 데이터를 생성하며, 원본을 임의로 분리하거나 수정하지 않는다.

각주 기능은 공통 문서 렌더러의 기능으로 설계하되, 초기 검증은 경론 콘텐츠를 중심으로 진행한다.

### 7.5 GitHub 원본 연결

일반 독자의 기본 읽기 화면은 보리도 공개 사이트로 한다.

필요한 경우 개별 문서에서 다음 기능을 제공한다.

- GitHub의 원본 Markdown 파일 보기
    
- GitHub 저장소의 관련 디렉터리 보기
    
- 원본 파일 다운로드
    
- 변경 이력 확인
    

GitHub 저장소의 파일 탐색 화면을 기본 독서 화면으로 강제하지 않는다. 보리도는 GitHub 저장소를 콘텐츠의 관리·배포 기반으로 활용하되, 독서 경험은 독립적으로 설계한다.

## 8. 콘텐츠 파일과 메타데이터 관리 원칙

### 8.1 파일 형식

- 본문: Markdown
    
- 메타데이터: JSON
    
- 디자인: HTML·CSS·JavaScript 등
    
- 빌드 결과: 정적 웹 파일
    

### 8.2 메타데이터 자동 관리

사용자가 모든 메타데이터를 직접 작성할 필요가 없도록 한다.

프로그램이 자동으로 관리할 항목은 다음과 같다.

- 내부 ID
    
- 콘텐츠 유형
    
- 생성 시각
    
- 수정 시각
    
- 기본 경로 및 파일 배치
    
- 공개 상태의 기본값
    
- 문서의 필수 구조
    

제목·본문·요약 등 콘텐츠 내용은 사용자가 작성한다. 유형별로 필요한 서지정보와 선택 필드는 별도로 관리한다.

### 8.3 ID·파일 경로·URL 분리

- 내부 ID는 제목과 파일명에 종속되지 않는다.
    
- 파일명은 로컬에서 콘텐츠를 관리하기 위한 용도로 사용한다.
    
- slug는 공개 주소 생성에 활용할 수 있다.
    
- 공개 URL은 파일 경로와 별도로 관리할 수 있어야 한다.
    
- 이름 변경과 이동 후에도 내부 ID를 유지한다.
    
- URL 변경 시 이전 URL의 리디렉션을 생성할 수 있도록 한다.
    

세부적인 ID 형식, 메타데이터 필드, 파일 배치 및 URL 생성 규칙은 별도의 콘텐츠 데이터 및 파일 구조 명세서에서 확정한다.

## 10. 정적 사이트 생성 및 배포

### 10.1 빌드 과정

1. 콘텐츠 파일과 설정을 읽는다.
    
2. 메타데이터와 필수 필드를 검증한다.
    
3. 중복 ID와 경로 충돌을 검사한다.
    
4. 내부 문서 참조를 검사한다.
    
5. Markdown을 HTML로 변환한다.
    
6. 콘텐츠 유형별 템플릿을 적용한다.
    
7. 경론 분류별 목록과 문서 트리를 생성한다.
    
8. 각주 참조와 각주 패널 데이터를 생성한다.
    
9. 검색 인덱스와 목록을 생성한다.
    
10. 이미지와 기타 자산을 복사한다.
    
11. 공개 URL 및 배포 경로를 검증한다.
    
12. `dist/`에 정적 사이트를 생성한다.
    

빌드 오류가 발생하더라도 원본 콘텐츠를 변경하거나 삭제하지 않는다.

### 10.2 배포 과정

1. 콘텐츠와 설정을 검증한다.
    
2. 정적 사이트를 빌드한다.
    
3. 변경 사항을 확인한다.
    
4. 배포 대상과 공개 범위를 확인한다.
    
5. 사용자에게 변경 요약을 표시한다.
    
6. 확인 후 Git 커밋 및 푸시를 수행한다.
    
7. GitHub Pages 배포 상태를 확인할 수 있도록 한다.
    

초기 버전은 로컬 Git 명령을 활용한다. 직접 GitHub API를 이용한 복잡한 배포 기능은 필요성이 확인된 후 검토한다.

### 10.3 공개 범위

- 초안과 비공개 문서는 공개 결과물에서 제외한다.
    
- 공개된 콘텐츠와 실제로 필요한 자산만 배포한다.
    
- 비공개 자료가 공개 출력물에 섞이지 않도록 검증한다.
    
- 프로젝트 사이트 경로 접두부와 사용자 정의 도메인을 지원한다.

각 디렉터리의 세부 구성과 파일 규칙은 기술 명세서에서 확정한다.

- `app/server/`: 로컬 서버와 파일 작업
    
- `app/admin/`: 브라우저 편집기
    
- `core/`: 콘텐츠 모델, 검증, Markdown 처리, 경로와 URL
    
- `site/`: 정적 사이트 템플릿, 스타일, 스크립트
    
- `content/`: 원본 콘텐츠
    
- `media/`: 이미지 및 첨부파일
    
- `config/`: 사이트와 콘텐츠 설정
    
- `dist/`: 빌드 결과물
    

### 11.2 기술 선택 원칙

- 필요한 기능을 작은 모듈로 분리한다.
    
- Markdown 파싱 등 검증된 라이브러리를 적극 활용한다.
    
- 자체 구현은 보리도 고유 요구사항에 집중한다.
    
- 특정 프레임워크의 기능에 불필요하게 종속되지 않는다.
    
- 복잡한 플러그인 시스템이나 범용 스키마 편집기는 초기 범위에서 제외한다.
    
- 데이터 모델과 디자인을 서로 독립적으로 변경할 수 있게 한다.
