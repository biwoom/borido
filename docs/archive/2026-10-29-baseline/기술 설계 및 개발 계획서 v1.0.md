## 1. 목적과 적용 범위

이 문서는 보리도 로컬 편집기와 정적 사이트 생성기를 실제로 개발하기 위한 기술적 기준을 정한다.

기능 요구사항과 화면 구성은 기존 기획서 및 명세서를 따르며, 이 문서에서는 다음 사항을 구체화한다.

1. 시스템 아키텍처와 모듈 경계
    
2. 프로젝트 디렉터리 및 파일 구성
    
3. 핵심 데이터 흐름과 모듈 간 인터페이스
    
4. 라이브러리 선정과 기술 선택 기준
    
5. 로컬 편집기와 공개 사이트의 구현 방식
    
6. 테스트 전략과 품질 기준
    
7. GitHub 인증, 저장소 연결 및 배포 절차
    
8. 단계별 개발 순서와 완료 조건
    
9. 구현 전 확정해야 할 기술적 결정
    

### 1.1 개발의 기본 방향

보리도는 범용 CMS 프레임워크를 조합하는 프로젝트가 아니라, 콘텐츠 파일 구조와 공개 화면을 직접 통제할 수 있는 작은 독립형 시스템으로 개발한다.

따라서 다음 원칙을 적용한다.

- 로컬 파일을 콘텐츠 원본으로 유지한다.
    
- 별도 데이터베이스 서버를 도입하지 않는다.
    
- 편집기와 정적 사이트 생성기를 분리한다.
    
- 데이터 모델과 화면 디자인을 분리한다.
    
- 공통 기능을 필요한 수준에서만 모듈화한다.
    
- 빌드 결과를 원본 파일에 역으로 반영하지 않는다.
    
- 초기 버전에서 불필요한 프레임워크, 플러그인 시스템, 원격 API 의존성을 추가하지 않는다.

### 2.2 세 가지 실행 영역

|영역|역할|외부 의존성|
|---|---|---|
|로컬 편집기|콘텐츠 작성·관리·미리보기·배포 제어|로컬 서버 API|
|Core 및 생성기|데이터 해석·검증·Markdown 변환·페이지 생성|로컬 파일, 명시적 라이브러리|
|공개 정적 사이트|독자가 콘텐츠를 탐색하고 읽는 환경|정적 파일만으로 동작|

공개 사이트에는 Node.js 서버나 데이터베이스가 필요하지 않다. 공개 사이트는 생성된 파일을 웹 서버에 올리기만 하면 동작해야 한다.

### 2.3 의존성 방향

의존성은 다음 방향을 유지한다.

```
편집기 UI ──→ 로컬 서버 API ──→ Core
                                   ↑
빌드 CLI ─────────────────────────┘
                                   │
                                   ▼
                              콘텐츠 파일

정적 생성기 ──→ Core
       │
       └──→ site/templates
       └──→ site/styles
       └──→ site/scripts
```

Core는 편집기 UI나 특정 화면 구현을 알지 못해야 한다. 콘텐츠 검증과 URL 생성은 편집기와 빌드 과정에서 같은 규칙을 사용한다.

## 3. 모듈 경계

모듈은 디렉터리 수를 늘리기 위한 장치가 아니라, 서로 다른 책임을 분리하기 위한 장치다.

### 3.1 핵심 모듈

|모듈|책임|포함하지 않을 책임|
|---|---|---|
|`project`|프로젝트 설정 읽기·쓰기, 초기화, 경로 확인|화면 렌더링|
|`content`|콘텐츠 읽기·쓰기, 생성·수정·이동·삭제|HTML 생성|
|`schema`|JSON 데이터 구조 및 필드 검증|파일 저장|
|`taxonomy`|대장경 분류와 분류 참조 검증|분류 데이터 임의 생성|
|`tree`|경론의 번역·원문·연구 트리 처리|공개 화면 디자인|
|`markdown`|Markdown 파싱, 각주 및 문서 링크 처리|전체 페이지 레이아웃|
|`url`|내부 ID와 공개 URL 매핑, URL 충돌 및 이력 검증|파일 시스템 경로 추정|
|`media`|미디어 파일 확인, 경로 해석, 사용 여부 검증|이미지 편집 기능|
|`build`|콘텐츠 검증, 공개 대상 선별, 생성 과정 조정|원본 파일 수정|
|`render`|템플릿에 페이지 데이터를 전달하여 HTML 생성|콘텐츠 파일 탐색|
|`server`|로컬 HTTP API, 파일 작업 요청 처리|브라우저 UI|
|`git`|Git 상태, 변경 사항, 원격 저장소 및 배포 처리|콘텐츠 모델 변경|
|`admin`|편집기 화면과 사용자 상호작용|직접 파일 시스템 접근|

### 3.2 모듈 설계 규칙

1. 각 모듈은 한 가지 중심 책임을 가진다.
    
2. 다른 모듈의 내부 파일 경로를 임의로 조작하지 않고 공개 함수로 요청한다.
    
3. 파일 입출력은 서버 및 Core의 명시적인 경계에서 처리한다.
    
4. UI는 JSON 스키마와 URL 규칙을 중복 구현하지 않는다.
    
5. 공개 사이트의 화면 컴포넌트와 편집기 컴포넌트를 공유하려고 무리하지 않는다.
    
6. 공통으로 공유할 것은 데이터 규칙, URL 규칙, 검증 규칙, 콘텐츠 변환 규칙이다.
    
7. 초기 버전에서는 의존성 주입 프레임워크나 범용 이벤트 시스템을 도입하지 않는다.
    

### 3.3 공통 API 원칙

Core 모듈은 가능한 한 명시적인 입력과 출력을 가진 함수로 작성한다.

예를 들어 다음과 같은 인터페이스를 사용한다.

```
validateContent(content, context)
resolveDocumentUrl(documentId, urlIndex)
buildDocumentTree(rootPath, options)
parseMarkdown(markdown, options)
buildSite(projectRoot, buildOptions)
```

위 함수 이름은 인터페이스의 형태를 설명하기 위한 예시다. 실제 이름과 인자는 구현 전에 확정한다.

함수는 가능한 한 결과와 오류 정보를 명시적으로 반환한다. 화면에서 보여줄 메시지와 내부 오류 정보를 구분하여, 내부 경로나 민감한 정보가 불필요하게 노출되지 않도록 한다.

### 4.1 디렉터리별 원칙

`**app/server/**`

로컬 HTTP 서버와 요청 처리를 담당한다. 허용된 프로젝트 경로를 확인한 뒤 Core의 기능을 호출한다. 파일 경로를 URL 파라미터 그대로 사용하지 않는다.

`**app/admin/**`

편집기 UI를 담당한다. 브라우저에서 동작하는 JavaScript는 서버 API를 통해서만 파일을 읽고 쓴다.

`**core/**`

콘텐츠 데이터 모델, 검증, 트리, Markdown, URL, 미디어 및 빌드 로직을 둔다. 특정 UI 라이브러리에 의존하지 않는다.

`**site/**`

공개 사이트의 템플릿, CSS, JavaScript를 둔다. Basecoat 스타일과 보리도 전용 스타일을 구분한다.

`**content/**`**,** `**media/**`**,** `**config/**`

사용자가 관리하는 원본 자료와 프로젝트 설정이다. 빌드 결과를 저장하는 위치로 사용하지 않는다.

`**scripts/**`

개발자가 명령줄에서 실행하는 빌드 및 검증 도구를 둔다.

`**tests/**`

단위 테스트, 통합 테스트, 브라우저 테스트와 테스트용 콘텐츠를 둔다.

`**dist/**`

공개 사이트 생성 결과다. 원본 콘텐츠와 분리하고 Git 추적 여부는 배포 방식을 결정할 때 명시적으로 설정한다.

### 4.2 사용자 콘텐츠와 애플리케이션 코드의 분리

보리도 프로그램 자체와 사용자가 편집하는 콘텐츠는 분리되어야 한다.

프로그램을 업데이트하더라도 `content/`, `media/`, `config/`의 사용자 데이터가 덮어써지면 안 된다.

프로젝트 생성과 애플리케이션 업데이트는 별도 작업으로 처리한다. 프로젝트를 초기화할 때 기존 콘텐츠가 발견되면 무조건 덮어쓰지 않고 중단하거나 명시적인 확인을 요구한다.

## 5. 데이터 처리 및 저장 설계

### 5.1 데이터 원본

콘텐츠의 기준 원본은 Markdown과 JSON 파일이다.

- JSON: 제목, 내부 ID, 콘텐츠 유형, 상태, 분류, 정렬 순서 등
    
- Markdown: 실제 본문
    
- 미디어 파일: 이미지 및 첨부 문서
    
- 설정 JSON: 사이트 설정, 분류 목록, URL 이력
    

초기 버전에서는 데이터베이스나 별도의 캐시 서버를 도입하지 않는다.

### 5.2 ID와 파일 경로

내부 ID, 제목, 파일명, slug, 공개 URL은 별개로 취급한다.

- 내부 ID는 콘텐츠의 지속적인 식별자다.
    
- 파일 경로는 로컬 저장 위치다.
    
- slug는 URL 생성에 사용하는 사람이 읽을 수 있는 식별자다.
    
- 공개 URL은 사이트에서 실제로 접근하는 주소다.
    

콘텐츠 이동이나 이름 변경 시 이 값들을 무조건 동일하게 바꾸지 않는다. 특히 내부 ID는 일반적인 편집 과정에서 변경하지 않는다.

### 5.3 경론 트리

경론의 번역·원문·연구는 독립된 트리로 처리한다.

트리 모듈은 다음을 담당한다.

- 노드의 부모·자식 관계 해석
    
- 명시적인 `order` 값에 따른 정렬
    
- 구조 노드와 실제 본문 문서의 구분
    
- `_node.json` 및 선택적인 `_index.md` 처리
    
- 존재하지 않는 부모 노드와 중복 ID 검증
    
- 이동·삭제 시 영향받는 하위 구조 확인
    

권·장·절 등의 깊이를 고정하지 않는다.

### 5.4 파일 변경 작업의 안전성

파일 저장은 가능한 한 임시 파일에 기록한 뒤 최종 파일로 교체하는 방식으로 처리한다.

이동·삭제 등 여러 파일에 영향을 주는 작업은 다음 순서를 따른다.

1. 변경 대상과 영향을 받는 파일 확인
    
2. 데이터 및 경로 검증
    
3. 사용자 확인
    
4. 파일 변경 실행
    
5. 변경 결과 검증
    
6. 실패 시 복구 가능한 상태를 유지
    

파일 시스템의 여러 변경을 완전한 데이터베이스 트랜잭션처럼 취급할 수는 없다. 따라서 대규모 일괄 변경보다 작은 단위의 변경과 명확한 오류 처리를 우선한다.

### 5.5 공개 상태와 빌드

공개 빌드에는 `published` 상태의 콘텐츠만 포함한다.

`draft`와 `private` 콘텐츠는 HTML뿐 아니라 검색 인덱스, 목록, 사이트맵 및 링크 해석 결과에서도 제외한다.

상위 경론이나 노드가 공개되었다는 이유만으로 하위 문서가 자동 공개되지는 않는다.

## 6. 라이브러리 선정

라이브러리는 유지보수 상태, 라이선스, 브라우저·Node.js 호환성, 보안, 번들 크기와 실제 요구사항을 기준으로 선택한다.

아래는 초기 구현을 위한 권장안이다. 정확한 버전은 구현 착수 시 호환성을 확인하고 `package-lock.json`에 고정한다.

|영역|권장 선택|사용 목적|
|---|---|---|
|실행 환경|지원 중인 Node.js LTS|로컬 서버 및 빌드 실행|
|언어|JavaScript ES Modules|프런트엔드와 서버의 단순한 모듈 구조|
|로컬 HTTP 서버|Node.js 기본 `http` 모듈 우선|작은 로컬 API 구현|
|Markdown 파서|`markdown-it`|Markdown을 HTML 및 구조화된 결과로 변환|
|각주|`markdown-it-footnote` 또는 검증된 동등 확장|각주 참조와 정의 처리|
|HTML 정화|`sanitize-html`|생성 HTML의 허용 요소·속성 제한|
|JSON 스키마|`Ajv`|설정과 메타데이터 검증|
|템플릿|`Nunjucks`|공통 레이아웃 및 페이지 렌더링|
|UI 디자인|Basecoat CSS|편집기와 공개 사이트의 기본 컴포넌트 스타일|
|번들링|`esbuild`|편집기 JavaScript 번들 생성|
|단위·통합 테스트|`Vitest`|Core 및 빌드 테스트|
|브라우저 테스트|`Playwright`|반응형 UI와 주요 사용자 흐름 검증|
|GitHub 인증|GitHub CLI (`gh`)|브라우저 기반 인증 및 인증 상태 확인|
|버전 관리|Git|로컬 변경 관리 및 원격 배포|

### 6.1 프런트엔드 프레임워크

초기 버전은 별도의 React·Vue 프레임워크 없이 HTML, CSS, JavaScript ES Modules로 구현하는 것을 권장한다.

이유는 다음과 같다.

- 편집기 화면의 상태와 기능이 아직 제한적이다.
    
- 콘텐츠 데이터와 UI의 결합을 줄이기 쉽다.
    
- 빌드와 배포 구조가 단순해진다.
    
- 프레임워크 업데이트에 대한 유지보수 부담을 줄인다.
    

단, 화면 상태 관리가 실제로 복잡해지는 경우에는 전체 시스템을 재작성하기보다 해당 부분만 별도 컴포넌트로 정리한 후 재검토한다.

### 6.2 Markdown 처리

Markdown은 `markdown-it`을 우선 검토한다. 각주 확장과 내부 링크 처리는 별도의 보리도 전용 변환 계층에서 관리한다.

처리 순서는 대략 다음과 같다.

1. 원본 Markdown 읽기
    
2. 표준 Markdown 파싱
    
3. 각주와 내부 참조 식별
    
4. 내부 문서 ID를 공개 URL로 해석
    
5. 링크 및 미디어 경로 처리
    
6. 허용된 HTML 요소와 속성 검증
    
7. 최종 본문 HTML과 각주 패널 데이터 생성
    

사용자 입력으로 작성된 HTML을 무제한 허용하지 않는다. Markdown 파서의 기본 보안 설정을 확인하고, 외부 링크의 프로토콜과 HTML 속성도 검증한다.

각주 패널을 위해 Markdown 원본을 별도의 비표준 형식으로 바꾸지 않는다.

### 6.3 템플릿

Nunjucks를 사용해 공통 레이아웃과 콘텐츠 유형별 페이지 템플릿을 분리한다.

- 공통 헤더와 푸터
    
- 경론 분류 및 목록
    
- 경론 개요와 본문
    
- 이야기
    
- 블로그
    
- 일반 페이지
    
- 404 및 빈 상태
    

템플릿은 콘텐츠 파일을 직접 읽지 않는다. 빌드 모듈이 정리한 페이지 데이터를 받아 HTML을 생성한다.

자동 이스케이프 기능을 유지하고, 안전한 본문 HTML로 승인된 결과와 일반 문자열을 구분한다.

### 6.4 Basecoat와 CSS

Basecoat 기본 스타일, 보리도 공통 스타일, 보리도 전용 컴포넌트 스타일을 분리한다.

```
site/styles/
├── vendor/
│   └── basecoat.css
├── borido/
│   ├── tokens.css
│   ├── base.css
│   ├── layout.css
│   └── components.css
└── main.css
```

위 파일 배치는 권장안이다. 실제 Basecoat 배포 방식과 필요한 의존성을 확인한 뒤 결정한다.

Basecoat 파일을 직접 수정하지 않는다. 가능하면 필요한 파일을 로컬에 포함하여 CDN 없이 동작하도록 한다.

경론 트리, 문서 도구모음, 우측 목차·각주 패널은 보리도 전용 컴포넌트로 구현한다.

### 6.5 라이브러리 도입 기준

라이브러리를 추가하기 전 다음을 확인한다.

- 초기 기능에 실제로 필요한가?
    
- 더 단순한 내장 기능으로 해결할 수 있는가?
    
- 라이선스가 프로젝트에 적합한가?
    
- 유지보수가 지속되고 있는가?
    
- Node.js 및 브라우저 환경에서 호환되는가?
    
- 보안 취약점이나 불필요한 전이 의존성이 있는가?
    

편의만을 이유로 여러 개의 중복 라이브러리를 도입하지 않는다.

## 7. 로컬 서버 및 API 설계

### 7.1 기본 원칙

로컬 서버는 편집기와 파일 시스템 사이의 제한된 인터페이스다.

- 기본 주소는 `127.0.0.1`에 바인딩한다.
    
- 허용된 프로젝트 루트 밖의 파일에 접근하지 않는다.
    
- 요청 경로와 파일 경로를 별도로 검증한다.
    
- JSON 요청의 크기와 필드 형식을 검증한다.
    
- 브라우저에서 임의의 셸 명령을 실행할 수 있는 API를 제공하지 않는다.
    
- 인증 정보와 내부 서버 오류를 응답에 노출하지 않는다.
    

### 7.2 API 범위

초기 API는 다음 기능만 제공한다.

|기능 그룹|예시 기능|
|---|---|
|프로젝트|설정 읽기, 설정 변경, 초기화 확인|
|콘텐츠|목록 조회, 상세 조회, 생성, 수정, 이동, 삭제|
|트리|트리 조회, 노드 생성 및 변경|
|미디어|파일 목록, 경로 확인, 파일 등록|
|미리보기|선택한 콘텐츠의 미리보기 생성|
|빌드|검증 실행, 전체 빌드, 결과 보고서 조회|
|Git|상태 확인, 변경 목록, 원격 연결 확인|
|배포|인증 상태 확인, 배포 가능 여부 확인, 명시적 배포|

실제 엔드포인트 이름과 요청 형식은 구현 전 별도 API 명세에서 정한다.

### 7.3 파일 시스템 보호

사용자가 제공한 경로를 그대로 파일 작업에 사용하지 않는다.

- 프로젝트 루트와 정규화된 경로를 비교한다.
    
- 경로 조작을 검증한다.
    
- 심볼릭 링크를 통한 프로젝트 외부 접근을 고려한다.
    
- 파일 업로드 시 허용 위치와 파일명을 검증한다.
    
- 삭제 및 덮어쓰기 작업에 확인 절차를 둔다.
    

로컬에서만 실행된다는 이유로 보안 검증을 생략하지 않는다.

## 8. 정적 사이트 생성기

### 8.1 책임

정적 사이트 생성기는 콘텐츠 파일을 해석하여 공개 가능한 HTML, CSS, JavaScript, 이미지 및 기타 파일을 생성한다.

편집기 UI와 분리된 명령줄 작업으로도 실행할 수 있어야 한다.

예를 들어 다음과 같은 명령을 제공한다.

```
npm run validate
npm run build
npm test
```

실제 스크립트 이름은 `package.json` 작성 시 확정한다.

### 8.2 빌드 파이프라인

```
프로젝트 설정 읽기
        ↓
콘텐츠와 미디어 인덱싱
        ↓
JSON 및 파일 구조 검증
        ↓
공개 상태 선별
        ↓
경론 분류와 트리 구성
        ↓
Markdown 및 각주 처리
        ↓
내부 링크와 URL 해석
        ↓
페이지 데이터 생성
        ↓
템플릿 렌더링
        ↓
검색 인덱스 생성
        ↓
URL·경로·비공개 자료 재검증
        ↓
임시 출력 디렉터리
        ↓
검증 성공 시 dist/ 반영
```

### 8.3 빌드의 원자성

가능한 경우 빌드 결과는 임시 출력 디렉터리에 먼저 생성한다.

검증이 성공하면 최종 `dist/`에 반영한다. 빌드 도중 오류가 발생했을 때 기존의 정상 결과물을 불완전한 파일로 덮어쓰지 않도록 한다.

### 8.4 빌드 보고서

빌드 결과는 성공·오류·경고를 구분해 보여준다.

오류에는 파일 경로, 콘텐츠 ID, 문제가 발생한 항목과 가능한 해결 방법을 포함한다. 다만 인증 정보, 민감한 운영체제 경로 등 불필요한 정보는 표시하지 않는다.

초기에는 복잡한 시각화보다 명확한 목록형 보고서를 우선한다.

## 9. 공개 사이트 구현

### 9.1 공통 페이지

공개 사이트는 다음 페이지를 생성한다.

- 홈
    
- 경론 분류 및 목록
    
- 경론 개요 및 읽기 화면
    
- 이야기 목록 및 상세
    
- 블로그 목록 및 상세
    
- 일반 페이지
    
- 검색 결과
    
- 404 및 빈 상태
    

모든 콘텐츠 유형이 동일한 템플릿을 공유하도록 강제하지 않는다. 공통 헤더, 푸터, 타이포그래피 등의 공통 요소는 재사용하되 콘텐츠별 화면은 목적에 맞게 분리한다.

### 9.2 경론 읽기 화면

읽기 화면은 가장 중요한 통합 개발 대상이다.

확정된 기준은 다음과 같다.

- 데스크톱 왼쪽 트리 너비: 240px
    
- 왼쪽 트리는 기본적으로 열림
    
- 현재 자료 유형의 트리만 표시
    
- 우측 목차·각주 패널은 기본적으로 숨김
    
- 데스크톱 우측 패널은 본문을 밀어내는 방식
    
- 좁은 데스크톱에서는 공간에 따라 오버레이 방식으로 전환 가능
    
- 모바일 왼쪽 트리는 왼쪽 드로어
    
- 모바일 목차·각주 패널은 오른쪽 드로어
    
- 모바일에서 두 드로어를 동시에 열지 않음
    
- 도구 버튼은 아이콘과 텍스트 레이블을 함께 표시
    
- 각주가 없는 문서에는 각주 버튼을 표시하지 않음
    

본문 최대 너비, 패널 너비, 줄 간격과 반응형 전환점은 실제 콘텐츠를 이용해 검증한다. 기존 명세서의 수치는 초기 시험값이며, 검증 전에는 절대값으로 고정하지 않는다.

### 9.3 탐색과 접근성

- 실제 링크를 사용해 새로고침과 직접 URL 접근을 지원한다.
    
- 브라우저 뒤로 가기와 앞으로 가기가 정상 동작해야 한다.
    
- 목차 이동 시 해당 제목으로 이동한다.
    
- 각주 참조와 각주 본문 사이를 왕복할 수 있다.
    
- 키보드로 트리와 패널을 조작할 수 있다.
    
- Escape로 드로어를 닫고 포커스를 적절히 복귀시킨다.
    
- 현재 문서와 현재 메뉴에 접근성 상태를 제공한다.
    

### 9.4 URL 처리

로컬 파일 경로와 공개 URL을 분리한다.

빌드 시 사이트 기본 URL과 경로 접두사를 기준으로 링크와 자산 경로를 생성한다. GitHub Pages 프로젝트 사이트와 사용자 지정 도메인 모두에서 정상 동작하도록 테스트한다.

URL 변경 이력은 `config/url-history.json`을 기준으로 관리하는 방향을 유지한다. 리디렉션의 실제 생성 방식은 호스팅 환경에서 가능한 범위를 확인해 구현한다.

## 10. GitHub 인증 및 배포 기술 설계

### 10.1 인증 경로

기본 인증 경로는 GitHub CLI다.

```
Git 설치 확인
    ↓
GitHub CLI 설치 확인
    ↓
인증 상태 확인
    ↓
미인증이면 브라우저 인증 안내
    ↓
인증 상태 재확인
    ↓
저장소 접근 확인
    ↓
쓰기 권한 확인
    ↓
배포 설정 확인
```

보리도는 비밀번호를 입력받지 않는다. 토큰을 브라우저 JavaScript나 일반 설정 파일에 저장하지 않는다.

GitHub CLI가 운영체제 자격 증명 저장소를 사용하는지, 별도 설정 파일을 사용하는지는 환경에 따라 달라질 수 있으므로 인증 상태를 확인할 때 실제 실행 환경을 기준으로 안내한다.

### 10.2 Git 명령 실행

Git 명령은 Node.js의 프로세스 실행 기능을 이용해 실행하되, 셸 문자열을 이어 붙여 명령을 구성하지 않는다. 실행 파일과 인자를 분리하고, 작업 디렉터리를 명시한다.

인증 관련 명령의 표준 출력과 오류 출력은 토큰 등의 비밀 정보가 포함될 수 있으므로 그대로 로그에 남기지 않는다.

### 10.3 배포 방식

초기 버전은 GitHub API를 필수로 사용하지 않는다.

배포 방식은 구현 전 다음 두 가지를 구분하여 확정한다.

1. **소스 저장소**: 편집기 코드, 콘텐츠 원본, 설정을 보관하는 저장소
    
2. **공개 결과 저장소/브랜치**: `dist/`의 결과물을 GitHub Pages에 제공하는 위치
    

초기 권장안은 소스 저장소와 공개 결과를 명확히 분리하고, 공개 결과를 지정된 배포 브랜치에 게시하는 방식이다. GitHub Pages의 설정에 맞춰 배포 브랜치를 구성한다.

배포 구현에는 `gh-pages` 같은 검증된 도구를 사용할 수 있지만, 최종 선택 전 해당 도구의 유지보수 상태와 Git 동작을 확인한다. 직접 구현하더라도 강제 푸시를 기본 동작으로 사용하지 않는다.

### 10.4 배포 전 검증

배포는 다음 조건을 모두 만족할 때만 가능하다.

- 빌드 성공
    
- 공개 결과물 검증 성공
    
- 비공개 콘텐츠 유입 검사 성공
    
- 대상 저장소 확인
    
- 대상 브랜치 확인
    
- 사용자 승인
    

인증 성공은 배포 가능성을 보장하지 않는다. 저장소 접근, 쓰기 권한, Pages 설정과 브랜치 상태는 별도로 확인한다.

### 10.5 복구와 실패 처리

배포 실패 시 다음 정보를 보여준다.

- 실패한 단계
    
- 대상 저장소와 브랜치
    
- 가능한 원인
    
- 사용자가 취할 수 있는 조치
    

인증 실패, 권한 부족, 네트워크 오류, 충돌, 빌드 오류를 구분한다. 자동 강제 푸시나 사용자 확인 없는 원격 이력 재작성은 금지한다.

## 11. 테스트 전략

테스트는 개별 함수의 정확성뿐 아니라 실제 콘텐츠가 편집기에서 공개 사이트까지 정상적으로 이동하는지 검증해야 한다.

### 11.1 단위 테스트

대상:

- JSON 스키마 검증
    
- 콘텐츠 상태 판정
    
- ID 중복 검사
    
- 경론 트리 구성 및 정렬
    
- URL 생성과 충돌 검사
    
- 내부 ID 참조 해석
    
- Markdown과 각주 처리
    
- 경로 정규화
    
- 공개 콘텐츠 선별
    

외부 서비스에 접속하지 않고 실행할 수 있어야 한다.

### 11.2 통합 테스트

대상:

- 프로젝트 설정 읽기
    
- 콘텐츠 파일 읽기·쓰기
    
- 경론 트리 전체 구성
    
- Markdown 변환과 템플릿 렌더링
    
- 내부 링크 및 미디어 경로 해석
    
- 전체 빌드
    
- 비공개 콘텐츠 제외
    
- 임시 빌드 결과의 검증 및 반영
    

테스트에는 실제 운영 데이터를 사용하지 않고 별도의 테스트 프로젝트와 샘플 콘텐츠를 사용한다.

### 11.3 브라우저 테스트

Playwright를 사용해 주요 화면과 사용자 흐름을 확인한다.

|테스트 영역|확인 항목|
|---|---|
|최초 실행|프로젝트 생성과 설정 저장|
|편집기|콘텐츠 목록, 편집, 저장 상태|
|경론 관리|트리 탐색, 노드 이동, 문서 열기|
|공개 읽기 화면|트리·본문·목차·각주 동작|
|반응형|데스크톱, 좁은 화면, 모바일 드로어|
|URL|직접 접근, 새로고침, 뒤로 가기|
|접근성|키보드 조작, 포커스, 현재 항목 표시|
|배포|인증 상태와 권한 오류의 안내|

브라우저 테스트는 로컬에서 실행할 수 있어야 하며, GitHub 계정에 실제 배포하는 작업은 기본 자동 테스트에서 분리한다.

### 11.4 보안 테스트

필수 점검 항목:

- 프로젝트 루트 밖의 파일 접근 차단
    
- 경로 조작 입력 처리
    
- 악의적인 HTML과 링크 처리
    
- 비공개 콘텐츠의 검색 인덱스 유입 여부
    
- 인증 정보의 로그 노출 여부
    
- 임의 셸 명령 실행 가능성
    
- 업로드 파일 경로 검증
    
- 오류 응답의 민감 정보 노출 여부
    

### 11.5 실제 경론을 이용한 수직 통합 테스트

가장 먼저 완성할 테스트 사례는 실제 경론 한 편이다.

이 샘플에는 다음을 포함한다.

- 경론 메타데이터
    
- 번역 트리
    
- 원문 트리
    
- 연구 트리
    
- 서로 다른 깊이의 하위 노드
    
- 제목과 본문이 있는 문서
    
- 내부 문서 링크
    
- 각주가 있는 본문
    
- 미디어 참조
    
- 공개 및 비공개 자료
    

이 자료를 로컬 편집기로 관리하고, 저장하고, 빌드하고, 공개 화면에서 읽는 전 과정을 확인한다. 경론 분류 번호는 권위 있는 목록으로 검증하기 전까지 예시 데이터로 취급한다.

### 11.6 테스트 완료 기준

- 단위 및 통합 테스트가 통과한다.
    
- 핵심 화면의 브라우저 테스트가 통과한다.
    
- 공개 결과에 초안과 비공개 자료가 포함되지 않는다.
    
- URL과 미디어 경로가 정상 동작한다.
    
- 경론 트리와 각주 탐색이 데스크톱과 모바일에서 동작한다.
    
- 빌드 실패가 기존 정상 결과물을 손상시키지 않는다.
    
- GitHub 인증 정보가 일반 프로젝트 파일이나 브라우저 코드에 저장되지 않는다.
    

## 12. 개발 환경과 프로젝트 관리

### 12.1 개발 환경

- Node.js LTS
    
- npm
    
- Git
    
- GitHub CLI
    
- 코드 편집기
    
- 자동화 테스트 도구
    

개발 환경과 실제 사용자 실행 환경을 구분한다. 개발 도구가 설치되어 있다는 이유만으로 사용자의 최초 실행 환경에도 설치되어 있다고 가정하지 않는다.

### 12.2 `package.json`

명령어는 기능별로 분리한다.

```
{
  "scripts": {
    "dev": "node app/server/index.js",
    "validate": "node scripts/validate.js",
    "build": "node scripts/build.js",
    "test": "vitest run",
    "test:e2e": "playwright test"
  }
}
```

위 스크립트는 설계 예시다. 실제 파일 경로와 명령은 구현 과정에서 일치시킨다.

### 12.3 개발 규칙

- ES Modules를 사용한다.
    
- 라이브러리 버전은 잠금 파일로 관리한다.
    
- 자동 테스트를 통과한 상태에서만 주요 변경을 병합한다.
    
- 데이터 스키마 변경 시 기존 콘텐츠와의 호환성을 검증한다.
    
- 사용자 콘텐츠를 테스트 fixture와 혼합하지 않는다.
    
- 생성 결과물과 원본 파일을 구분한다.
    
- 코드 생성 도구를 사용할 때 `AGENTS.md`에 아키텍처, 금지 사항, 테스트 명령을 기록한다.

## 14. 개발 우선순위와 범위 통제

초기 개발의 우선순위는 다음과 같다.

1. 콘텐츠 원본을 안전하게 저장한다.
    
2. 콘텐츠를 정확하게 읽고 검증한다.
    
3. 경론 트리를 올바르게 구성한다.
    
4. 실제 읽을 수 있는 정적 사이트를 생성한다.
    
5. 편집기에서 콘텐츠를 관리한다.
    
6. 안전하게 배포한다.
    
7. 이후에 편의 기능을 추가한다.
    

초기 버전에서는 다음 기능을 추가하지 않는다.

- 지식 그래프와 온톨로지
    
- AI 자동 분류
    
- 플러그인 마켓
    
- 원격 CMS
    
- 계정 및 협업 시스템
    
- 별도 데이터베이스
    
- 자동 배포와 예약 작업
    
- 분석 및 추적 기능
    

기능을 추가하고 싶을 때는 핵심 흐름의 완성도와 유지보수 부담을 먼저 검토한다.

## 16. 최종 설계 원칙

보리도는 작은 규모의 독립형 로컬 CMS로 시작한다. 핵심은 프레임워크의 기능을 많이 활용하는 것이 아니라, 콘텐츠 원본과 데이터 규칙을 직접 통제하고 이를 안정적인 공개 사이트로 변환하는 데 있다.

따라서 다음을 유지한다.

- **원본 우선**: 콘텐츠는 일반 파일로 보관한다.
    
- **명확한 경계**: 편집기, Core, 생성기, 공개 사이트를 분리한다.
    
- **공통 규칙**: 데이터 모델과 URL 규칙은 한 곳에서 관리한다.
    
- **검증 우선**: 잘못된 콘텐츠와 비공개 정보의 유입을 빌드 단계에서 차단한다.
    
- **안전한 배포**: GitHub 인증은 기존 도구에 맡기고, 배포는 사용자 승인 후 실행한다.
    
- **단계적 확장**: 실제 콘텐츠 한 편의 전체 흐름을 성공시킨 뒤 범위를 넓힌다.
    

이 계획서의 목표는 모든 세부사항을 미리 확정하는 것이 아니다. 개발자가 임의로 핵심 원칙을 바꾸지 않으면서, 아직 결정되지 않은 사항을 적절한 시점에 검증하고 선택할 수 있도록 하는 것이다.
