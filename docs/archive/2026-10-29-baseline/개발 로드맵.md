# 보리도(Borido) 개발 로드맵 제안

기준 문서: 기획문서 v0.2 · 콘텐츠 데이터 및 파일 구조 명세서 v1.0 · 정적 사이트 화면 명세서 v1.0 · 경론 읽기 화면 상세 명세서 v1.0 · 로컬 편집기 설계서 v1.1 · 기술 설계 및 개발 계획서 v1.0

## 1. 개발 전략: Codex 중심의 단계적 구현

보리도는 단순한 웹사이트가 아니라, 로컬 파일을 기반으로 불교 콘텐츠를 관리하고 정적 사이트를 생성·배포하는 독립형 콘텐츠 관리 시스템이다.

따라서 개발의 핵심은 화면을 먼저 완성하는 것이 아니라, 콘텐츠 원본을 안전하게 관리하는 기반을 만들고, 그 기반 위에 정적 사이트와 로컬 편집기를 순차적으로 구현하는 것이다.

기획서와 명세서의 방향을 종합하면 다음과 같은 개발 전략이 적절하다.

1. 프로젝트 기반과 실행 환경

디렉터리 · 설정 · 로컬 서버 · Codex 작업 규칙

2. 콘텐츠 Core와 검증 시스템

JSON · Markdown · ID · 경론 트리 · URL · 내부 참조

3. 공개 사이트

경론 독서 화면 · 이야기 · 블로그

4. 로컬 편집기

콘텐츠 관리 · 편집 · 미리보기

5. 통합 검증과 안전한 빌드

자동 테스트 · 공개 상태 검사 · 경로 및 보안 검증

6. GitHub Pages 배포와 운영 안정화

명시적 배포 · 복구 절차 · 사용 설명서

위 구조에서 공개 사이트와 로컬 편집기는 서로 다른 실행 환경이지만, 동일한 콘텐츠 모델과 Core를 이용한다. 특히 공개 사이트의 독서 기능을 먼저 검증하면 편집기와 빌드 시스템이 어떤 결과를 만들어야 하는지 명확해진다.

### Codex를 기본 개발 도구로 사용하는 것이 가능한가?

가능하다. 개발자가 매번 VS Code에서 코드를 직접 편집하거나 터미널에 명령을 입력하는 방식 대신, Codex에 작업을 지시하고 생성된 변경 사항을 검토하는 방식으로 개발할 수 있다.

다만 Codex가 모든 것을 알아서 완성하도록 맡기는 방식은 권하지 않는다. 보리도는 파일 시스템 접근, 원본 데이터 보존, URL 생성, 비공개 콘텐츠 제외, GitHub 배포 등 실수의 영향이 큰 기능을 포함한다.

권장 역할 분담은 다음과 같다.

|역할|담당|
|---|---|
|사용자|요구사항 확정, 실제 사용성 판단, 콘텐츠와 공개 결과 승인|
|ChatGPT|개발 순서 설계, 작업 범위 분해, 설계 검토, 문제 분석|
|Codex|코드 작성·수정, 테스트 실행, 오류 수정, 문서 갱신|
|자동 테스트|ID·경로·콘텐츠 공개 여부·화면 동작 등의 반복 검증|

Codex를 통해 코드를 작성하는 것과 실제 프로그램을 실행하고 결과를 확인하는 것은 구별해야 한다. Codex의 실행 환경과 접근 권한에 따라 로컬 브라우저 확인, 파일 접근 또는 배포 과정에서 사용자의 승인이 필요할 수 있다.

## 2. 전체 개발 단계와 우선순위

기술 설계 및 개발 계획서의 단계 구성을 유지하되, Codex를 이용한 실제 개발에서는 작업을 검증 가능한 단위로 더 세분화하는 편이 좋다.

기간은 주당 투입 시간과 Codex의 실제 작업 결과에 따라 달라진다. 아래는 고정 일정이 아닌 상대적 작업 순서다.

0단계. 개발 착수 준비

최우선

작업 단위: 설계 확정과 Codex 환경 구축

- 기존 명세서와 기술 설계서의 충돌 및 미결정 사항 확인
    
- `AGENTS.md` 작성 및 작업 규칙 설정
    
- 프로젝트 초기 구조와 테스트 명령 확정
    
- 샘플 경론과 테스트 데이터 정책 수립
    

완료 기준: Codex가 프로젝트 규칙을 읽고, 테스트 가능한 변경을 만들 수 있는 상태.

1단계. 프로젝트 기반과 로컬 서버

작업 단위: 실행 환경 · 프로젝트 생성 · 경로 보안

- Node.js 기반 로컬 서버와 기본 편집기 화면
    
- 사이트 설정 JSON의 읽기·쓰기
    
- 신규 프로젝트 생성 및 기존 프로젝트 열기
    
- 허용된 프로젝트 경로 내부에서만 파일에 접근하도록 제한
    

완료 기준: 로컬에서 편집기를 실행하고 설정을 저장할 수 있으며, 프로젝트 외부 파일 접근을 차단한다.

2단계. 콘텐츠 Core

작업 단위: 데이터 모델 · 파일 입출력 · 검증

- 네 가지 콘텐츠 유형과 공통 메타데이터
    
- UUID, slug, 공개 상태 및 경로 규칙
    
- 콘텐츠 생성·조회·수정·삭제
    
- ID 중복, 잘못된 JSON, 참조 오류 검사
    

완료 기준: 파일 기반 콘텐츠를 생성·수정할 수 있고, 핵심 규칙을 자동 테스트로 검증한다.

3단계. 경론 분류와 독립 트리

작업 단위: 경론 모델 · 분류 데이터 · 트리 조작

- 경론과 번역·원문·연구 영역 분리
    
- 구조 노드와 본문 문서 구분
    
- 노드 추가·이동·정렬 및 부모·자식 관계 검증
    
- 신수대장경 분류 데이터 연결
    

완료 기준: 번역·원문·연구가 서로 다른 깊이와 구조를 가진 경론 한 편을 올바르게 관리한다.

4단계. Markdown 처리와 정적 사이트 생성기

작업 단위: 콘텐츠 변환 · 링크 · 빌드 파이프라인

- Markdown 파싱과 각주 변환
    
- 내부 ID 기반 링크 및 미디어 경로 해석
    
- 공개 URL 생성과 충돌 검사
    
- 템플릿 렌더링, 검색 인덱스, 빌드 보고서
    
- 임시 출력 후 검증 성공 시에만 `dist/` 반영
    

완료 기준: 샘플 경론의 정적 HTML이 생성되고, 비공개 콘텐츠가 출력물에 포함되지 않는다.

5단계. 공개 사이트 완성

작업 단위: 경론 독서 화면 · 공통 페이지 · 반응형

- 홈, 경론 분류 및 목록, 경론 개요
    
- 좌측 240px 트리와 중앙 독서 영역
    
- 목차·각주 패널 및 모바일 드로어
    
- 이야기·블로그·일반 페이지 템플릿
    
- 검색·404·빈 상태 화면
    

완료 기준: 실제 경론을 데스크톱과 모바일에서 탐색하고 읽을 수 있다.

6단계. 로컬 편집기 완성

작업 단위: 콘텐츠 관리 UI · Markdown 편집 · 미리보기

- 최초 실행 마법사와 설정 화면
    
- 경론 목록 및 트리 편집
    
- Markdown 편집·저장·미리보기
    
- 이야기·블로그·페이지 관리
    
- 미디어 관리 및 빌드 실행
    

완료 기준: 일반적인 콘텐츠 작성과 공개 준비를 코드 직접 수정 없이 수행할 수 있다.

7단계. 통합 검증과 GitHub 배포

작업 단위: 회귀 테스트 · 보안 · 배포 · 복구

- Vitest 단위·통합 테스트 및 Playwright 브라우저 테스트
    
- 실제 경론을 통한 전체 흐름 검증
    
- Git·GitHub CLI 인증 및 저장소 연결
    
- GitHub Pages 배포, 오류 안내 및 복구 절차
    
- 설치·사용·백업 설명서 작성
    

완료 기준: 원본 데이터의 안전성을 확인하고, 승인된 결과물을 공개 사이트에 배포할 수 있다.

위 순서는 기술 설계서의 프로젝트 기반 → Core → 경론 트리 → 정적 생성기 → 공개 사이트 → 나머지 콘텐츠 유형 → 배포라는 흐름을 구체화한 것이다. 실제 작업에서는 5단계와 6단계 일부를 병행할 수 있지만, 콘텐츠 모델과 빌드 규칙은 먼저 안정화하는 것이 좋다.

## 3. Codex로 개발하기 위한 작업 방식

핵심은 Codex에게 한 번에 보리도 전체를 만들도록 지시하지 않고, 작업 지시 → 구현 → 자동 검증 → 변경 검토 → 다음 작업 승인의 반복 구조를 만드는 것이다.

### 3.1 먼저 Codex 작업 규칙을 만든다

프로젝트 루트에 `AGENTS.md`를 두고, Codex가 작업을 시작할 때마다 준수할 규칙을 기록한다.

최소한 다음 내용을 포함하는 것이 좋다.

- 상위 기획서와 기술 명세서의 우선순위
    
- 콘텐츠 원본과 빌드 출력물의 분리
    
- 모듈별 책임과 의존성 규칙
    
- 변경 전 기존 코드와 관련 테스트를 확인하는 절차
    
- 작업 후 실행해야 하는 테스트 명령
    
- 명세서와 다른 구현이 필요할 때 임의로 결정하지 않고 보고하는 규칙
    
- GitHub 배포와 원본 삭제 등 위험 작업에 대한 승인 규칙
    

예를 들어, Codex에 다음과 같이 지시할 수 있다.

보리도 프로젝트의 개발을 시작한다.

먼저 프로젝트에 추가된 다음 문서를 모두 검토하라.

1. 기획문서 v0.2
    
2. 콘텐츠 데이터 및 파일 구조 명세서 v1.0
    
3. 정적 사이트 화면 명세서 v1.0
    
4. 경론 읽기 화면 상세 명세서 v1.0
    
5. 로컬 편집기 설계서 v1.1
    
6. 기술 설계 및 개발 계획서 v1.0
    

아직 본격적인 기능 구현은 하지 않는다.

첫 작업은 다음과 같다.

- 문서 사이의 충돌 및 미결정 사항을 조사한다.
    
- 기술 설계서에서 확정된 사항과 구현 전에 결정해야 할 사항을 구분한다.
    
- 프로젝트 루트의 AGENTS.md 초안을 작성한다.
    
- 이후 개발 단계와 완료 조건을 작업 단위로 나눈다.
    
- 기존 문서에 없는 기술적 결정을 임의로 확정하지 않는다.
    
- 각 작업에 필요한 테스트와 검증 기준을 명시한다.
    

결과는 변경한 파일 목록, 발견한 문제, 결정이 필요한 항목, 다음 단계 제안으로 보고한다. 이 작업에서는 별도의 기능 구현이나 배포를 하지 않는다.

이 지시를 첫 작업으로 권하는 이유는 기술 설계서가 이미 개발 기준안을 제시하고 있지만, 모든 세부 결정이 확정된 것은 아니기 때문이다. Codex가 빈틈을 임의로 메우기 전에 먼저 그 빈틈을 드러내야 한다.

### 3.2 Codex 작업은 작게 분리한다

다음과 같은 단위가 적절하다.

|적절한 작업 단위|피해야 할 작업 지시|
|---|---|
|JSON 메타데이터 검증 모듈 구현 및 테스트|콘텐츠 시스템 전체 구현|
|ID 중복 검사와 오류 보고 구현|Core 완성|
|경론 트리 구성 함수 구현|경론 관리 기능 전부 구현|
|목차·각주 패널 동작 구현|독서 화면을 한 번에 완성|
|빌드 실패 시 기존 `dist/` 보존 테스트|빌드·배포 시스템 전부 구현|

각 작업이 끝날 때 Codex에게 변경 파일, 테스트 결과, 남은 문제를 보고하게 한다. 사용자가 그 결과를 확인한 뒤 다음 작업으로 넘어가는 방식이다.

### 3.3 개발 중 지켜야 할 원칙

- 한 작업에서 여러 핵심 모듈을 동시에 바꾸지 않는다.
    
- 자동 테스트가 실패한 상태에서 새로운 기능을 계속 추가하지 않는다.
    
- 데이터 구조를 바꾸면 기존 샘플 데이터와 호환성을 확인한다.
    
- 공개 배포는 일반 테스트와 분리하고, 사용자가 승인한 경우에만 실행한다.
    
- 구현 결과가 명세와 다르면 코드에 맞춰 명세를 조용히 바꾸지 않는다.
    

## 4. 어떤 기술과 라이브러리로 시작할 것인가?

기술 설계서의 기본 방향을 유지하면서, 실제 개발에 필요한 범위로 제한하는 것을 권한다.

|영역|제안|이유|
|---|---|---|
|실행 환경|Node.js LTS, ES Modules|로컬 파일 관리와 서버 실행|
|편집기 UI|HTML·CSS·JavaScript|불필요한 프런트엔드 프레임워크 의존성 최소화|
|디자인|Basecoat UI + 보리도 전용 CSS|명세서의 화면 기준과 일치|
|콘텐츠|Markdown + JSON|파일 중심의 원본 관리|
|정적 생성|보리도 전용 빌드 모듈|URL과 문서 구조 통제|
|단위·통합 테스트|Vitest|Core 및 빌드 로직 검증|
|브라우저 테스트|Playwright|실제 UI 흐름과 반응형 동작 검증|
|버전 관리|Git + GitHub CLI|명시적인 변경 관리와 배포|

이 표는 새 라이브러리를 더 추가하자는 제안이 아니다. 기술 설계서에 명시된 선택을 기준으로, 실제 개발 중 추가 의존성을 늘리지 않는다는 뜻이다.

특히 React, Next.js, 데이터베이스, CMS 프레임워크를 개발 초기에 도입할 이유는 크지 않다. 보리도는 콘텐츠 파일 구조와 정적 생성기를 직접 통제하는 것이 핵심이므로, 초기에는 작은 모듈을 조합하는 편이 설계 목적에 부합한다.

## 5. 첫 번째 통합 목표: 경론 한 편을 끝까지 처리한다

초기 개발에서 가장 중요한 것은 기능 수가 아니라 수직 통합(vertical slice)이다. 즉, 하나의 실제 경론이 로컬 편집기에서 시작해 공개 사이트에 도달하는 전체 흐름을 완성하는 것이다.

1. 경론 메타데이터와 기본 서지정보 생성
    
2. 번역·원문·연구의 독립 트리 구성
    
3. 서로 다른 깊이의 구조 노드와 본문 문서 생성
    
4. Markdown 본문, 내부 링크, 각주, 미디어 연결
    
5. 공개 및 비공개 문서가 섞인 샘플 데이터 검증
    
6. 정적 HTML 빌드 및 URL·경로 검증
    
7. 독서 화면에서 트리 이동, 목차, 각주, 모바일 동작 확인
    

이 과정에서 실제 콘텐츠는 테스트용 샘플과 구별해 관리해야 한다. 경론 분류 번호 또한 권위 있는 자료를 확인하기 전에는 검증된 데이터로 취급하지 않는다. 이 기준은 기술 설계서의 실제 경론 기반 수직 통합 테스트 계획과 일치한다.

기획문서 v0.2 및 기술 설계 및 개발 계획서 v1.0.md

이 통합 목표가 완성되면 이야기·블로그·일반 페이지를 추가할 때 기존 Core와 빌드 시스템을 재사용할 수 있다.

## 6. 개발 완료를 판단할 기준

개발 완료 여부는 화면이 보기 좋게 나오는지만으로 판단해서는 안 된다.

### 출시 전 검증 체크리스트

0/6

콘텐츠 원본의 안전성

저장·이동·삭제·빌드 과정에서 원본이 의도치 않게 손상되지 않는다.

데이터 일관성

ID 중복, 잘못된 경로, URL 충돌, 존재하지 않는 참조를 감지한다.

공개 상태 통제

초안과 비공개 콘텐츠가 HTML·검색 인덱스·미디어 출력에 유입되지 않는다.

독서 경험

트리, 문서 이동, 목차, 각주, 직접 URL 접근이 정상 작동한다.

반응형과 접근성

좁은 화면과 모바일에서 탐색 패널을 사용할 수 있고 키보드 조작도 가능하다.

배포 안전성

GitHub 인증 정보가 노출되지 않으며 실패한 빌드가 기존 정상 결과물을 손상시키지 않는다.

체크리스트 복사

이 체크리스트는 출시 기준의 요약이며, 실제 완료 판정은 자동 테스트 결과와 실제 브라우저 검증을 근거로 해야 한다.

## 7. 지금 당장 시작할 작업

현재 단계에서 제가 권하는 다음 순서는 명확하다.

1. Codex에게 전체 문서 검토를 맡긴다. 명세서 간 충돌, 미결정 사항, 구현 위험을 먼저 보고하게 한다.
    
2. `AGENTS.md`와 작업 규칙을 확정한다. 이후 모든 코드 생성 작업의 기준으로 삼는다.
    
3. 프로젝트 기반만 구현한다. 디렉터리, `package.json`, 로컬 서버, 설정 파일 입출력, 경로 검증을 완성한다.
    
4. Core의 검증 기능부터 테스트한다. ID, 메타데이터, 경로, 공개 상태처럼 다른 기능의 기반이 되는 부분부터 만든다.
    
5. 경론 한 편의 전체 흐름을 완성한다. 그 뒤 나머지 콘텐츠 유형과 배포 기능을 확장한다.
    

개발 일정은 특정 주차에 기능을 무조건 완료하는 방식보다 각 단계의 완료 조건을 통과했을 때 다음 단계로 이동하는 방식으로 관리하는 것이 좋다.

결론적으로, Codex를 활용하되 개발의 중심은 코드 생성량이 아니라 검증 가능한 작은 단위와 명확한 완료 조건에 두어야 한다. 이렇게 하면 직접 코드를 많이 작성하지 않으면서도 프로젝트의 구조와 데이터 안전성을 통제할 수 있다.
