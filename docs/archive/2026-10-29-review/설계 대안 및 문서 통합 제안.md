# 보리도 설계 대안 및 문서 통합 제안

- 작성일: 2026-10-29
- 상태: 사용자 검토용 추천안. 이 문서의 추천을 기존 명세의 확정 사항으로 취급하지 않는다.
- 대상: [기존 검토의 I01–I12·D01–D22](<문서 검토 및 결정 과제.md>)와 문서 체계 재편.
- 이번 반영: 프로젝트 저장소 기록, 대안 조사와 통합 계획. 원문 이동·통합 명세 재작성·기능 구현·Git 변경·배포는 아직 수행하지 않았다.

## 1. 먼저 반영한 프로젝트 정보

사용자가 지정한 저장소는 [https://github.com/biwoom/borido](https://github.com/biwoom/borido)다. Git 원격 주소 형식은 `https://github.com/biwoom/borido.git`이다. 2026-10-29 GitHub 연결로 공개성 `public`과 기본 브랜치 `main`을 확인했다. 로컬 폴더에는 아직 Git 저장소가 없다. 원격의 Pages 설정이나 실제 사이트 주소는 확인하거나 변경하지 않았다.

이 주소는 프로젝트 기록과 루트 [AGENTS.md](<AGENTS.md>)에 반영했다. 프로그램 개발 저장소와 사용자의 콘텐츠 원본/공개 사이트 배포 저장소는 역할을 구분할 것을 권한다. 주소 제공만으로 모든 콘텐츠와 `dist/`를 이 저장소에 올리는 것으로 해석하지 않는다.

특히 **공개 Git 저장소에 들어간 원본과 Git 이력은 `private` 콘텐츠 상태로 숨길 수 없다.** 공개 빌드에서 제외하는 것과 저장소 접근을 제한하는 것은 다른 경계다. 따라서 이 프로젝트의 파일 중심 철학을 유지하면서도 사용자 프로젝트를 프로그램 체크아웃 밖에 두는 것이 우선 권고다.

## 2. 대안을 고르는 기준

보리도는 개인이 문헌을 오래 보존하고 편집하며 독립된 사이트로 읽게 하는 도구다. 다음 순서로 대안을 평가했다.

1. 원본 파일과 사용자의 편집 내용을 보존할 것.
2. 비공개 자료가 의도치 않게 공개되지 않을 것.
3. 프로그램이 없어도 파일과 구조를 이해할 수 있을 것.
4. 편집기·생성기·공개 화면에서 같은 규칙을 사용할 것.
5. 개인이 유지보수할 수 있도록 의존성과 상태를 줄일 것.
6. 실제 경론 한 편으로 끝까지 검증할 수 있을 것.

가장 작은 코드가 항상 가장 단순한 운영을 뜻하지는 않는다. URL 안정성, 저장 충돌 감지, 실패 복구는 초기에 포함할 가치가 있다. 반면 자동 저장, 프레임워크, 여러 스타일 팩, 다중 사용자, 원격 CMS는 초기 복잡성을 늘린다.

기존 문서의 빈칸을 모두 영구 고정하는 것도 피한다. **데이터 계약과 안전 원칙은 구현 전에 정하고, 글꼴·치수·성능 예산은 실제 자료를 측정해 확정하는 방식**을 권한다. 이는 미결정 방치가 아니라 각 결정을 검증 가능한 시점에 하는 것이다.

## 4. 미결정 과제 22건의 추천안

### D01. 실행 환경과 도구

**추천:** Node.js 24 LTS·npm·JavaScript ES Modules, Node 기본 HTTP, 바닐라 UI를 기준으로 한다. 파서는 `markdown-it`+`markdown-it-footnote`, 검증은 Ajv, 템플릿은 Nunjucks, 정화는 `sanitize-html`, 테스트는 Vitest/Playwright를 권한다. UI는 네이티브 ESM으로 시작하고 npm 모듈 번들링이 실제로 필요한 시점에 esbuild를 도입한다.

- 이유: 기존 기술 방향을 유지하면서 초기 실행·빌드 구조를 작게 만들 수 있다. Node.js 공식 목록에서 24와 26이 모두 LTS인 것을 확인했으며, 초기 기준은 24로 제안한다. 26까지 지원한다고 미리 약속하지 않는다. [Node.js 공식 릴리스 목록](https://nodejs.org/en/about/previous-releases)
- 대안: 최신 LTS인 26을 즉시 기준으로 삼을 수도 있다. 이득보다 초기 호환성 검증 범위를 줄이는 쪽을 우선해 24를 추천한다. React/Vue·TypeScript·대형 정적 사이트 프레임워크는 초기 추가하지 않는다.
- 범위: 로컬 편집기는 우선 현재 개발 환경인 macOS에서 검증하고 Windows/Linux 지원은 검증 후 표시한다. 공개 사이트는 Chromium·Firefox·WebKit 자동 검증과 실제 Safari/모바일 확인을 목표로 한다. 엔진 테스트와 실제 기기 테스트는 구분한다.
- 검증: 도입 시점의 배포된 패키지·Node/npm 패치 버전·라이선스·보안·ESM 호환성을 확인하고 잠금 파일에 고정한다. 이번에는 설치·실행하지 않았다. 도구의 조합 가능성과 프로젝트에서의 동작 확인은 구별한다.

Nunjucks는 콘텐츠와 템플릿을 엄격히 분리하고 자동 이스케이프를 명시적으로 켠다. 템플릿은 신뢰하는 프로젝트 코드이며 임의 콘텐츠를 템플릿으로 실행하지 않는다. Nunjucks 공식 문서는 샌드박스를 제공하지 않는다고 설명한다. [Nunjucks API](https://mozilla.github.io/nunjucks/api.html)

추가 조사에서 `sanitize-html`의 기존 독립 저장소는 모노레포로 이전했음을 확인했다. 패키지를 폐기된 것으로 단정하지 않고 새 [공식 소스](https://github.com/apostrophecms/apostrophe/tree/main/packages/sanitize-html)를 기준으로 설치할 버전의 요구사항을 검증해야 한다. README와 패키지의 요구 버전 표기가 다를 수도 있으므로 실제 배포 패키지의 `engines`와 설치 테스트를 우선 확인한다.

### D02. 프로그램과 사용자 프로젝트

**추천:** `biwoom/borido`에는 앱 코드·기본 템플릿·문서·테스트 자료를 두고, 실제 `content/`, `media/`, `config/`, `dist/`는 별도로 선택한 사용자 프로젝트 루트에 둔다. 시작 시 프로젝트 경로를 명시하고 한 프로세스가 한 루트만 연다.

- 최초 마법사는 지정된 폴더에서 프로젝트 생성/기존 열기와 사이트 설정을 처리한다. 이후 진입 화면은 경론 목록으로 한다.
- GitHub 연결과 배포 설정은 건너뛸 수 있어야 한다. 설치 후 콘텐츠 작성·저장·빌드는 오프라인으로 가능해야 한다.
- 활성 경로를 보관할 전역 사용자 DB나 최근 프로젝트 관리자는 초기 제외하고 실행 인자/실행 바로가기에 경로를 명시한다. 임의 브라우저 요청으로 서버의 허용 루트를 바꾸지 않는다.
- 초기에는 외부 콘텐츠 경로·프로젝트 폴더 이동 기능을 넣지 않는다. 사용자가 앱을 종료하고 폴더를 이동한 뒤 새 경로로 다시 여는 절차를 안내한다.
- 대안: 앱 루트 안에 운영 콘텐츠를 두면 초기 설정은 짧지만 업데이트·공개 Git·백업 경계가 복잡해진다. 별도 사용자 루트를 추천한다.
- 검증: 신규/기존/다른 폴더, 오프라인 설정, 앱 업데이트와 프로젝트 이동 후 재열기에서 원본 보존 확인.

### D03. API와 로컬 서버 보호

**추천:** 파일 경로보다 콘텐츠 ID 중심 API를 두고, 요청/응답·오류 형식은 서버 구현 전에 작은 계약 문서로 정한다. `127.0.0.1` 바인딩, 허용 Host·동일 출처 검사, CORS 기본 차단, 변경 요청의 실행 세션 토큰 검사를 함께 적용한다. 이 토큰은 로컬 실행 세션용이며 사용자 계정 시스템을 추가하는 것이 아니다.

- 서버 포트는 사용 가능한 루프백 포트를 선택하거나 실행 인자로 지정하게 하고 실제 Origin을 표시한다. 셸 명령 문자열을 받는 API는 만들지 않는다.
- JSON 요청·미디어 업로드의 상한을 구분하고 샘플 크기에 맞게 정한다. 세션 정보는 일반 프로젝트 설정에 저장하지 않는다.
- 오류에는 안정적인 코드와 프로젝트 상대 위치·필드 정보를 담는다. 인증 출력과 절대 운영체제 경로는 정제한다.
- 대안: localhost 바인딩만으로 끝내는 방식은 파일 작업을 하는 서버의 요청 경계를 충분히 설명하지 못한다.
- 검증: 다른 웹 출처·위조 Host·누락/잘못된 토큰·경로 조작·심볼릭 링크·과대 요청이 파일 변경 없이 거절되는지 확인.

### D04. 파일·레코드·ID의 최소 계약

**추천:** 일반 콘텐츠는 `meta.json`+본문 파일 하나를 유지한다. 경론 트리는 아래 유형을 구분한다.

|대상|메타데이터|본문|자식|
|---|---|---|---|
|경론|`meta.json`, `type: text`|선택 `_index.md`|번역/원문/연구 영역|
|자료 영역|`_node.json`, `type: text_area`, 영역 코드|선택 `_index.md`|구조/문서 노드|
|구조 노드|`_node.json`, `type: tree_node`, `node_kind`|선택 `_index.md`|구조/문서 노드|
|본문 문서|`_node.json`, `type: text_document`|`body.md` 하나|없음|
|이야기/블로그/페이지|`meta.json`, 각 유형 코드|대표 Markdown 하나|없음|

- `text_area`·`text_document`는 상위 콘텐츠 유형을 늘리는 것이 아니라 경론 내부 레코드의 명시적인 유형 코드 제안이다.
- 부모는 폴더 포함 관계에서 해석하고 `parent_id`를 원본에 중복 저장하지 않는다. Core가 반환하는 모델에는 해석된 부모 ID를 포함할 수 있다.
- `_index.md`는 소유 레코드의 개요이며 별도 ID·상태·URL을 만들지 않는다. 개요의 공개 상태는 소유 레코드를 따른다.
- 본문 매핑 필드는 레코드에 명시하고 해당 디렉터리 안의 허용 파일만 가리키게 한다. 본문 문서는 `body.md`, 개요는 `_index.md`로 제한해 임의 경로를 막는다.
- 콘텐츠·영역·노드·미디어는 UUID v4, 분류는 별도 안정 문자열 ID를 사용한다. `order` 동률은 ID로 안정 정렬하고 편집기에 경고한다.
- 새 콘텐츠의 상태는 `draft`, 시각은 UTC ISO 8601, ID는 이동·제목 변경 시 불변으로 한다. 빌드로 시각을 변경하지 않는다.
- 대안: 폴더와 본문이 함께 있는 모든 노드를 같은 유형으로 처리하면 UI·공개·이동 규칙이 복잡해진다. 명시적인 구분을 추천한다.
- 검증: 실제 파일 한 세트의 읽기/쓰기 왕복, 개요/본문 구분, 다른 깊이의 세 트리, 중복 ID·없는 본문·문서 하위 노드 거절.

### D05. 공개 조건

**추천:** 자기 레코드와 모든 조상이 `published`일 때만 공개한다. 비공개/초안 조상 아래 공개 자식은 저장할 수 있지만 공개 출력에서 제외하며, 편집기에 차단 이유를 표시한다. 자식을 다른 위치로 자동 옮기거나 조상을 자동 공개하지 않는다.

- 개요가 있거나 공개 자손이 있는 구조 노드를 표시한다. 둘 다 없는 노드는 숨긴다. 공개할 빈 노드를 위한 추가 설정은 초기 제외한다.
- 상태 누락/오류는 공개하지 않고 스키마 오류로 보고한다. ‘비공개로 취급’과 ‘검증 오류가 없다’는 뜻을 혼동하지 않는다.
- 대안: 공개 자식을 위로 끌어올리는 방식은 저자의 구조를 바꾼다. 저장 자체를 막으면 작성 중 구조 변경이 불편하다. 공개에서 제외하고 이유를 알리는 쪽을 추천한다.
- 검증: 조상/자식 상태 조합을 트리·목록·직접 URL·breadcrumbs·검색·미디어·관련 자료에서 동일하게 적용.

### D06. 저장·동시 편집·복구

**추천:** 첫 버전은 저장 버튼과 Cmd/Ctrl+S에 의한 명시 저장으로 시작한다. 미저장/저장 중/완료/실패를 표시하고 문서 이동·창 닫기 전에 미저장 변경을 확인한다. 자동 저장은 후속 사용성 검증 뒤 검토한다.

- 저장 요청에 열었을 때의 리비전 값을 보내고 서버는 현재 파일 내용의 해시와 비교한다. 충돌 시 덮어쓰지 않고 충돌 응답과 비교/재열기 선택을 제공한다.
- 파일은 임시 쓰기 후 교체한다. 본문+JSON, 이동, 삭제처럼 여러 파일이 바뀌면 변경 전 사본과 작은 작업 기록을 프로젝트의 비공개 작업 디렉터리에 보관한다.
- 실패하면 이전 정상 상태로 복원하거나 복구 대기 상태를 명확히 남긴다. 삭제는 복구 보관소로 보내고, 보관소 정리는 별도 명시 작업으로 한다. Git이 없어도 이 보호는 동작해야 한다.
- 저장 실패 시 편집 버퍼를 유지한다. 이 추천만으로 브라우저 강제 종료 전의 모든 미저장 입력까지 복구된다고 보장하지 않는다. 미저장 입력의 주기적 복구 저장은 별도 후속 기능이다.
- 대안: 처음부터 자동 저장·여러 탭 동기화·자동 병합을 넣으면 원본을 언제 쓰는지와 실패 복구가 복잡해진다.
- 검증: 응답 지연/중단, 쓰기·교체·복원 실패, 외부 편집·동시 탭, 삭제 취소·복구에서 편집 버퍼·마지막 정상 파일 보존.

### D07. URL과 트리 이동

**추천:** 분류 경로를 분리하고 공개 문서 주소에서는 구조 노드 경로를 빼는 방식을 우선한다.

```text
/texts/
/texts/categories/{section-slug}/
/texts/{text-slug}/
/texts/{text-slug}/{area}/
/texts/{text-slug}/{area}/{document-slug}/
/texts/{text-slug}/{area}/nodes/{node-slug}/
/stories/{story-slug}/
/blog/{post-slug}/
/pages/{page-slug}/
/search/
```

- 트리와 breadcrumbs는 데이터 계층을 그대로 보여준다. 주소에 모든 계층이 없어도 문헌 구조를 잃지 않는다.
- `categories`는 경론 slug에서, `nodes`는 영역의 문서 slug에서 예약한다. 다른 시스템 경로와 자산 경로도 전체 경로표에서 예약한다.
- 문서 slug는 경론의 자료 영역 안에서 고유해야 한다. 구조 노드 slug도 같은 영역의 구조 노드 사이에서 고유해야 한다. 폴더명이 아니라 메타데이터를 기준으로 URL을 만든다.
- 같은 영역 안에서 폴더/부모가 바뀌어도 URL은 유지된다. 다른 경론/영역으로 이동하거나 URL slug를 명시 변경할 때는 이력 대상이다. 충돌 시 사용자에게 새 slug를 선택하게 하고 기존 공개 URL을 조용히 바꾸지 않는다.
- 공개 slug는 소문자 영문·숫자·하이픈을 기본으로 제안한다. 한글 제목은 보존하고 자동 음역은 하지 않는다. 자동 생성 이름도 공개 전 편집할 수 있게 한다.
- **기존 명세에서 달라지는 부분:** 기존의 `{node-path}` URL 예시를 평평한 문서 경로로 바꾸는 제안이다. 수정 없이 유지할 수 있는 것으로 위장하지 않는다.
- 대안: 계층 URL을 꼭 유지하려면 각 노드에 생성 시 `public_path`를 저장하고 이동 시에도 보존해야 한다. 가능하지만 원본 트리 외에 관리해야 할 경로 상태가 하나 더 생기므로 초기에는 평평한 URL을 추천한다.
- 검증: 분류/경론 동일 slug, 예약명, 정규화 충돌, 같은 영역 내 이동·제목 변경의 URL 불변, 접두사/도메인 환경.

### D08. URL 이력과 리디렉션

**추천:** 중앙 `config/url-history.json`에 `from`, `target_id`, `changed_at`을 기록한다. 현재 URL은 대상 ID에서 해석하여 새 주소를 중복 저장하지 않는다. 명시적 URL 변경/영역 이동 작업이 이력을 쓰고 빌드는 읽기만 한다.

- 과거 경로에서 현재 공개 대상까지 한 번에 연결한다. 순환·현재 경로 충돌·대상 미존재는 검증한다. 과거 경로의 다른 콘텐츠 재사용은 초기에는 거절한다.
- GitHub Pages에서는 정적 리디렉션 HTML과 실제 새 링크를 제공한다. HTTP 301/302를 구현한 것처럼 표기하지 않는다.
- 비공개/삭제된 대상의 이전 리디렉션은 출력하지 않고 이전 빌드의 파일도 제거한다. 공개 해제는 원격 Git 이력 삭제까지 뜻하지 않는다.
- 대안: 콘텐츠마다 이전 URL 배열을 두면 편집은 가깝지만 프로젝트 전체 충돌 확인이 분산된다. 중앙 파일을 추천한다.
- 검증: 여러 번 변경·현재 URL 충돌·루프·비공개 전환·삭제·빌드 전후 원본 무변경.

### D09. 내부 링크·앵커·제목

**추천:** 일반 Markdown 링크 안에 `[표시 문구](doc:UUID#anchor)`로 내부 문서를 표현하고 Core가 공개 URL로 변환한다. 관련 자료는 메타데이터의 ID 관계로 관리하며 본문 링크와 구분한다.

- 메타데이터 제목을 페이지 제목으로 사용한다. 본문은 기본 H2부터 작성하며, 과거 본문의 제목을 조용히 삭제/변환하지 않는다. 중복 H1은 편집기 경고로 안내한다.
- 제목 앵커는 한글·한자를 보존하는 일관된 정규화와 문서 내 중복 접미사로 생성한다. 안정적인 수동 앵커가 필요하면 `## 제목 {#anchor-id}` 같은 제한된 확장을 함께 명세할 것을 권한다. 실제 인식은 파서 토큰 단계에서 처리한다.
- 공개 본문의 없는/비공개 대상·앵커 참조는 빌드 오류로 한다. 링크만 제거해도 표시 문구에 비공개 제목이 남을 수 있으므로 공개할 문구를 저자가 수정하게 한다.
- 선택적인 관련 자료 관계는 비공개 대상을 출력하지 않고 경고한다. 원본 ID 관계를 자동 삭제하지 않는다.
- 대안: 파일 상대 경로는 외부 도구에 익숙하지만 이동 시 대규모 수정이 필요하다. 안정적인 ID 링크를 추천한다. 독립적인 Markdown 도구에서 `doc:` 링크가 바로 동작하지 않는 한계는 안내한다.
- 검증: ID 유지 이동·대응 자료 없음·한글/중복 제목·명시 앵커·없는 앵커·비공개 링크 문구·정화 후 앵커 유지.

### D10. 각주

**추천:** `[^id]` 문법, 최초 참조 순서로 번호/목록 생성, 같은 각주의 반복 참조와 여러 문단·목록·표·이미지를 지원한다. 중첩 각주와 인라인 각주 확장은 초기 제외한다.

- 정적 HTML에는 하단 각주와 실제 앵커를 둔다. JS가 켜지면 **같은 각주 DOM을** 우측 패널로 옮겨 활용한다. 하단과 패널에 같은 ID를 가진 DOM을 복제하지 않는다.
- JS가 없으면 하단 각주로 읽는다. 각주 해시로 직접 들어오면 해당 내용을 보이게 한다. 이는 일반 진입 시 패널 닫힘의 명시적인 예외로 정한다.
- 반복 참조에는 고유 참조 앵커와 돌아가기 링크를 제공하고, 클릭으로 연 경우 해당 참조로 돌아간다.
- 미정의/중복 정의·지원하지 않는 중첩은 공개 문서에서 오류, 미사용 정의는 경고로 한다.
- 대안: JS로만 각주를 만들거나 패널 전용 데이터만 출력하면 정적 접근·직접 해시·인쇄가 취약해진다. 하단 HTML을 기본으로 추천한다.
- 검증: 참조/정의 순서가 다른 문서·반복 참조·긴 각주·JS 비활성·직접 해시·패널 전환·초점/스크롤 왕복. 파서 확장의 실제 토큰/렌더러 동작도 검증한다. [각주 확장 공식 설명](https://github.com/markdown-it/markdown-it-footnote)

### D11. 미디어

**추천:** `media/assets.json`에 UUID, 프로젝트 상대 파일 경로, 유형, 대체 텍스트/캡션, 공개 상태를 기록하고 `![설명](asset:UUID)`로 참조한다. 파일 크기와 사용 목록 등 파일에서 계산할 수 있는 값은 매번 원본에 중복 기록하지 않는다.

- 자산 기본 상태는 `private`로 두고 공개에 필요한 자산만 명시적으로 `published`로 바꾼다. 공개 문서가 비공개 미디어를 참조하면 빌드 오류로 안내한다.
- 본문·각주·대표 이미지·공통 사이트 설정의 참조를 모두 조사하고 실제 필요한 공개 자산만 복사한다. 사용하지 않는 미디어는 출력하지 않는다.
- 사용자 업로드는 초기에는 일반 래스터 이미지와 PDF 중심으로 지원한다. 앱의 신뢰된 SVG 아이콘과 사용자 업로드 SVG를 구분하고 후자는 지원 검증 전 제외한다.
- 파일 이름 변경/이동은 ID를 유지한다. 삭제 전 공개/비공개 문서 모두의 참조를 검사한다. 알 수 없는 파일은 무조건 삭제하지 않고 미등록 파일로 표시한다.
- 대안: 본문에 상대 경로를 직접 쓰고 `media/` 전체를 복사하면 단순하지만 이동 안정성·비공개 자산 구분을 충족하기 어렵다.
- 검증: 동일 자산 공유·각주 이미지·대표 이미지·파일명 충돌·이동·삭제·비공개 자산·미등록/미사용 파일과 인덱스 왕복.

### D12. 분류·서지와 샘플 경론

**추천:** 신수대장경을 기준 체계로 두되, 원 목차와 [SAT](https://21dzk.l.u-tokyo.ac.jp/SAT/)·[CBETA](https://cbeta.org/) 자료를 대조하고 한국어 표시명과 외부 분류 관례를 구분해 기록한다. 이 사이트들의 존재 확인은 실제 분류/번호 전체 검증을 마쳤다는 뜻이 아니다.

- `verification_status`, 근거 URL/자료명·해당 위치·확인일을 기록한다. 분류·문헌 소속·번호는 각각 검증하고 미검증 항목을 공식 공개 목록에 넣지 않는다.
- 초기에는 사용할 경론 한 편과 필요한 분류부터 검증한다. 전체 문헌 목록을 먼저 수집하거나 외부 API를 실행 의존성으로 추가하지 않는다.
- 저자/역자는 표시명 목록, 판본은 표시명과 선택 출처, 참고문헌은 서지 문구와 선택 URL 등 최소 필드를 시작점으로 삼고, 인물/판본의 별도 지식 그래프를 만들지 않는다.
- 실제 샘플 본문은 운영자가 제공하거나 출처·사용 조건을 확인한 자료를 사용한다. 예시를 공식 서지로 확정하지 않는다.
- 검증: 선택한 문헌의 실제 출처 대조, 분류 ID 존재·소속/번호 일치·미검증 제외·선택 서지 누락 화면.

### D13. 검증·빌드 실패

**추천:** 원본 전체의 JSON 문법·식별자·스키마·경로 무결성을 먼저 검사하고, 공개 대상의 렌더링·링크·미디어 완전성을 추가 검사한다.

- 원본의 잘못된 JSON·중복 ID·필수 필드/상태 오류·허용 경로 이탈은 비공개라도 오류다. 공개 URL 충돌·공개 본문의 깨진 링크/각주/미디어·비공개 유입도 오류다.
- 비공개 문서의 작업 중 참조, 미사용 각주/미디어, 선택 서지 누락, 비공개 조상 때문에 제외된 공개 자식 등은 경고로 보고한다.
- 앱의 파일 변경 작업은 프로젝트별로 직렬화한다. 빌드는 변경과 충돌하지 않게 원본 스냅샷을 만들고, 원본/설정/템플릿/자산을 식별하는 manifest를 남긴다. 출력 검증과 입력 변경 여부 확인 후 완전한 결과만 반영한다.
- 임시 출력·이전 정상 출력·복구 기록을 구분하고, 교체 도중 실패했을 때 이전 결과 복원 절차를 둔다. 사용 중인 `dist/`를 먼저 비우지 않는다.
- 대안: 잘못된 초안을 임의 무시하면 중복 ID나 파일 충돌을 놓칠 수 있다. 모든 비공개 본문의 링크까지 차단 오류로 삼으면 집필 중 공개 작업을 불필요하게 막는다. 기본 무결성과 공개 완전성을 나누는 방식을 추천한다.
- 검증: 각 단계 실패 주입·동시 요청·외부 수정·정상 결과 보존·비공개 표식 검색·재현 가능한 manifest.

### D14. 스타일과 독서 치수

**추천:** Basecoat 기본 Vega를 초기 기준으로 고정하고 완성된 CSS 배포 파일과 필요한 JS만 로컬에 포함한다. Tailwind 전체 빌드나 모든 컴포넌트 스크립트는 필요할 때 도입한다. 기본 파일은 수정하지 않고 보리도 CSS를 뒤에 둔다.

- 기본 스타일과 필요한 파일을 복사/제공하는 경로는 [Basecoat 설치 문서](https://basecoatui.com/installation/)에서 확인했다. npm 소스 CSS를 그대로 쓰는 방식과 이미 컴파일된 배포 CSS를 제공하는 방식을 혼동하지 않는다.
- 트리는 확정된 240px를 유지한다. 본문 약 800px·우측 패널 약 300px·줄 간격 약 1.9를 **검증용 시작값**으로 사용한다. 전환점은 실제 최소 본문 폭으로 판단하고 기존 1200/900/640px 예시를 영구 규칙으로 삼지 않는다.
- 글꼴은 우선 로컬 시스템 대체 글꼴로 시작하고 한글·한자·팔리어가 불충분할 때 사용 조건을 확인한 글꼴을 로컬 포함한다. 현재 목차 강조 같은 보조 기능은 기본 동작 후 추가한다.
- 대안: 여러 스타일 팩을 먼저 비교·지원하는 작업은 보리도의 핵심 가치 검증을 늦춘다. 기본 한 가지로 실제 문헌을 읽어본 뒤 필요하면 변경한다.
- 검증: 긴 제목·한글/한자/음역·표·각주, 좁은 화면·낮은 높이·키보드·터치, CDN 차단과 레이아웃 전환 전후.

### D15. 검색과 사이트맵

**추천:** 빌드 시 공개 문서의 제목·유형·최종 URL·경론/영역 맥락·설명·본문 평문을 JSON 인덱스로 생성하고, 초기 검색은 정규화한 문자열 포함 검색으로 구현한다. 제목 일치를 먼저 보여주고 나머지는 안정 정렬한다.

- 한글 형태소 분석·퍼지 검색·외부 검색 서버·검색 순위 모델은 초기 제외한다. 단순 포함 검색이 형태소 검색을 제공하는 것으로 안내하지 않는다.
- 본문 문서는 검색 결과로 만들고 순수 구조 폴더는 결과를 중복 생성하지 않는다. 개요가 실제로 있는 경론/영역/구조 페이지는 별도 검색 문서로 포함할 수 있도록 계약을 명시한다.
- 빈 검색·일치 없음·입력 특수문자·한국어 정규화 사례를 규정한다. 큰 인덱스는 실제 크기를 측정한 뒤 분할/검색 도구 도입을 판단한다.
- 사이트맵은 고유한 현재 공개 페이지를 포함하고 검색 결과·과거 리디렉션·비공개 URL을 제외하는 정적 파일로 생성할 것을 권한다.
- 검증: 예상 한글 검색 목록, 결과에서 맞는 본문으로 진입, 공개 해제 후 인덱스/사이트맵 잔존 없음, 오프라인 검색.

### D16. MVP 탐색과 도구모음

**추천:** 핵심은 자료 트리·목차·각주·자료 영역 진입·이전/다음 문서다. 이전/다음은 현재 공개 트리의 깊이 우선 순서에서 본문 문서만 대상으로 하고 구조 개요는 제외한다.

- 자료 전환에서 명시적인 대응 ID가 있으면 그 문서로, 없으면 해당 자료 영역의 개요/목록으로 이동한다. 같은 트리 위치를 근거로 대응 문서를 추정하지 않는다. 자료가 없으면 연결하지 않는다.
- 인쇄는 첫 버전에 기본 인쇄 CSS로 지원하되 도구모음 버튼은 필수가 아니다. 본문 텍스트/링크 복사, Markdown 다운로드·글자 크기 조절은 후속으로 둔다.
- GitHub 원본 보기/이력은 공개가 허용된 원본 저장소의 공개 문서일 때만 제공한다. 공개 앱 저장소 주소를 사용자의 원본 링크로 대체하지 않는다.
- 대안: 모든 편의 버튼을 첫 버전에 넣으면 공개 적합성·브라우저 권한·반응형 검증 범위가 커진다. 읽기 탐색을 우선하는 구성을 추천한다.
- 검증: 빈 영역·대응 없는 자료·첫/마지막 문서·숨겨진 문서 건너뛰기·아이콘+레이블·긴 도구모음·인쇄 시 각주 표시.

### D17. 미리보기

**추천:** 미저장 편집 버퍼를 서버에 보내 임시 메모리 모델로 변환하고, 공개 빌드와 같은 변환 규칙·템플릿을 적용한다. 원본 저장·공개 상태 변경·원격 전송은 일으키지 않는다.

- 전체 사이트 미리보기는 마지막 성공 빌드를 대상으로 하고, 선택 문서의 미저장 미리보기와 구분한다.
- draft/private는 로컬 미리보기에서만 볼 수 있으며 상태와 미저장 여부를 표시한다. 임시 파일이 필요하면 `dist/`와 다른 비공개 작업 위치를 쓴다.
- 미리보기 HTML에 공개 불가능한 링크가 있으면 공개 빌드에서 오류가 된다는 사실을 표시한다. 로컬에서 보인다는 이유로 공개 가능하다고 판단하지 않는다.
- 검증: 미리보기 후 원본 해시 불변·공개 출력에 비공개 파일 잔존 없음·미저장/저장본 구별·동일 본문과 각주 표현.

### D18. 저장소와 배포

**확인된 사실:** 프로젝트 저장소 주소는 `biwoom/borido`, 현재 공개 저장소이며 기본 브랜치는 `main`이다. **추천 정책:** 이곳은 프로그램 소스 저장소로 사용하고 사용자 원본은 별도 프로젝트/필요 시 비공개 원본 저장소로 관리한다. 앱은 원본을 자동 커밋·푸시하지 않는다.

- 사용자 사이트의 배포 대상은 프로젝트 설정으로 따로 지정한다. `biwoom/borido`에 이 프로젝트의 시연/공개 사이트를 둘 경우 공개 결과 전용 `gh-pages` 브랜치를 선택할 수 있다. 현재 사용 중이거나 승인되었다고 가정하지 않는다.
- `dist/`는 원본 브랜치에서 추적하지 않고, 검증된 정적 결과만 배포 브랜치의 루트에 게시하는 방식을 초기 권고로 한다. `docs/`는 개발 문서용으로 사용한다.
- 앱이 Git 실행 파일과 인자를 분리해 격리된 배포 작업 디렉터리를 다루고 일반 fast-forward 푸시만 수행하는 방식을 우선한다. 원본 체크아웃을 갈아타거나 전체 변경을 자동 스테이징하지 않는다. 충돌 시 중단한다. 직접 구현 범위와 도구 비교는 배포 단계에서 로컬 bare 저장소로 검증한다.
- 배포 승인 대상은 출력 manifest/파일 해시·원본 리비전·설정·원격/브랜치다. 승인 뒤 결과나 대상이 바뀌면 다시 검토한다. 오래된 미리보기나 다른 빌드를 대신 전송하지 않는다.
- GitHub는 브랜치 또는 Actions를 게시 원본으로 지원하고, 브랜치 방식은 루트/`docs`를 지정할 수 있다. **로컬에서 명시적으로 생성물을 푸시하는 정책**을 권하며, 이후 GitHub의 Pages 처리와 구분한다. 사용자 승인 없이 앱이 자동 배포하는 기능을 넣는다는 뜻이 아니다. [GitHub 공식 게시 원본 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)
- 대안: Actions 기반 빌드도 가능하지만 원본의 공개성·원격 실행·인증·아티팩트 범위가 추가된다. 초기에는 로컬 검증 결과를 명시적으로 보내는 쪽이 프로젝트 철학에 가깝다.
- 검증: 소스/결과 분리·비공개 원본 미전송·승인 누락/대상 변경 차단·인증/권한/네트워크/충돌 오류·무강제 푸시·승인한 파일 동일성. 실제 배포는 별도 실행 범위로 둔다.

### D19. 나머지 콘텐츠 유형의 필드

**추천:** 공통 필드에 실제 화면이 사용하는 최소 필드만 추가한다.

- 이야기: 출처 목록, 원전 서지 문구, 각색 여부/설명, 선택 대표 미디어 ID.
- 블로그: 작성자 표시명, 명시적인 `published_at`, 태그 목록. 작성/수정 시각과 게시일을 구분하고 게시일 역순·동률 ID 순으로 정렬한다. 공개 전환 시 게시일을 입력/확인한다.
- 미래 게시일을 가진 `published` 블로그는 오류로 안내한다. `draft`에서는 미래 게시일 계획을 허용하되 시간 도래만으로 공개하지 않는다. 이는 자동/예약 배포와 구별한다.
- 일반 페이지: `menu_visible`, `menu_order`, 코드에서 허용한 템플릿 이름. 메뉴 표시가 공개 상태를 대신하지 않는다. 임의 템플릿 경로를 입력받지 않는다.
- ISO 시각은 UTC로 저장하고 사이트 시간대로 표시한다. 날짜가 없는 과거 게시물은 자동 추측하지 않고 공개 준비 과정에서 수정하게 한다.
- 검증: 선택 이미지/출처 없음·게시일 누락/동률/미래·시간대·비공개 메뉴·허용되지 않은 템플릿·유형별 왕복.

### D20. 스키마·설정·마이그레이션

**추천:** 스키마의 기준은 앱 코드의 JSON Schema 한 곳으로 두고, `content-types.json`은 지원하는 필드의 표시/기본값 등 편집 정책만 설정한다. 일반 설정이 필수 필드나 공개 검증 규칙을 약화시키지 못하게 한다.

- 사용자 프로젝트 설정과 레코드에 스키마 버전을 명시한다. 문서 버전·앱 버전·스키마 버전은 구별한다.
- 알 수 없는 최신 스키마는 편집/쓰기와 공개 빌드를 거절하고 호환 버전 안내를 제공한다. 단순히 JSON을 읽을 수 있다는 이유로 덮어쓰지 않는다.
- 마이그레이션은 별도 명령/작업으로 변경 목록 제시→백업→명시 실행→검증→실패 복구 순서로 한다. 앱 실행·빌드 시 몰래 실행하지 않는다.
- 미지원 필드가 있으면 원본은 그대로 보존하고 해당 레코드의 편집 저장·공개 빌드를 막은 뒤 지원 정보를 안내한다. 자동으로 필드를 삭제하거나 저장 시 누락시키지 않으며, 무제한 사용자 필드 확장기는 만들지 않는다.
- 검증: 구형/신형/알 수 없는 버전·추가 필드·설정 불일치·변환 실패·백업 복원·동일 파일 재변환 시 일관성.

### D21. 명령과 테스트 정책

**추천:** `dev`, `validate`, `build`, `test`, `test:e2e`를 일관된 명령 이름으로 사용하되 실제 기능이 연결된 시점부터 제공한다. 배포는 `build`에 섞지 않고 별도 명령/화면으로 둔다. 복구/이행 명령도 원본 변경 작업으로 분리한다.

- 단위/통합은 Vitest로 시작하고 실제 임시 파일을 사용하는 테스트를 포함한다. 브라우저 흐름은 Playwright로 확인한다. Vitest도 Vite 의존성이 있는 도구임을 인지하고 테스트 개발 의존성으로 한정한다. [Vitest 공식 시작 안내](https://vitest.dev/guide/)
- 자동 테스트에는 운영 파일 대신 fixtures를 사용한다. 작은 합성 자료와 출처가 확인된 실제 경론의 격리 자료를 함께 둔다.
- 기본 테스트는 GitHub 계정·외부 API 없이 실행한다. 실제 인증/Pages 게시와 기기 사용성은 별도 수동 검증으로 남긴다. 브라우저 바이너리는 버전에 맞게 설치하며 오프라인 실행과 최초 설치의 네트워크 필요를 구분한다. [Playwright 브라우저 안내](https://playwright.dev/docs/browsers)
- 검증: 새 환경에서 잠금 설치 후 명령 재현·실패 시 종료 코드·필수 음성 fixture·Git/프로세스 대역·현재 AGENTS 명령과의 일치.

### D22. 성능과 최종 완료 판정

**추천:** 임의의 시간/용량 수치를 영구 요구로 넣기보다 실제 경론 한 편의 정상 사례와 긴 문서·큰 트리 스트레스 사례를 명시하고 기준 환경에서 측정한다. 그 첫 측정에서 합의한 성능 예산을 개발 계획의 검증 기준으로 기록한다.

- 측정 대상은 빌드 시간/최대 메모리, 문서/검색 인덱스 크기, 첫 읽기, 목차/각주 열기와 위치 이동, 긴 트리 조작이다. 콘텐츠 규모와 OS/브라우저·기기 조건도 기록한다.
- 초기 필수 완료 조건은 데이터 무결성·원본 보존·비공개 제외·직접 URL·JS 없는 기본 읽기·키보드/모바일 동작·실패 복구다. 성능 예산이 미정인 동안 성능 작업을 통과로 표시하지 않는다.
- 느려지면 먼저 생성 결과/DOM/공통 자산을 줄인다. 전체 구조의 재작성·검색 서버·프레임워크·트리 가상화는 측정 근거가 있을 때 검토한다.
- 대안: 근거 없는 ‘모든 빌드 1초’나 ‘커버리지 100%’를 초기 완료 조건으로 두면 실제 독서 품질보다 지표를 맞추는 데 집중하게 된다.
- 검증: 반복 측정 결과와 최초 경론 흐름의 브라우저/수동 기록, 합의한 예산 대비 결과. 현재 성능을 측정하거나 보장한 것은 아니다.

## 5. 문서 통합의 추천 구조

한 파일에 모든 기획·화면·기술·작업 계획을 넣기보다, 같은 사실은 한 문서에만 정의하고 다른 문서는 참조하는 구성을 추천한다. 파일명에 버전을 붙이지 않고 문서 안에 개정일·상태를 둔다.

```text
borido/
├── README.md                  # 프로젝트 소개·저장소·문서 진입점
├── AGENTS.md                  # 실행 지침과 현재 기준 문서 링크
└── docs/
    ├── README.md              # 문서 목록·담당 범위·현재 상태
    ├── product.md             # 목적·철학·범위·핵심 흐름·MVP
    ├── content-spec.md        # 데이터·파일·ID·공개·URL·참조·미디어
    ├── ui-spec.md             # 공개 사이트·경론 읽기·로컬 편집기 UX
    ├── technical-spec.md      # 아키텍처·실행·API·저장·보안·빌드·배포
    ├── development-plan.md    # P/W 작업·선행 조건·테스트·완료 증거
    ├── decisions.md           # D01–D22의 제안/채택/대체 상태와 근거
    └── archive/
        ├── 2026-10-29-baseline/ # 기존 기획/명세 6개와 로드맵 원문
        └── 2026-10-29-review/   # 기존 검토·계획·지침 초안·이 제안 기록
```

위 경로와 새 파일은 **이번에 생성/이동하지 않은 재편 제안**이다. 기술 명세 안의 API와 데이터 명세의 스키마 표가 너무 커질 때에만 해당 전문 문서를 추가 분리한다. 처음부터 항목마다 별도 파일이나 22개의 ADR 파일을 만들지는 않는다.

|현재 자료|새 기준 문서로 가져갈 내용|
|---|---|
|기획문서 v0.2|`product.md`에 목적·철학·범위·MVP. 데이터/화면/기술 상세는 각 전문 문서를 참조|
|콘텐츠 데이터 및 파일 구조 명세서 v1.0|`content-spec.md`의 기준. 노드·공개·URL·서지·미디어 계약 보완|
|정적 사이트 화면 명세서 v1.0|`ui-spec.md`의 공개 사이트 공통·유형별 화면|
|경론 읽기 화면 상세 명세서 v1.0|같은 `ui-spec.md`의 독서 화면 절. 공통 레이아웃과 중복 서술 제거|
|로컬 편집기 설계서 v1.1|편집/저장 UX는 `ui-spec.md`, 시스템/보안/인증은 `technical-spec.md`, 모델은 `content-spec.md`로 분리|
|기술 설계 및 개발 계획서 v1.0|실행 계약은 `technical-spec.md`, 작업 순서는 `development-plan.md`, 후보/미결정은 `decisions.md`로 분리|
|개발 로드맵·개발 작업 계획|`development-plan.md` 하나로 통합하고 기존 P/W ID 유지. 겹치는 설명과 잔여 내보내기 텍스트 제거|
|문서 검토·이 추천안|I→D→새 명세 절→W 연결표와 결정 이력으로 요약. 상세 검토 원문은 archive에 보존|

예를 들어 공개 상태의 계산식은 `content-spec.md`에만 정의하고, 화면 문서는 그 결과의 표시·오류 안내를 설명한다. 기술 문서는 같은 계산을 다시 쓰지 않고 Core가 적용하는 위치와 검증 경계를 설명한다. 테스트 기대값은 기준 규칙을 참조한다.

원문 아카이브는 설명용 인덱스에서 과거 문서임을 표시하고 현재 구현 근거로 자동 선택하지 않는다. 새 기준 문서의 해당 절이 과거 어떤 요구와 결정을 대체했는지 연결한다. 원문 자체의 문구를 고쳐 새 결정이 과거에도 있던 것처럼 만들지 않는다.

## 6. 재작성 전에 검토할 중요한 선택

22건을 모두 같은 무게로 한 번에 논의할 필요는 없다. 다음 네 가지가 파일·화면·검증 구조를 크게 바꾸므로 우선 검토하는 것이 좋다.

1. **프로그램과 사용자 프로젝트 분리**: 공개 `biwoom/borido`를 프로그램 저장소로 사용하고 운영 원본은 밖에 둘 것인지.
2. **트리와 공개 URL 분리**: 권/장 폴더를 URL에 모두 넣는 대신 평평한 문서 URL을 사용할 것인지.
3. **명시 저장으로 시작**: 자동 저장을 초기 필수에서 빼고 실패·충돌·복구를 먼저 완성할 것인지.
4. **초기 필수 탐색 범위**: 트리·목차·각주·자료 영역·이전/다음을 필수로 하고 다운로드/복사 등은 후속으로 둘 것인지.

나머지는 위 추천안을 기본 초안으로 작성할 수 있지만 사용자 검토 전 채택 상태로 변경하지 않는다. 치수·글꼴·성능 예산·패키지 패치 버전은 별도 확인 조건을 남긴다.

## 7. 후속 문서 재편 작업과 검증 기준

이 절은 다음 문서 작업의 구체적인 순서다. 이번 사용자 요청의 ‘우선 검토’ 범위와 구분한다.

1. 현재 원문과 검토 자료의 파일 목록·해시를 기록한다. 아카이브 대상과 새 문서의 담당 범위를 확정한다.
2. `docs/`에 통합 기획/명세 초안을 작성하고, 추천 중 채택된 내용과 여전히 실증이 필요한 내용을 구분한다. 이 단계에서는 원문을 보면서 요구 누락을 대조한다.
3. I01–I12·D01–D22 각각에 새 문서 절·채택 상태·관련 P/W 작업·검증 기준을 연결한다. 충돌한 요구를 없애는 경우 이유를 남긴다.
4. 새 초안의 완전성을 확인한 다음 기존 문서를 아카이브로 이동한다. 원문 바이트는 보존하고 원본 지침 초안도 별도 보관한 뒤 루트 AGENTS를 갱신한다.
5. 루트/문서 README와 AGENTS의 링크를 갱신하고 중복된 기준 문서가 남지 않도록 한다. Git 초기화·커밋·푸시와 기능 구현은 이 문서 작업에 섞지 않는다.

완료 판정은 다음을 모두 확인하는 것이다.

- 기존 원문의 해시 일치와 파일별 이동 대응표.
- 과거 요구와 12개 쟁점·22개 결정·P/W 작업의 추적표. 누락되거나 이유 없이 삭제된 MVP 요구 없음.
- 문서 안에서 확정/제안/검증 대기 상태가 일관됨. 같은 항목을 서로 다른 문서에서 다시 미결정/확정으로 쓰지 않음.
- 파일/ID/공개 조건/URL/미디어의 예시가 서로 맞고 경로 충돌·ID 중복·상태 조합의 기대값이 명시됨.
- 로컬 문서 링크, 표 구조, 작업 의존성, archive와 최신 문서의 표시 검증.
- 테스트 명령이 아직 미구현인 사실과 외부/실행 검증을 수행하지 않은 범위를 정확히 표시.
