6개 요청 문서의 본문 전체와 추가 로드맵을 검토했다. 문서 제목의 버전이나 작성 순서만으로 일괄 우선순위를 만들지 않는다. 기획의 목적과 각 전문 명세의 담당 범위를 함께 적용하고, 상세 문서가 명시적으로 구체화한 항목은 그 근거를 기록한다. 서로 다른 요구가 남으면 해당 구현을 보류하고 결정 과제로 관리한다.

판정은 다음과 같이 구분한다.

- **확정 원칙**: 명시적 요구이며 후속 결정 목록과 상충하지 않는 항목.
- **명시적 구체화**: 이전 문서의 여지를 상세 문서가 좁힌 항목. 원문 동기화는 필요할 수 있다.
- **충돌·긴장**: 필수 여부나 표현이 달라 같은 구현·완료 판정을 보장하지 못하는 항목.
- **누락·미결정**: 원칙은 있지만 저장 형식, 동작 또는 검증의 기대 결과가 정의되지 않은 항목.
- **권장·예시**: 확정 기술이나 실행 가능한 계약으로 승격하지 않는 항목.

검토 시 폴더에는 기존 Markdown 7개만 있다. `AGENTS.md`, 애플리케이션 코드, `package.json`, 잠금 파일, 테스트, Git 저장소는 없었다. `git status`는 저장소가 아니라는 오류를 반환했다. 따라서 실행·빌드·테스트·버전 호환성을 확인한 상태가 아니다.

## 3. 발견한 충돌과 구현 공백

아래 I 항목은 문제 조사 결과이며, D 항목은 이를 해소할 결정 과제다. 추론으로 발견한 위험을 이미 발생한 결함이나 확정 요구로 표시하지 않는다.

### I01. 기술 선택의 확정 수준이 문서 안에서도 다름

- 근거: 기술 §6의 권장 표, §6.3의 Nunjucks 사용 서술, §15의 JSON 스키마·템플릿·서버·상태 관리 재검토 목록. 로드맵 §4는 같은 표를 ‘명시된 선택’으로 설명한다.
- 영향: 후보가 승인된 의존성으로 굳거나, 잠금 파일 없이 설치될 수 있다.
- 처리: 확정 원칙과 후보를 위에서 분리했다. 도입 전 D01에 선택 근거와 버전 검증을 기록해야 한다.

### I02. 분류 URL과 경론 URL이 같은 자리를 차지함

- 근거: 데이터 §15.2, 화면 §9.2, 편집기 §16에 `/texts/{section-slug}/`와 `/texts/{text-slug}/`가 함께 있다.
- 재현 가능한 예: 분류와 경론의 slug가 모두 `sample`이면 둘 다 `/texts/sample/`을 요구한다. 이는 경로 예시를 그대로 적용했을 때의 충돌 가능성이다.
- 누락: 별도 네임스페이스, 전역 slug 제약, 예약 경로 중 어느 정책인지 불명확하다. `translation` 등 영역명과 하위 경로, `/pages/`·홈·검색·404·자산 경로도 전체 경로표가 필요하다.
- 결정: D07. 자동 이름 변경이나 새 URL 규칙을 이번에 채택하지 않았다.

### I03. 구조 노드·본문 문서·영역·개요를 저장할 최종 계약이 없음

- 근거: 데이터 §1.2는 레코드가 본문 경로를 참조한다고 하나 공통 필드(§5.1)에 본문 경로 필드가 없다. §8.3은 구조와 본문을 구분하며 `_index.md`를 개요로 연결하지만 §9.1 예시는 `_node.json`과 일반 Markdown을 같은 폴더에 둔다. §8.4의 `type`은 구조용 `tree_node`이고 본문 문서용 스키마는 없다.
- 누락: 영역의 소속 경론 관계·영역 구분, 본문 문서의 유형/ID/상태 저장 위치, 부모 관계를 폴더에서 유도할지 필드에 기록할지, `_index.md`의 ID·상태·제목·URL 및 소유 레코드가 정의되지 않았다.
- 영향: 예시를 서로 다르게 해석하면 구조 노드와 본문을 합치거나 중복 ID·중복 URL이 생긴다. `order` 동률의 안정적 보조 정렬도 미정(§8.5).
- 결정: D04. 예시가 곧 잘못된 구조라고 단정하지 않고 실제 파일 한 세트로 계약을 검토해야 한다.

### I04. 공개 상태의 부모 방향과 ‘빈 노드’ 판정이 불완전함

- 근거: 데이터 §5.2·§8.6·§17, 기술 §5.5는 상위 공개가 하위를 자동 공개하지 않는다고만 규정한다. 상태가 없거나 틀리면 공개하지 않는다(데이터 §5.2).
- 미정 사례: 비공개 경론/영역/구조 노드 아래 `published` 문서가 있을 때 제외·차단·재배치 중 무엇인지, 본문은 없지만 공개 하위가 있는 노드와 개요만 있는 노드를 ‘빈 노드’로 볼지, 모든 하위가 비공개일 때 조상 표시 여부.
- 영향: 직접 URL, 트리, breadcrumbs, 검색, 관련 링크에서 부모 제목·경로가 유출되거나 고아 문서가 생길 수 있다.
- 결정: D05. 공개 조건 조합별 결과표가 먼저 필요하다. 상태 누락 시 비공개라는 원칙과 빌드 실패 여부(D13)는 별개다.

### I05. URL 이력의 저장·변경 시점과 URL 독립성에 여지가 남음

- 근거: 데이터 §16.2는 중앙/콘텐츠별 저장을 선택 가능하게 두지만 §20.4는 중앙 파일에서 관리·자동 기록한다고 서술한다. 기술 §9.4도 중앙 관리 방향이나 §15에서 확정을 요구한다.
- 추가 공백: 데이터 §15.3의 파일 이동과 URL 분리, §18.2의 이동 시 이력 갱신을 함께 만족시킬 공개 경로 보존 방식이 없다. `node-path`가 파일 폴더를 그대로 뜻하는지도 미정이다.
- 영향: 빌드 중 이력을 기록하면 ‘빌드는 원본을 수정하지 않는다’는 원칙과 충돌한다. 비공개/삭제된 대상으로 이어지는 과거 리디렉션도 공개 정보가 될 수 있다.
- 결정: D07–D08. 이력 갱신은 어떤 명시적 변경 작업에서 수행할지 정하고, 빌드는 읽기만 해야 한다.

### I06. 도구모음의 MVP 범위가 일치하지 않음

- 근거: 기획 §7.3은 다운로드·본문 복사·인쇄·이전/다음·관련 자료 이동 등을 초기 도구로 열거하되 실제 제공은 조건부로 둔다. 화면 §4.5는 목차·각주만 필수, 자료 전환·링크 복사·인쇄 등은 이후 기능으로 둔다. 읽기 §7.1은 다른 자료가 있을 때 자료 전환을 기본 버튼으로 둔다.
- 영향: 완료 기준이 달라진다. 자료 유형 진입 링크와 특정 문서의 대응 관계도 서로 다른 기능이다.
- 결정: D16. 다운로드/원본 링크 포함 시 비공개 원본 저장소, 원본 Markdown 내부 ID·링크·주석 등의 공개 적합성도 D18과 함께 검토한다.

### I07. 초기 진입 화면과 프로젝트 경로 변경 범위가 불일치함

- 근거: 기획 §3.2는 초기화 후 대시보드, §9.2는 경로·백업/복구 설정을 포함한다. 편집기 §4.3은 복잡한 대시보드를 제외한다. 따라서 대시보드 전부가 금지된 것은 아니지만 실제 시작 화면은 미정이다.
- 경로: 기획 §3.2는 경로 변경 시 이동·복사·검증 제공, 데이터 §2.3·§23은 초기 지원을 제한하며 구체 범위를 후속 검토한다. 기술 §4.2는 앱 업데이트와 사용자 프로젝트를 분리하나 기본 구조는 한 루트로 표현한다.
- 추가 공백: 활성 프로젝트 경로를 최초에 어디서 읽는지, 앱 설치 위치와 사용자 프로젝트 관계, GitHub 설정 없는 오프라인 최초 실행의 필수 입력.
- 결정: D02. 임의 전역 설정 디렉터리나 다중 프로젝트 기능을 도입하지 않는다.

### I08. 각주 지원 범위와 정적 접근 방식이 완결되지 않음

- 근거: 화면 §4.6은 각주 안의 다른 각주도 작동해야 한다고 서술하지만 데이터 §13.5는 중첩 각주 지원 범위를 따로 정하도록 한다. 화면은 ‘정의된 순서’, 읽기 §5.1은 ‘문서 순서’라고 표현한다.
- 미정 사례: 정의 순서와 최초 참조 순서가 다른 경우, 같은 각주의 여러 참조, 미정의 참조·사용되지 않는 정의·긴 표/이미지, 직접 각주 해시 진입 시 기본 닫힘과의 관계.
- 접근성 공백: 읽기 §12.3·화면 §11.3의 JS 없는 본문·주요 링크 접근과 기본 숨김 패널을 함께 만족할 각주 대체 표현이 없다.
- 결정: D10. 표준 각주 문법 유지·본문 왕복·원본 보존은 확정이며, 번호/지원 범위/대체 표현은 미정이다.

### I09. 미디어 공개 원칙에 비해 식별·저장·검증 규칙이 부족함

- 근거: 데이터 §4.3은 미디어 ID를 권장, §11.2는 미디어별 JSON을 의무화하지 않으며, §11.3은 안정적인 내부 자산 참조를 설계하도록 한다. 기획 §12는 비공개 미디어도 제외하도록 한다.
- 누락: 중앙 인덱스의 형식·위치, 본문 참조 문법, 직접 파일 경로 지원 여부, 사용 여부 계산, 미디어 자체 비공개 상태와 공개 문서의 참조가 충돌할 때 정책, 공유/공통 자산 포함 기준.
- 영향: 미디어 폴더 전체 복사나 이동 시 참조 단절로 이어질 수 있다. 공개 문서의 각주·대표 이미지·템플릿도 참조 집합에 포함할지 정해야 한다.
- 결정: D11. ‘공개 콘텐츠에서 필요한 자산만 포함’이라는 원칙은 유지한다.

### I10. API·저장·복구·빌드의 실패 계약이 빠져 있음

- 근거: 기술 §3.3·§7.2는 함수/엔드포인트를 예시로만 두고 별도 명세를 요구한다. §5.4·§8.3은 안전한 저장/빌드 방향만 정한다. 편집기 §12·§14는 저장 실패·미리보기 규칙을 후속 검토한다.
- 추가 조사 과제: 요청 출처/Host 보호 등 로컬 서버의 다른 웹페이지 접근 방어, 포트·요청 제한, 동시 탭/외부 편집 충돌, 여러 파일 변경의 부분 실패, 복구 기록의 위치·보존·Git 미초기화 상태, 미저장 본문 미리보기, 미리보기의 비공개 자산 격리.
- 빌드: 전체 데이터 검증과 공개 변환의 경계, 비공개 콘텐츠 오류의 빌드 차단 여부, 임시 디렉터리 교체 실패·동시 빌드·이전 출력 정리, 승인 후 파일 변경 시 배포 대상 동일성도 미정이다.
- 결정: D03·D06·D13·D17·D18. 이들은 검토에서 드러난 공백이며 특정 잠금·인증·복구 구현을 채택한 것은 아니다.

### I11. 공통 필드만으로 나머지 요구를 구현할 수 없음

- 근거: 데이터 §6.2·§10·§20·§23; 화면 §5–7·§10·§15; 편집기 §21.
- 누락: 서지 배열/객체 구조, 검증된 분류 상태 필드와 출처, 이야기 출처·각색·대표 이미지, 블로그 게시일·태그·정렬, 일반 페이지 메뉴·템플릿 선택, 사이트 URL과 접두사 필드, 검색 문서 단위·인덱스 형식·검색 동작, 스키마 버전과 마이그레이션.
- 결정: D04·D12·D15·D19–D20. 예시 서지 번호나 임의 필드를 운영 데이터로 확정하지 않는다. ‘사이트맵에도 비공개 정보 제외’는 확정이지만 사이트맵 자체 생성 범위/형식은 별도 확인한다(D15).

### I12. 단계 번호와 일부 참고 문서 품질이 다름

- 근거: 기획 §13은 설계 단계부터, 데이터 §21은 모델부터, 편집기 §19는 6단계, 기술 §13은 8단계다. 로드맵은 0–7단계로 배포와 안정화를 합치고 중간에 복원되지 않은 파일명 참조·‘0/6’, ‘체크리스트 복사’ 텍스트가 남아 있다.
- 처리: 서로 다른 문서 목적의 단계 번호를 제품 충돌로 단정하지 않는다. [개발 작업 계획](<개발 작업 계획.md>)은 기술의 1–8단계에 준비 0단계를 추가하고 작업 ID로 추적한다. 로드맵 원문은 수정하지 않았다.

### 충돌로 오인하지 말아야 할 명시적 구체화

- **240px 트리**: 화면 §15에는 미확정으로 남지만 읽기 §1·§2.3·§13과 기술 §9.2에서 명시적으로 확정한다. 현재 기준은 240px이며 긴 제목으로 검증한다. 800px 본문·300px 패널·1.8–2.0 줄 간격·1200/900/640px 전환점은 잠정값이다.
- **UUID v4**: 데이터 §4.2에서는 권장이지만 편집기 §8.1에서 기본 형식으로 구체화한다. 분류의 `taisho`·`madhyamaka` 같은 안정적 문자열까지 UUID로 강제하지 않는다. 실제 분류 목록의 유효성은 별도 검증한다.
- **GitHub 인증**: 기획 §3.3의 Git 인증 활용을 편집기 §6·기술 §10에서 `gh` 기본 경로로 구체화한다. 모든 환경에서 반드시 키체인에 저장된다고 보장하지 않는다.
- **UI와 디자인 공유**: 기획 §2.2의 모델·디자인 규칙 공유와 기술 §3.2의 UI 컴포넌트 공유 비강제는 양립한다. 공유 대상은 규칙이며 편집·독서 화면의 컴포넌트는 별도 구현 가능하다.
